# 案例

> **状态：空。这是全站最重要的缺口，且是唯一无法靠检索或推理补上的。**

外部审查把「真实案例」列为缺口清单第 1 位，并在「一个 CIO 会问的十个问题」中把它评为 **0/5**：

> 「你有做过的真实案例吗？效果数据呢？」——这是买方的**第一道过滤器**，不是第七道。
> 全库零案例、零效果数据。这一问会在第一次会议的前十分钟出现。

**为什么这里是空的**：本站的其他内容可以通过整理、核实与推理产出，案例不能。它只能来自作者自己的项目经历。**编造案例会摧毁本站赖以立足的全部可信度**——尤其是在一个把「区分共识与判断」当作核心机制的站点上。

---

## 需要什么样的案例

**一个失败的案例比三个成功的案例更有价值。**理由与本站写「未解问题」「本方法论覆盖不到的失败原因」的理由完全相同：只讲成功的方案在买方眼里是可疑的。

### 最低要求

一个案例只要能回答下面六个问题，就已经强于现在的零案例状态：

1. **什么行业、什么规模、什么起点**（M0/M1/M2）
2. **选了哪个决策，为什么是它**——对应 [四象限与六条标准](../20-实践/02-首个120天.md)
3. **本体建了几个对象，花了多久**
4. **落点行动是什么，可逆性是哪一级，起步在哪个自治级别**
5. **哪个旧动作被取消了**（或者：为什么没有取消成）
6. **结果如何，以及哪里判断错了**

### 脱敏规则

- 行业与规模保留，企业名称与人名去除
- 具体数字可以改为量级（「日均数千次」而非精确值）或相对值（「较基线下降约三成」）
- **不可为了叙事完整而补造未发生的环节**——缺失的环节直接写「这一步当时没做」

### 模板

```markdown
# 案例 · <行业> <决策名称>

| 项 | 内容 |
|---|---|
| 行业 / 规模 | |
| 起点成熟度 | M__ |
| 时间跨度 | |
| 我的角色 | |

## 1. 背景与选型
为什么选这个决策？当时排除了哪些候选？

## 2. 本体
建了哪几个对象？哪个对象最难？标识映射花了多少工夫？

## 3. 行动与自治
落点行动、可逆性级别、起步自治级别、晋级/未晋级的原因

## 4. 结果
业务指标变化（量级或相对值）、人机一致率、被取消的旧动作

## 5. 哪里判断错了
**这一节必须写。**当时的哪个判断事后证明是错的？

## 6. 如果重来
```

## 在案例补上之前，方案里应当怎么说

**〔判断〕** 诚实地说明现状，比含糊带过更有说服力：

> 「这套方法论目前没有公开可引的完整案例。它来自我在企业与产业软件领域的实践经验与对公开材料的系统整理，其中哪些是领域共识、哪些是我的判断，全文都做了标注。
> 如果案例是你决策的必要条件，我们可以先做一次成熟度诊断或决策清单工作坊——**那半天本身就会产出一份对你有用的资产，且不依赖你先相信我的方法论**。」

这个回答把「没有案例」从一个弱点转成了一个**低承诺的合作入口**。
