# 反模式清单

> 按「症状 → 根因 → 纠正」组织。这份清单在项目评审时逐条对照使用。

---

## A. 立项与范围

### A1｜从数据出发
**症状**：项目从「我们有哪些数据」开始，做出一堆没人要的能力。
**根因**：正向推导产生可能性列表，不产生需求。
**纠正**：从 [决策清单](03-决策清单工作坊.md) 开始。

### A2｜战略决策优先
**症状**：第一个场景选了「最重要的决策」——低频、不可逆、多方博弈。
**根因**：把重要性当成优先级。
**纠正**：首批必须落在「高频 + 可逆」象限。重要 ≠ 适合先做。

### A3｜平台化冲动
**症状**：还没有一个场景跑通，就开始做「通用中台」「插件框架」。
**根因**：违反「复杂度必须付租金」。
**纠正**：只有一个实现且没有稳定变化轴时，不提前建通用框架。第二个场景出现后再抽象。

### A4｜宽而浅的 PoC
**症状**：接了 10 个数据源、做了 5 个场景，但没有权限、审计、写回。
**根因**：证明了「模型能做对」，没证明「生产可行」。
**纠正**：极窄但完整。见 [首个 120 天](02-首个120天.md)。

## B. 本体

### B1｜本体膨胀 {#本体膨胀}
**症状**：有 300 张表就建 300 个对象；建了一年还没上线。
**根因**：缺少准入判据，尤其是「有绑定行动或明确决策用途」这一条。
**纠正**：本体按决策增量生长；第一版 5 个对象以内。

### B2｜只读本体
**症状**：本体建完了，没有任何行动绑定。
**根因**：本体被当成语义文档而非可执行层。
**纠正**：无行动的对象必须有明确决策用途，否则删掉。

### B3｜IT 定义本体
**症状**：对象的业务定义来自字段注释；Owner 是数据团队。
**根因**：把本体当成建模工作。
**纠正**：业务定义、IT 实现；Owner 必须是业务方具体的人。

### B4｜绕过本体的捷径
**症状**：报表直连数据库、Agent 写自由 SQL、前端硬编码业务公式。
**根因**：本体是「可选的」而非「唯一的」。
**纠正**：除本体外不存在第二条通往业务语义的路径。发现即按缺陷处理。

### B5｜忽略标识映射
**症状**：假设各系统 ID 能对上，关系连不起来。
**纠正**：标识映射单独立项；保留未匹配与冲突清单。

## C. 数据与事实

### C1｜数据湖谬误
**症状**：数据都集中了，业务侧感受不到变化。
**根因**：把物理集中当成语义统一。
**纠正**：本体在湖之上，且由决策驱动接入范围。

### C2｜时点错误
**症状**：用今天的主数据解释昨天的业务。结论偏乐观，且不报错。
**纠正**：双时间轴 + 有效期区间。见 [事实层](../15-DIA框架详解/05-F-事实层.md)。

### C3｜缺失值填充
**症状**：缺数据时用 0 或前值填充，指标虚假正常。
**纠正**：缺失就是缺失，标记为不可用，触发失败关闭。

### C4｜可变的历史
**症状**：直接 UPDATE 历史数据。
**后果**：无法重放，无法回答「三周前它为什么那么建议」。
**纠正**：只增不改，修正用新记录表达。

## D. 智能与 Agent

### D1｜什么都用大模型
**症状**：用大模型做一个 if 语句能做的判断。
**纠正**：能写死的不用模型，能用小模型的不用大模型。

### D2｜自由 SQL Agent
**症状**：给 Agent 数据库连接，让它自己查。
**后果**：口径失控、权限失控、不可审计、不可回归。
**纠正**：只给本体工具集。

### D3｜演示驱动
**症状**：用几个漂亮的 demo 案例代替评测。
**纠正**：没有冻结的评测集不上线。

### D4｜一步到全自动
**症状**：上线即全自动执行。
**纠正**：从 L1 起步，逐级晋升，晋级条件事前写死。

### D5｜追求零弃权
**症状**：把「不确定」当成缺陷，逼系统必须给答案。
**根因**：把弃权理解为能力不足，而非安全特性。
**纠正**：弃权率是核心指标；从不弃权的系统是危险的。

### D6｜提示词在生产手改
**症状**：有人「优化」了提示词，指标悄悄降了，两周后才发现。
**纠正**：提示词是代码，进版本控制，改动即回归。

### D7｜把 Agent 当员工
**症状**：期望「自主搞定」，但不给输入输出合同与成功判据。
**纠正**：自主是授权描述，不是能力描述。用分级自治表达。

---

## E. 行动与写回

### E1｜只读陷阱
**症状**：做成了会说话的看板，上线三个月日活个位数。
**纠正**：立项时必须回答「被允许改变什么」。

### E2｜第二套真相
**症状**：平台自己存了一份业务状态，与 ERP 不一致。
**纠正**：写回权威系统。判据：关掉平台，业务数据是否完全不受影响。

### E3｜无幂等
**症状**：重试导致重复下单、重复调价。
**纠正**：幂等键是必填项。

### E4｜参数无边界
**症状**：一个小数点错误导致调价 100 倍。
**纠正**：参数范围约束写进行动契约，是安全边界。

### E5｜R3 在不满足四条件时开放自动
**症状**：不可逆动作开放为全自动，但没有单次上限、没有总量上限、补偿路径没演练过、或没有具名担责人。
**后果**：一次事故毁掉整个项目的信任。
**纠正**：四条件缺一即保留人闸；或用「R2 前置 + R3 确认」拆解。
> ⚠️ 此前本站写「R3 永远人闸」——**这作为对现实的描述是错的**（程序化广告、自动放款、自动触达都在全自动跑）。已改为条件化规则。

### E6｜无频次上限
**症状**：每次都在参数范围内，但一天调用五千次。
**后果**：薅羊毛、失控循环、成本击穿。
**纠正**：行动契约第 10 要素「频次上限 / 速率限制」必填。**参数范围管单次幅度，管不了总量。**

### E7｜无主自动执行
**症状**：L3/L4 已经跑起来了，但说不出它以谁的身份跑、谁担责。
**后果**：通常意味着悄悄配了一个服务账号——「不存在超级 AI 身份」已经破了。
**纠正**：岗位委托身份 + 权限下界原则；岗位空缺自动降级 L2。

## F. 治理与组织

### F1｜没有旧动作被取消
**症状**：系统上线，流程照旧，只是多了一个要看的东西。
**纠正**：交付必须包含「被取消的旧动作」。落地的标志是减法。

### F2｜担责者是系统
**症状**：出问题时找不到具体的人负责。
**纠正**：担责者永远是人。找不到就不上自动执行。

### F0｜确认剧场
**症状**：L2 场景的人工批准率长期 ≥95%，审批变成点一下。
**根因**：批准率随时间上升而审查深度下降，这是已被纵向研究记录的规律，不是个别人偷懒。
**纠正**：监控批准率；≥95% 时要么晋级 L3 + 抽检，要么承认这个检查点无效并重新设计。**不要维持一个形式上的确认按钮。**

### F3｜只记录成功
**症状**：看板只展示成功案例，拒绝/失败/推翻不留痕。
**后果**：放弃了系统改进的唯一信息来源。
**纠正**：坏消息不可隐藏。人工推翻理由结构化收集。

### F4｜事后议定晋级条件
**症状**：看到效果后再商量「算不算达标」。
**纠正**：晋级条件在上线前写进决策卡，冻结。

### F5｜成本只告警不熔断
**症状**：夜间成本失控无人处理。
**纠正**：熔断必须是停止。

### F6｜回滚需要审批
**症状**：出事故了还在等审批。
**纠正**：回滚不需要审批；需要审批的是发布。

### G · 内容与论证（新增，针对方法论本身）

### G1｜用没有出处的数字做判据
**症状**：「第二个场景应复用 60% 以上」「本体建设通常 12–18 个月」——数字承担论证功能，却没有来源。
**后果**：一句「这个数哪来的」就能击穿整套论证。
**纠正**：数字要么有出处，要么标为「示意 / 经验估计」，要么删掉改为定性表述。**被用作判据的数字，必须由团队自己设定并冻结，而不是采用一个来历不明的外部数字。**
> 本站自己犯过这一条，见 [引用与数据来源](../40-参考/04-引用与数据来源.md) 的编辑规则。

### G2｜把个人观点标为共识
**症状**：〔共识〕后面跟着一个没有出处的比较级评价（「最强」「成本低」「唯一一个」）。
**纠正**：〔共识〕必须有可点击出处，否则降级〔判断〕。

### G3｜用二手转述做一手判断
**症状**：从某个博客/公众号抄来一个框架，当成官方表述写进方案地基。
**后果**：读过一手文档的人会在第一页发现，之后不再相信材料里任何一句关于外部世界的陈述。
**纠正**：**凡是作为架构地基使用的外部概念，必须核实到一手来源。**
> 本站在 Palantir 本体模型上犯过这一条。

## 评审用速查表

项目评审时逐条问：

- [ ] 需求是从决策倒推的吗？（A1）
- [ ] 第一个场景是高频+可逆吗？（A2）
- [ ] 有没有过早的平台化抽象？（A3）
- [ ] 本体第一版是否 ≤5 个对象？（B1）
- [ ] 每个对象有业务 Owner 吗？（B3）
- [ ] 有没有绕过本体的路径？（B4）
- [ ] 回溯分析用的是当时可知的数据吗？（C2）
- [ ] 缺数据时系统怎么办？（C3）
- [ ] Agent 能自由查数据吗？（D2）
- [ ] 评测集冻结了吗？（D3）
- [ ] 起步自治级别是几级？（D4）
- [ ] 关掉平台业务数据受影响吗？（E2）
- [ ] R3 若已自动，四条件是否齐备？（E5）
- [ ] 行动契约有频次上限吗？（E6）
- [ ] L3/L4 说得出以谁的身份跑、谁担责吗？（E7）
- [ ] 人工批准率是多少？（F0）
- [ ] 哪个旧动作被取消了？（F1）
- [ ] 担责者是谁？（F2）
- [ ] 晋级条件是事前定的吗？（F4）
- [ ] 方案里的数字有出处吗？（G1）
- [ ] 标〔共识〕的都有来源吗？（G2）
- [ ] 引用的外部框架核实到一手了吗？（G3）
