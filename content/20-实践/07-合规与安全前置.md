# 合规与安全前置

> **2026-08-23 新增。**外部审查指出：全站此前对等保、数据分类分级、个人信息保护、数据出境、提示注入**零字提及**，而这些是买方的**一票否决项**——合规过不了项目不会立项，安全评审过不了权限开不出来。
>
> 本页是**清单不是保证**。合规判断必须由企业法务与合规部门做出，本页只提供在**技术设计阶段**就该问的问题，以免到评审时才发现要重做。

---

## 一、为什么必须前置

**〔判断〕** 合规与安全在企业 AI 项目里的位置，与在传统 IT 项目里不同：

| | 传统 IT 项目 | 决策智能平台 |
|---|---|---|
| 数据流向 | 系统内闭环 | 业务数据进入模型（可能是第三方的） |
| 影响范围 | 记录被修改 | **业务状态被改变**（写回 ERP/OMS） |
| 可解释性 | 代码即解释 | 需要专门设计证据链 |
| 攻击面 | 接口与权限 | **加上「被输入操纵」** |

后果是：**合规评审的介入点必须早于架构定型**，否则「模型部署形态」「数据能否出域」「哪些属性可进上下文」这些结论一旦变化，本体与工具设计要整体返工。

**实践取向**：在 [首个 120 天](02-首个120天.md) 的阶段一（Day 1–30）就完成本页的清单，而不是等到上线前。

## 二、合规清单

### 2.1 数据分类分级 → 本体属性级权限

**这是本方法论与合规要求最大的一个协同点，应当主动利用。**

企业数据分类分级的结论（公开 / 内部 / 敏感 / 核心，以及个人信息、重要数据的认定），**天然可以映射到本体的属性级权限**：

```
数据分类分级结论  →  本体属性的 敏感度标记
                  →  属性级权限规则
                  →  Agent 上下文准入规则（哪些属性允许进入上下文）
                  →  证据链的脱敏规则
```

**〔判断〕** 一旦建立这个映射，「这个 Agent 能看到什么」就有了一个**可以拿给合规看的、结构化的答案**，而不是一句「我们会注意的」。这是本方法论在合规评审上的主要优势，应当在方案里显式呈现。

**必须在阶段一回答**：

- [ ] 每个本体对象的属性，是否已标注敏感度等级？
- [ ] 哪些属性含**个人信息**？其中哪些是**敏感个人信息**？
- [ ] 哪些数据被认定为**重要数据**？
- [ ] 分类分级的结论由谁签字？（不能由项目组自己定）

### 2.2 个人信息处理

**触发评估的典型情形**（需与法务确认，不同行业口径不同）：

| 情形 | 需要考虑 |
|---|---|
| 本体对象包含自然人（客户、员工、供应商联系人） | 处理目的、最小必要、告知同意的既有范围是否覆盖新用途 |
| 自动化决策直接影响个人（授信、定价、录用、考核） | **自动化决策的特别要求**：告知、说明、拒绝纯自动化决策的权利 |
| 个人信息进入模型上下文 | 是否构成「提供」；模型是否第三方；是否留存 |
| 证据链记录了个人信息 | 留存期限、访问权限（见 [模块四 4.4](../10-方法论总结/04-模块四-行动闭环与企业采纳.md)） |

**〔判断〕** 最容易被忽略的是**「自动化决策」这个概念本身**。本方法论的 L3/L4 就是自动化决策；一旦决策对象是自然人，法律义务与 L0/L1 完全不同。**这应当直接进入 [决策卡](04-模板库.md) 的一个新字段。**

### 2.3 模型部署形态与数据流出

模型部署形态决定了数据流向，进而决定合规路径：

| 形态 | 数据流向 | 主要考虑 |
|---|---|---|
| **私有化部署** | 不出企业网络 | 合规路径最短；成本与能力是主要约束 |
| **境内公有云 API** | 出企业、不出境 | 属于「委托处理」，需数据处理协议、留存与训练条款 |
| **境外 API** | **出境** | 触发数据出境的合规路径。**这是最需要早问的一条**——若结论是不可出境，模型选型与架构会整体改变 |
| **混合**（敏感数据本地小模型 + 非敏感走 API） | 分流 | 复杂度最高；**分流规则必须由本体的敏感度标记驱动**，不能靠提示词约定 |

**必须在阶段一回答**：

- [ ] 拟采用哪种形态？备选是什么？
- [ ] 若结论是「不可出境」，当前技术方案是否仍成立？
- [ ] 模型服务商的**留存与用于训练**条款是什么？合同层面是否已排除？
- [ ] 行业是否有额外要求（金融、医疗、汽车、政务等各有专门规定）？

### 2.4 审计与留存：证据链是加分项

**〔判断〕** 等保与多数行业监管对操作日志、审计留存有明确要求，而**本方法论的证据链设计本来就覆盖了其中大部分**：谁在什么时候基于什么做了什么、是否被审批、是否被推翻。

这不是负担，是**协同**。方案里应当把两者合并陈述：

> 「审计留存不是额外建设，它与决策证据链是同一套设施。」

但要注意两个方向的冲突：

| 冲突 | 处理 |
|---|---|
| 监管要求留存**下限**（如若干年）vs 个人信息要求**上限**（最短必要期限） | 分层留存：结构化决策记录长留存，含个人信息的原文短留存后脱敏 |
| 证据链要求**不可篡改** vs 个人信息的**删除权** | 用「标记删除 + 保留哈希」而不是物理删除，需与法务确认可接受性 |

## 三、安全清单：对抗性输入

> 完整的威胁模型与设计规则见 [模块三 3.6](../10-方法论总结/03-模块三-Agentic系统设计与编排.md)。本节是落地检查表。

### 3.1 为什么权限模型不够

**这一点必须在安全评审中主动讲，而不是等对方问出来。**

本方法论的权限模型能挡住**越权**，挡不住**权限内的被操纵行动**：一个供应商在订单备注里写一句话，被 Agent 读进上下文，可能触发一次完全在权限内、参数完全在范围内、审计完整的错误行动。

**主动承认这一点，然后给出第四类防线（输入可信度），比被问住可信得多。**

### 3.2 落地检查表

- [ ] **不可信来源已枚举**：哪些工具的返回可能包含外部方提供的自由文本？（客户留言、供应商备注、邮件正文、上传文档、网页内容）
- [ ] **不可信内容被标记**：从进入上下文的那一刻起带标记，直到输出
- [ ] **行动参数不由不可信内容决定**：参数必须来自结构化事实或用户直接指令
- [ ] **高风险行动做独立复算**：校验「这个参数能否由本体事实独立推导」——不能则拒绝
- [ ] **先定计划再读内容**：在摄入不可信内容前固定控制流
- [ ] **读到外部文本的那一轮自动降级**：L3 → L2
- [ ] **注入用例进评测集**：通过判据是「拒绝」而不是「答对」
- [ ] **第三方工具/MCP server/技能包已按外部依赖审查**：来源、版本锁定、变更通知、可撤销、最小权限
- [ ] **第三方工具未直接绑定 R2/R3 行动**
- [ ] **成本型拒绝服务已防护**：迭代上限、成本上限、熔断（见 [运行约束](../15-DIA框架详解/06-运行约束.md)）

### 3.3 与既有安全体系的接口

**〔判断〕** 不要新建一套安全体系。应当接进企业已有的：

| 已有能力 | 接法 |
|---|---|
| 身份与权限（IAM） | Agent 用委托身份，见 [模块四 4.4b](../10-方法论总结/04-模块四-行动闭环与企业采纳.md) |
| 数据分类分级 | 映射到本体属性敏感度（2.1） |
| 日志与审计 | 与证据链合并（2.4） |
| 变更管理 | 提示词与本体定义纳入同一发布流程 |
| 红蓝对抗 | 把注入用例加进现有红队范围，而不是单独立项 |

## 四、需要合规签字的四件事

**〔判断〕** 项目组自己不能决定、必须拿到书面结论的四件事。缺任何一件都不应进入阶段三：

1. **数据分类分级结论**——哪些属性是敏感的、哪些是个人信息、哪些是重要数据
2. **模型部署形态与数据流向的合规结论**——尤其是否可出境
3. **自动化决策的适用范围**——哪些决策对象是自然人、是否触发特别义务
4. **证据链的留存与访问规则**——存多久、谁能看、如何脱敏

---

## 五、诚实的边界

**〔判断〕** 本页不能替代的：

- **不能替代法务判断。**监管口径随行业与地区变化，且在演进中。
- **不能保证通过评审。**它只保证你不会因为「没想到要问」而在最后一刻返工。
- **不覆盖多 Agent 场景的安全。**[模块五 5.3](../10-方法论总结/05-模块五-整合视图与展望.md) 承认多 Agent 审计是未解问题，其安全模型同样未解。
- **不覆盖模型本身的安全属性**（越狱、有害输出、幻觉率），那是模型选型的议题。

**这一页的存在价值是：把「合规是上线前的一道关」变成「合规是架构设计的一个输入」。**
