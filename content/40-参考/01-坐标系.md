# 坐标系：与 Palantir 及其他范式的关系

> 明确「借鉴什么、不照搬什么」，以及本方法论在现有范式版图中的位置。

---

## 一、Palantir：借鉴内核，不照搬形态

### 值得借鉴的思想内核（一句话）

> **用本体把「数据」和「决策行动」缝合起来，让企业拥有一个可运行的数字孪生，而不是一个更大的数据仓库。**

> ⚠️ **2026-08-23 更正。**本站此前在此写「Palantir 官方的本体表述是三层：Semantic / Kinetic / **Dynamic（绑定到对象上的模型）**」。
> **官方没有 Dynamic 层。**该三层说法出自第三方博客转述，本站未经核实即采用，并据此给该转述来源的「概念准确性」打了高分——错误因此被双重放大。详见 [引用与数据来源 `P1`](04-引用与数据来源.md) 与 [参考站调研的更正说明](03-参考站调研-RebootingWithAI.md)。

**官方表述是两分法：**

| 元素 | 内容 |
|---|---|
| **Semantic elements**（语义 / 名词） | objects、properties、links |
| **Kinetic elements**（动能 / 动词） | actions、functions、**dynamic security** |

其中 **"dynamic" 指 dynamic security**——运行时计算的细粒度权限策略，是 kinetic 的**子项**，讲的是**权限，不是模型**。

名词—动词的比喻确实是官方自己的说法（`P2`：'Data elements are the nouns… actions are the verbs'），「组织的数字孪生」也是（`P3`）。**要害抓得准：名词 + 动词 + 权限，构成一个闭环，而不是一条单向管线。**

### 真正的洞察，其实是一句反直觉的话

大多数人以为 Palantir 卖的是数据整合能力。实际上它卖的是：

> **让「分析」和「操作」发生在同一个语义空间里。**

传统架构里，分析在数据仓库，操作在业务系统，中间隔着人。Palantir 的价值是把这堵墙拆掉——你在看板上看到的那个订单，就是你能直接操作的那个订单，权限、审计、回滚一并跟着。

**这才是要借鉴的东西**，而不是它的产品功能列表。

### 不应照搬的部分

| 不照搬 | 原因 |
|---|---|
| **重度专业服务模式** | Palantir 的落地依赖大量前置工程师驻场。多数企业和多数服务商都没有这个成本结构 |
| **全平台锁定** | 一次性替换全套数据基础设施，中国大多数企业不接受，也不必要 |
| **全企业本体优先** | 本方法论主张从决策倒推、增量生长（见 [本体层](../15-DIA框架详解/04-O-本体层.md)） |
| **高昂的起步成本** | 应当有一个 90 天、单场景、可验证的起步路径 |
| **技术叙事** | Palantir 的公开叙事偏技术与愿景；中国的 CIO 更需要责任边界、失败代价与组织承接的答案 |

> ⚠️ **另一处更正**：本站此前写「幂等、参数边界、可逆性、审批链、权限传播、时点正确性……这些**公开材料里基本没有**」。**这是错的，且是明显的稻草人化**——Palantir 文档逐条覆盖（`P4`）：Action rules / submission criteria、Undo or revert Actions、**Ontology proposals（官方明确类比 Pull Request 的评审与批准流程）**、markings 沿管线传播、幂等与并发冲突失败语义、time-series 与 edits history、本体分支与版本。
>
> **站得住的说法是**：Palantir 把这些作为 **Foundry 的产品特性**文档化，而不是作为一套**可迁移到任意技术栈的工程方法论**；对不采用 Foundry 的企业，那些文档的可移植价值有限。本方法论试图提供的是后者。

### 本方法论相对 semantic-kinetic-dynamic 的补充

Palantir 的三层框架描述了**本体是什么**，但没有回答**在企业里怎么让它真的跑起来**。本方法论补上的是：

| 补充 | 说明 |
|---|---|
| **对象准入五判据** | 防止本体膨胀——最常见的失败模式 |
| **业务 Owner 制度** | 本体是产品，要有人负责 |
| **行动十一要素契约** | 让 kinetic 层能真正上生产（幂等、参数边界、频次上限、数据依赖、失败语义） |
| **可逆性分级 + 人闸** | 让「敢不敢开权限」这个真问题有答案 |
| **分级自治 L0–L4** | 让 dynamic 层的放权有依据 |
| **四条横切约束** | 权限传播（含无人值守身份）、证据链、失败关闭、运行 |
| **组织承接** | 人机权责矩阵 + 被取消的旧动作 |

一句话：**Palantir 提供的是一个产品里的实现；本方法论试图提供的是一套不绑定产品的工程纪律。**

> 这个定位比此前的「它回答是什么、我回答怎么做」诚实——因为「怎么做」它其实也写了，只是写成了产品文档。

## 二、与其他范式的关系

### Data Mesh（数据网格）
- **完整主张**（`M1`，四条原则，本站此前只提了第二条）：**领域自治的数据所有权、数据即产品、自服务数据基础设施平台、联邦式计算化治理**
- **关系**：**互补**。它解决「谁负责数据」的组织问题，本方法论的事实层可直接采用其数据产品与合同思想；第四条原则更是**本方法论集团型企业口径治理的直接借鉴来源**（见 [模块二 2.5](../10-方法论总结/02-模块二-语义与本体.md)）
- **准确的差异**（`M2`）：**Data Mesh 自动化的是治理，不是决策。**
  > ⚠️ 本站此前写它「终点是把可信数据交给人」——**这是稻草人化**。第四条原则「联邦式计算化治理」讲的正是把治理策略计算化地固化进平台，用自动流程替代人工干预。
- **时间**（`D7`）：首篇 2019-05，四原则 2020-12。**Dehghani 本人把 Data Mesh 定位为对「第三代数据平台」的回应，不是第三代本身**——本站借用「代际」框架时与原作者用法冲突，已在 [模块一 1.2](../10-方法论总结/01-模块一-基础认知.md) 标注
- **现状**（`M3`）：2025–26 年业界分裂为「已死」与「理念对、落地失败」两派，主要批评是跨域 schema/质量不一致、基础设施重复、组织变革前置条件过重

### Lakehouse / 数据湖仓
- **关系**：**底座**。它是事实层的一种实现选择
- **警告**：Lakehouse 解决存储与计算，**不解决语义**。把它当成终点，就是 [数据湖谬误](../00-立场/02-为什么企业AI停在PoC.md)

### Semantic Layer / 指标平台（如 dbt Semantic Layer、Cube）
- **关系**：**本体层的一个子集**
- **差异**：指标平台管的是「指标口径唯一」，本体还要管对象、关系、状态机、**行动**与权限。**没有行动的语义层，是 BI 的延伸，不是决策平台**

### Knowledge Graph（知识图谱）
- **关系**：**技术手段之一**，可作为本体关系层的实现
- **差异**：知识图谱通常面向检索与推理，只读；本体必须可执行、绑定行动、承载权限

### MDM（主数据管理）
- **关系**：**前置能力**。标识映射与主数据治理是本体的必要基础
- **差异**：MDM 关注「唯一准确的主数据」，本体关注「可用于决策与行动的业务语义」。**MDM 是名词的正确性，本体是名词 + 动词 + 权限的完整性**

### RPA / 流程自动化
- **关系**：**行动层的一种实现手段**
- **差异**：RPA 自动化的是**已确定的流程**，本方法论自动化的是**决策本身**。RPA 不问「该不该做」，只问「怎么做」

### AI Agent 框架（LangGraph 等）
- **关系**：**智能层的实现工具**
- **警告**：框架解决编排，不解决企业问题。**Agent 的能力边界应由本体决定，而不是由框架能力决定**

### MCP / 工具互操作协议
- **关系**：**「工具即本体行动」这一主张的现成落地协议**
- 已于 2025-12-09 捐给 Linux Foundation 下的 Agentic AI Foundation（`A15`），Anthropic、OpenAI、Block 共同发起
- **本方法论应当明确引用它而不是回避**：把本体的查询与行动暴露为 MCP server，接入成本从 N×M 降到 N+M；网关级鉴权在这一层有位置
- **注意**：第三方 MCP server 是新的攻击面与供应链依赖，见 [模块三 3.6](../10-方法论总结/03-模块三-Agentic系统设计与编排.md)

### 竞争版图（2026 现状）
**〔判断〕** 本站此前只做范式对照、不做产品对照，导致无法回答 CIO 的「市面上谁在做同样的事」。需要知道的是：**语义/本体层的 Agent 接口已经是各大平台在卖的东西**——Snowflake、Databricks、Microsoft Fabric（含 Fabric IQ 的本体 + 图引擎 + MCP 暴露）、Google 都有对应产品。
把它们定位为「本体层的商业实现」而不是「BI 的延伸」，是与 CIO 对话时必须先做对的一件事。自建 vs 采购的拆解见 [自建 vs 采购](../20-实践/09-自建vs采购与退出剧本.md)。

## 三、定位图

```
                    高｜决策与行动闭环
                      │
                      │   ┌──────────────────┐
                      │   │  Palantir Foundry │
                      │   │  决策智能架构 DIA  │
                      │   └──────────────────┘
                      │
                      │        ┌─────────┐
                      │        │   RPA   │  （只有动作，没有决策语义）
                      │        └─────────┘
       ───────────────┼────────────────────────────────▶
                      │  ┌──────────┐   ┌───────────┐   语义完整度  高
                      │  │  BI/报表  │   │ 语义层/指标 │
                      │  └──────────┘   └───────────┘
                      │
                      │  ┌──────────┐   ┌──────────┐
                    低│  │ 数据湖仓  │   │ 知识图谱  │
                      │  └──────────┘   └──────────┘
```

**右上角是唯一有持续价值的位置**：语义完整 + 能驱动行动。

其余象限的工具都是通往右上角的组成部分，但单独停在那里，都会遇到价值天花板。

## 四、一句话总结

> 数据湖解决「数据在哪」，语义层解决「数字是什么」，知识图谱解决「关系是什么」，RPA 解决「怎么执行」——
> **本体解决「这家企业是什么，以及能对它做什么」，而治理解决「凭什么敢让它做」。**
>
> 前四个是工具，后两个才是架构。

> ⚠️ **一句必须补上的话**：说它们「是工具」不等于说它们没有持续价值。大量企业从 BI 与数仓获得的是长期、稳定、可观的回报（`D12`：2026 年云数仓仍占主环境 44%）。**它们的价值上限低于右上角，但不等于应该被替换。**既有投资如何直接复用见 [自建 vs 采购与共存](../20-实践/09-自建vs采购与退出剧本.md)。
