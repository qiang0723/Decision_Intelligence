## 4.1 从只读到写回：行动契约 {#41}

### 为什么行动是一等公民

**〔判断〕** 在传统数据架构里，「写回」是一个边缘功能。在决策智能架构里，行动必须与对象、属性同等重要。

理由是价值上限：一个只能回答问题的系统，它创造的价值都要经过一次人工转译才能落地——人看到结论、人理解、人打开另一个系统、人操作。这条链路每一环都在衰减，且吞吐量受限于人的注意力。

**〔共识〕** Palantir 的 kinetic 层、各类 Agent 平台的 action/tool 概念，都指向同一件事。分歧不在于「要不要行动」，而在于**行动要定义到什么程度才能上生产**。

### 行动契约：十一个必备要素

**〔判断〕** 这是我认为公开材料里最缺的一块。一个行动在进入生产前必须完整定义：

| # | 要素 | 说明 |
|---|---|---|
| 1 | **前置条件** | 用状态机表达，如「订单状态 ∈ {待发货}」 |
| 2 | **参数模式** | 结构、类型、**取值范围——范围就是安全边界** |
| 3 | **权限** | 谁可执行；Agent 执行时继承谁的权限 |
| 4 | **副作用** | 改变哪些对象状态，触发哪些下游 |
| 5 | **幂等键** | 重复执行不产生重复效果。**必填项，不是优化项** |
| 6 | **可逆性** | R1 / R2 / R3，见 4.2 |
| 7 | **审批链** | 什么条件免批，什么条件强制人工 |
| 8 | **审计记录** | 触发者、参数、依据、口径与模型版本、审批人、结果 |
| 9 | **失败语义** | 失败后状态、是否重试、何时需人工 |

**〔判断〕** 缺任何一项都不应上线。实践中最常被跳过的是 5（幂等键）和 2 的范围部分——而这两项恰好是事故率最高的两项。参数无边界的典型后果：一个小数点错误导致调价 100 倍。

### 写回原则：不要制造第二套真相

**〔判断〕** 行动必须写回**权威系统**（ERP、OMS、WMS、CRM），而不是只写在平台内部。

如果平台自己存了一份「我们认为的库存」，而 ERP 里是另一份，企业就有了两套真相。这比没有 AI 更糟：对账量增加、出问题无法定位哪套对、业务方会自然相信旧系统。

判据：

> **关掉这个平台，企业的业务数据是否完全不受影响？**
> 是 → 写回设计正确（平台是决策者与执行者，不是记录者）
> 否 → 制造了第二套真相，必须重构

**例外**：平台可以保留**决策记录与证据链**——这是平台独有的资产，不与业务系统冲突。

## 4.2 可逆性分级与人在回路 {#42}

**〔判断〕** 这是整个授权体系的核心依据，也是公开材料里几乎完全缺失的一环。社区谈 "human-in-the-loop" 时，通常停留在「要不要加个确认按钮」，而没有回答**在什么条件下可以不加**。

### 三级分类

| 级别 | 定义 | 例子 | 授权取向 |
|---|---|---|---|
| **R1 可撤销** | 一键回到原状态，无外部影响 | 修改内部标签、调整优先级、更新预测 | 可较早开放自动 |
| **R2 可补偿** | 不能直接撤销，但有明确反向操作 | 调价、创建工单、库存调拨 | 限额内自动，超限审批 |
| **R3 不可逆** | 一旦执行，外部世界已改变 | 已发货、已付款、已发客户通知、已监管报送 | **永远需要人** |

### R3 是否永远需要人闸：一处重要更正

**〔争议〕** 本站此前写「**R3 不可逆行动永远需要人闸**，无论评测指标多好都不能开放为全自动」，并列为不可协商。

**这作为对现实的描述是错的，作为规范也不是领域共识。**反方立场必须列出：

> **产业界大量不可逆行动今天就在全自动执行**：程序化广告投放（预算花出去不可撤回）、算法交易、自动放款与自动扣款、自动发送的营销短信与推送、自动化物流下单与承运商调度、SaaS 自动扣费与续订。
> 这些系统的通行做法不是人闸，而是**限额 + 速率限制 + 异常熔断 + 事后补偿 + 保险**。

而且本站自己在 [电商剖面](../30-行业剖面/01-电商.md) 已经写了「是否退款：**小额自动，大额人闸**」——这本来就是一个例外，此前没有承认它是例外。

**〔判断〕** 修正后的规则是**有条件的**，而且比原来更有力——因为它说清了真正要守的东西不是「必须有人点确认」，而是**必须有可承担的损失上界**：

> **R3 行动开放自动执行，需要同时满足四条：**
> 1. **单次影响有硬上限**（金额、数量、影响对象数）
> 2. **单位时间总量有硬上限**（对应行动契约第 10 要素）
> 3. **有可执行的事后补偿路径**（不是理论上可补偿，是补偿动作已实现并演练过）
> 4. **有实时异常熔断**，以及**一个具名担责人**
>
> **四者缺一，即保留人闸。**

### 最实用的落地模式：把 R3 拆成 R2 + R3

**〔判断〕** 这是我认为企业 AI 落地最有用的一个具体技巧：

```
「自动发货」        = R3，不能自动
拆解后：
「自动创建发货单」   = R2（可作废，未下发前无外部影响）  → 可以自动
「确认发货」        = R3（不可逆）                      → 保留人闸，一键确认
```

AI 承担 95% 的工作量，人只保留最后那个不可逆的确认动作。

**这个模式几乎适用于所有 R3 场景**：自动生成退款单 + 人工确认；自动起草客户通知 + 人工发送；自动准备付款指令 + 人工放行。

### 人在回路的三种形态

**〔共识〕**

| 形态 | 人的位置 | 适用 |
|---|---|---|
| **Human-in-the-loop** | 执行前必须人批 | R3、高代价 |
| **Human-on-the-loop** | 人监督，可随时干预与叫停 | R2 限额自动 |
| **Human-in-command** | 人只做定期审计与规则调整 | R1 稳定运行后 |

**〔判断〕** 这三种形态与 4.3 的自治级别一一对应。选哪一种，由可逆性决定，而不是由模型准确率决定。

## 4.3 分级自治 L0–L4 {#43}

**〔判断〕** 「自主」不是能力描述，是**授权描述**。这个区分是本节的全部要点。

社区里常见的「Agent 自主性等级」讨论，多数从**模型能力**出发（能不能自己规划、能不能自己纠错）。企业需要的分级必须从**授权与责任**出发。

### 五级

| 级别 | 名称 | 系统做什么 | 人做什么 | 典型准入条件 |
|---|---|---|---|---|
| **L0** | 观察 | 只输出分析与解释 | 全部决策与执行 | 上线即可 |
| **L1** | 建议 | 给出推荐动作与理由 | 决策 + 执行 | 离线评测达标 |
| **L2** | 草拟 | 生成参数已填好的动作草稿 | 审批 + 一键执行 | 影子运行期通过 |
| **L3** | 限额自动 | 阈值内自动执行，超限升级 | 例外处理 + 抽检 | 连续 N 期在线指标达标 |
| **L4** | 全自动 | 全量自动执行 | 监控 + 定期审计 | 长期稳定，且仅限 R1/R2 |

### 四条硬规则

**〔判断〕**

1. **R3 行动开放到 L3/L4 需满足 4.2 的四条件；四者缺一则最高只能到 L2。**（此前本站写「R3 最高只能到 L2」，已按 4.2 更正）
2. **晋级条件必须事前冻结**，不能看到结果后临时议定。
3. **降级条件自动生效，不需要审批。**
4. **每次晋级/降级都是一条审计记录。**

> **晋级靠证据，不靠信心。**
> 「我们觉得它已经挺准了」不是晋级理由。晋级条件应当在上线之前就写进决策卡。

### 一条重要修正：L2 不是稳定状态

**〔判断〕** 本站此前把 L2（草拟 + 人工确认）当作一个可以长期停留的稳定状态。`A10` 的纵向研究否定了这个假设：

> 对 Agent 输出的**批准率随时间上升，而审查深度下降**。
> 经验规则：**批准率 ≥95% 时，这个检查点已经是「确认剧场」**，实际保护力接近零。

修正后的取向：

- **L2 是过渡态，不是终点。**长期停留在 L2 的场景，人工确认会退化为形式
- **必须监控批准率**，与「人工推翻率」并列进入可观测指标
- 批准率过高时，正确的动作是**要么晋级到 L3 + 抽检，要么承认这个检查点无效并重新设计**——而不是维持一个形式上的确认按钮

详见 [模块三 3.6](03-模块三-Agentic系统设计与编排.md)。

### 为什么必须从 L1 起步

**〔判断〕** 常见的反驳是「我们很有信心，直接上 L3 吧」。三个理由不行：

- **证据不足**：离线评测集覆盖不了真实分布，影子运行期是唯一能发现分布外行为的阶段
- **信任建立**：业务方需要一段时间观察系统与自己判断的差异，跳过这段，第一次出错就是终点
- **组织准备**：L3 需要「例外处理」流程与责任人，这些在 L1/L2 期间才能磨合出来

## 4.4 四条治理约束：权限 · 证据 · 可逆 · 运行 {#44}

**〔判断〕** 这几条不属于某一层，而是整套架构的设计前提。

> **2026-08-23 更新**：此前是「三条约束 + 六层（含 R 运行层）」。外部审查指出 R 运行层的内容（环境隔离、成本熔断、发布回滚、可观测）**作用于所有层，与「事实层之下」这个位置没有任何关系**，把它画成最底层只是因为分层图需要一个底；而且它包含的「权限落到运行时」与约束一重复。
> **现改为五层 + 四条横切约束**，运行成为第四条约束。记忆锚点相应改为「**一个中心，两个方向，四条约束**」。详见 [模块五 5.1](05-模块五-整合视图与展望.md)。

### 约束一｜权限 Authority

**原则**：权限定义在本体上；**Agent 继承调用者权限，不存在超级 AI 身份**。

- 四个维度：对象级、行级、属性级、行动级
- 身份上下文必须贯穿：用户 → Agent → 工具 → 数据 → 行动。**中间任何一处退化成服务账号，模型即破**
- 越权返回**明确拒绝**，不是空结果

**〔判断〕** 隐蔽风险：销售 A 问「我们最大的客户是谁」，如果 Agent 用超级权限回答了，就等于绕过了原有权限体系。**这类泄漏不会触发任何传统安全告警。**

### 约束二｜证据 Evidence

**原则**：任何结论可追溯到输入与版本；**失败与拒绝同样留痕**。

一条完整证据链：

```
决策/结论
  ├── 触发：谁、什么时候、通过什么入口
  ├── 输入：哪些对象与指标，取值与时间点
  ├── 口径：指标权威实现版本、本体版本
  ├── 推理：规则 / 模型 / 提示词版本
  ├── 输出：建议或已执行的行动、参数
  ├── 人的介入：谁审批、是否被推翻、推翻理由
  └── 结果：执行成功/失败、后续影响
```

**〔判断〕** 「坏消息不可隐藏」是这条约束下最容易被违反的一点：拒绝、弃权、失败、人工推翻全部要留痕。**人推翻系统建议的理由，是最有价值的改进信号。**

> 界面可以降噪，但不能删除或改写权威状态。
> 做一个只展示成功案例的看板，等于主动放弃了系统改进的唯一信息来源。

#### 证据链本身也需要被治理

**〔判断〕** 这是本站此前的一个盲点：证据链是全架构中**唯一允许平台自己长期存储的数据**，而它必然包含用户提问、数据取值、决策依据、被推翻的理由——**这是一个新创建的高敏感数据存储**。方法论创造了一个新风险，就必须治理它：

| 项 | 要求 |
|---|---|
| **留存期限** | 明确保存多久、到期如何处理。等保与行业监管对日志留存有**下限**要求，个人信息保护对**上限**有要求，两者要同时满足 |
| **访问权限** | 证据链的读取权限**不等于**业务数据的读取权限。谁能看别人的决策记录，必须单独定义 |
| **个人信息** | 提问内容与决策依据里可能含个人信息，需纳入数据分类分级 |
| **不可篡改** | 证据链自身必须是追加式的，且修改证据链的操作本身要留痕 |

**这同时是一个卖点而非负担**：等保对审计留存的要求与证据链设计高度重合——**证据链本来就能满足大部分审计要求**。合规评审时应当主动拿出来讲。见 [合规与安全前置](../20-实践/07-合规与安全前置.md)。

### 约束三｜可逆 Reversibility

**原则**：默认可撤销；不可逆行动永远需要人。

运行时体现为**失败关闭（Fail-Closed）**：

| 情形 | 正确行为 | 错误行为 |
|---|---|---|
| 数据缺失 | 返回 `NOT_READY` + 缺什么 | 用 0 或前值填充后继续 |
| 口径不明 | 返回 `NOT_EVALUATED` | 按最可能的口径猜一个 |
| 权限不足 | 返回 `DENIED` | 返回空结果 |
| 置信度低 | 弃权，转人工 | 输出最佳猜测 |
| 断言失败 | 阻断下游 | 告警但继续出结论 |

**〔判断〕**

> **降级成「看起来成功」是最危险的失败模式。**
> 一个明确的错误会被立刻发现和修复；一个看起来正常的错误会持续污染决策数月。

### 约束四｜运行 Runtime

**原则**：**能力必须能被停下来、退回去、算清楚。**

这一条此前是「R 运行层」，现升格为横切约束（理由见本节开头）。内容见 4.5 与 [运行约束](../15-DIA框架详解/06-运行约束.md)：环境隔离、配额与熔断、发布与回滚、可观测性。

**〔判断〕** 把它作为约束而不是层，有一个实际后果：**任何一层的设计评审都必须回答「这一层出问题时怎么停、怎么退、成本怎么算」**，而不是把这些问题推给「底层去解决」。


```
权限  ──决定──▶  能做什么
  ↓
可逆  ──决定──▶  能自动做到什么程度
  ↓
证据  ──决定──▶  能不能被采信、能不能改进
  ↓
运行  ──决定──▶  出事时能不能停下来、退回去、算清楚
```

**〔判断〕** 四者共同构成企业 AI 的**信任基础设施**。技术能力决定上限，这四条决定能不能开始。

**〔争议〕** 需要承认的是：这四条约束的**完整实施成本很高**，而产业界大量成功的自动化系统（广告投放、风控、推荐）并没有全部做到——它们用限额、熔断与事后补偿替代了其中几条。本方法论的立场是「在可写回企业权威系统的场景下四条都需要」，但这是我的判断，不是共识。

## 4.4b 无人值守时的身份 {#44b}

> **本节是补漏，2026-08-23 新增。**

### 漏洞是什么

**〔判断〕** 本站在六个文件里反复陈述：

> 「Agent 继承调用者权限，不存在超级 AI 身份」「中间任何一处退化成服务账号，模型即破」

同时 L3（限额自动）与 L4（全自动）的定义是系统**自动执行**——定时触发或事件触发。

**在无人值守的自动执行里，没有「调用者」。**那么此时 Agent 用谁的身份？

本站此前**没有任何一处回答这个问题**。而这恰恰是企业安全评审第一个会问的，也是「超级 AI 账号」在现实中真正诞生的地方——绝大多数团队会在这里悄悄配一个服务账号，按本站自己的说法就是「模型即破」。

### 规则

**〔判断〕** 采用**岗位委托身份**，它与「担责者永远是人」天然衔接：

> **自动执行以「担责岗位」的身份运行。**
> 该身份的权限**恰好等于**该岗位的人工权限，不多一分；
> 该岗位的具体担责人对每一次自动执行**事后可见、可撤回**；
> 岗位空缺或担责人离职时，该自动执行**自动降级为 L2**，直到指定新的担责人。

**配套的两条硬约束**：

| # | 约束 |
|---|---|
| 1 | **权限下界原则**：当一个自动执行服务于多个岗位时，其权限必须是这些岗位权限的**交集**，不是并集 |
| 2 | **绝对禁止**：不得使用任何权限**大于**其担责人的自动执行身份。这条没有例外——一旦允许，「不存在超级 AI 身份」就失效了 |

### 落到契约

行动契约第 3 要素（权限）此前只写「Agent 执行时继承：`<调用者身份>`」，在 L3/L4 下这个字段填不出来。现补为：

```
权限
  人工触发时：继承调用者身份
  自动执行时：以担责岗位 <岗位名> 的委托身份运行
             担责人：<具体的人>
             权限来源：该岗位人工权限的 [全集 / 与 XX 岗位的交集]
             岗位空缺时的行为：降级至 L2
```

见 [模板库](../20-实践/04-模板库.md)。

**〔争议〕** 业界正在成型的另一条路径是标准化的 Agent 身份委派（A2A、OAuth Cross-App Access 一类）。它与本节的规则不冲突——那是**实现机制**，本节定的是**权限边界**。但如果这类标准成熟，应当优先采用标准而不是自建。

## 4.5 运行层：隔离 · 成本 · 发布回滚 {#45}

**〔判断〕** 最不性感，但它是 PoC 与生产之间那道断崖的主体。

### 环境隔离

| 环境 | 数据 | 允许的行动 |
|---|---|---|
| 研究/沙箱 | 脱敏或只读副本 | **只读，零写回**（凭据级隔离，不靠自觉） |
| 预生产 | 生产数据只读 | 影子行动：记录不执行 |
| 生产 | 生产数据 | 完整行动，受权限与自治级别约束；**只运行受控发布的不可变版本** |

### 成本必须能熔断

**〔共识〕** 生成式系统的边际成本不可忽略，且可在无人察觉时指数增长。

四件事必须强制：预算、配额、**熔断**、成本归因。

**〔判断〕**
> **熔断必须是「停」，不是「提醒」。**
> 一个只发告警不停止的成本保护，在夜间和周末等于不存在。

### 发布与回滚

**〔判断〕** 代码、配置、提示词、模型、本体定义、评测集全部版本化，一次发布对应一组确定的版本组合。

> **回滚不需要审批；需要审批的是发布。**

特别提醒：**提示词与本体定义的变更，与代码变更享受同等待遇**。它们同样改变系统行为，却经常被当成「配置微调」绕过流程——这是生成式系统最常见的事故来源。

### 可观测性

三类信号缺一不可：技术指标（时延、错误率、成本）、质量指标（准确率、弃权率、抽检）、业务指标（该决策对应的业务成效）。

**〔判断〕** **人工推翻率是最诚实的指标**，通常比技术指标更早报警。

## 4.6 组织承接：人机权责与减法 {#46}

**〔判断〕** 这是公开材料里最被忽略、而失败率贡献最大的一环。

### 人机权责矩阵

对每个决策，明确四个角色：

| 角色 | 定义 | 可以是 AI 吗 |
|---|---|---|
| 建议者 | 提出方案 | ✅ 通常从这里开始 |
| 决定者 | 拍板 | 取决于自治级别 |
| 执行者 | 实际操作系统 | ✅ 通过行动层 |
| **担责者** | 出问题时负责 | **❌ 永远是人** |

**〔判断〕** 不可协商：

> 任何一个「AI 自动执行」的场景，都必须能指出一个具体的人对结果负责。
> **找不到这个人，就不要上自动执行。**

### 交付时必须回答的问题

> **哪一个旧动作因此被取消了？**

**〔判断〕** 如果答案是「没有，只是多了一个参考」，那么这个场景在组织意义上没有落地，它会在三个月内消亡。

新增一个动作而不取消任何动作，是净增加负担。

> **落地的标志是减法。**

### 决策界面的形态优先级

**〔争议〕** 按优先级（**这个排序在 2026 年是有争论的**：对话式 + 结构化确认的混合界面正在成为主流形态之一，纯按钮式界面在需要解释的场景上不够）：

1. **嵌入现有工作流**（最优）：ERP 待办、飞书/企微卡片、工单系统推荐
2. **推送到人所在的地方**：告警、日报、审批流
3. **独立控制台**（次选）：仅当需要复杂上下文探索
4. **对话式界面**（谨慎）：适合探索性分析，**不适合日常高频决策**

> 常见错误：把所有场景都做成 Chat。
> **对话是探索的界面，不是执行的界面。**
> 一个高频重复的决策，界面应该是一个按钮和一行理由，不是一个输入框。

### 变更管理：判据之外还需要方法

**〔判断〕** 本站此前在这里只有两个交付物（人机权责矩阵、被取消的旧动作）。它们是好判据，**但判据不是方法**。以下是四个真实会发生、而本站此前没有工具应对的情形：

| 情形 | 可用的处理 |
|---|---|
| **被取消动作的岗位抵触** | 先取消**信息搜集类**动作而不是判断类动作——前者是负担，后者是身份。让这个岗位成为系统的**审核者与例外处理者**，职责升级而不是缩小。在人机权责矩阵里把他写成担责者，是最直接的安抚 |
| **Owner 拒绝当 Owner** | 这通常不是懒，是**责任与权力不匹配**——他要为口径负责，却无权否决别的部门的用法。解法是把「裁决权」与「Owner」一起给出去；给不出裁决权，就不要设这个 Owner，改用 [模块二 2.5](02-模块二-语义与本体.md) 的分层指标模式 |
| **sponsor 换人** | 这是本方法论**覆盖不到**的失败原因之一（见 [模块一 1.3](01-模块一-基础认知.md)）。唯一的对冲是**在 sponsor 任期内产出可独立成立的资产**：决策清单、本体与数据合同即使项目停摆也仍然有用，把它们做成交付物而不是中间产物 |
| **过渡期的激励错配** | 影子运行期人要同时做旧动作和看新建议，**工作量是增加的**。这段时间必须有明确的补偿或考核豁免，否则影子期数据会被敷衍地生成，评测结论随之失真 |

### 技能退化：人在回路的第二条衰减曲线

> **2026-08-24 新增。**本站此前的组织章节只覆盖了**抵触、责权不匹配、sponsor 变更、激励错配**四类短期问题，**完全没有覆盖长期的能力退化**。这一类风险由 [rebootingwithai.com](../40-参考/03-参考站调研-RebootingWithAI.md) 的「Risks of OverUsing Agentic Automation」提出（`H1`）。

**〔争议〕** 长期依赖 AI 完成判断类工作，会降低使用者的独立思考、记忆与问题解决能力（「认知债」）。该效应的强度、可逆性与适用边界仍在研究中，不同任务类型差异很大——**本站按〔判断〕使用它，不作为已确立的结论**。

#### 为什么它对本方法论特别重要

因为它和本站自己在 [4.3](#43) 得出的「**确认剧场**」是**同一现象的两个时间尺度**：

| | 确认剧场（`A10`） | 技能退化（`H1`） |
|---|---|---|
| 尺度 | 数周到数月 | 数年 |
| 衰减的是 | **注意力**——人还会看，但看得越来越浅 | **能力**——人已经判断不了 |
| 可观测性 | 批准率上升即可发现 | **批准率不变也可能已经发生** |
| 可逆性 | 换人、抽检、重设计即可恢复 | 恢复需要重新训练，成本高得多 |

**〔判断〕** 两者叠加的后果，比任何一个单独更严重：

> **L2「草拟 + 人工确认」有两条独立的衰减曲线。**
> 我们此前只说了第一条（注意力），据此得出「L2 是过渡态不是终点」。
> 加上第二条（能力）之后，这个结论更强：**一个长期停在 L2 的场景，最终会退化成一个没有人真正在把关、而且已经没有人有能力把关的自动执行系统**——但它在流程上、审计上看起来一切正常。

这也解释了一个常见现象：企业在系统出问题后想「先切回人工」，却发现切不回去。

#### 四条对策

**〔判断〕** 都是组织设计，不是技术手段：

| # | 对策 | 说明 |
|---|---|---|
| **1** | **例外处理必须由人做，且不要把例外也自动化** | **例外是保持技能的唯一训练场。**一旦连例外都交给系统，人就彻底失去了接触真实困难案例的机会。这条与「效率」直接冲突，必须明确取舍 |
| **2** | **保留一定比例的无辅助处理** | 定期（如每周若干单）由人在不看系统建议的情况下独立判断，再与系统结果比对。它同时是**技能维持**和**人类基线的持续测量**（见 [模板库](../20-实践/04-模板库.md) 评测集的人类基线字段） |
| **3** | **角色升级而不是缩小** | 把岗位从「执行者」变成「审核者 + 例外处理者 + 规则维护者」。这与 4.6 开头的抵触对策是同一件事——**它既是安抚，也是防退化** |
| **4** | **把「人还能不能接管」纳入定期演练** | 与灾备演练同类。演练结果应当是一个可报告的数字，而不是一个感觉 |

#### 它同时是一项被漏算的退出成本

**〔判断〕** [退出剧本](../20-实践/09-自建vs采购与退出剧本.md) 此前假设「叫停后回退到旧流程」是可行的。技能退化让这个假设不成立：

> 运行两年后叫停，**团队可能已经没有能力按旧方式做这件事了**。
> 这是一项真实的、此前完全没有计入的退出成本，而且它随时间单调上升。

对策 1–4 同时是在**保住退出选项**。这一点应当写进立项文件——它是「为什么不能把效率优化到极致」的正当理由。

---

**〔争议〕** 组织变革管理有成熟的通用方法论（Kotter、ADKAR 等），本节不试图替代它们。我的判断是：**企业 AI 的变更管理特殊性在于「被改变的是判断权而不是操作方式」**，这一点通用变更管理框架处理得不好。但这是我的判断，不是共识。

## 4.7 成熟度模型：M0–M2 + 覆盖率 {#47}

> **2026-08-23 更正。**本站此前用 M0–M4 五级。外部审查指出 **M3/M4 只是把 L2/L3 换了个名字重说一遍**：
> M3「系统草拟，人一键确认」= L2 的定义；M4「系统在限额内自动执行」= L3 的定义。
> 同时本站自己的规则三已经写了「有价值的是有多少决策进入了闭环，不是最高做到第几级」——**那就应该让模型本身长成这个样子**，而不是先给五级再叮嘱别追求级别。
> 现收敛为 **M0–M2 三级（描述组织与语义状态）+ 一个覆盖率指标**。

**〔判断〕** 一个自我定位的坐标，以及「下一步该做什么」的答案。

### 三级状态（描述组织与语义，不描述自动化程度）

| 级别 | 特征 | 决策如何发生 | 典型症状 |
|---|---|---|---|
| **M0** 手工 | 数据散在各系统与 Excel | 靠经验、开会、人工拉数 | 「这个数我要问一下财务」 |
| **M1** 可见 | 有 BI/看板，数据集中 | 人看报表后决定 | 「报表有了，但还是按经验做」 |
| **M2** 有语义 | 本体成型，口径唯一，有行动契约 | 人基于统一事实决定，且系统**能**写回 | 「终于不吵口径了」 |

### 覆盖率（描述自动化程度，取代原 M3/M4）

自动化程度直接用 **L 级的决策计数**表达，不再新造级别：

```
某域的成熟度报告 = M2 ＋ 「该域 12 个已识别决策中，5 个 ≥L2，2 个 ≥L3」
```

这样表述有三个好处：

1. **不重复**——不需要 M3/M4 去复述 L2/L3
2. **能表达混合状态**——原模型无法回答「一个域 M3 但只有一个场景在 L2 该怎么报告」，现在直接可表达
3. **与规则三一致**——它奖励的是「有多少决策进入闭环」，而不是「最高做到第几级」

### 三条使用规则

**〔判断〕**

1. **M2 是分水岭，不可跳过。**
   M0 → M1 是数据工程问题，钱能解决。**M1 → M2 是组织问题，钱解决不了**——M2 的实质是企业接受了「某个人对某个口径有裁决权」，这是权力的重新分配。跳过 M2 直接上 M3 的项目，会在上线三个月后陷入口径战争。

2. **级别按域算，不按企业算。**
   供应链 M3、营销 M1、财务 M2 完全正常。笼统说「我们公司是 M2」没有意义。

3. **不要为了升级而升级。**
   低频决策停在 L1/L2 完全合理；不满足 4.2 四条件的 R3 场景天花板本来就在 L2。**有价值的是覆盖率，不是最高级别。**

### 与本总结各模块的对应

| 成熟度跃迁 | 主要涉及模块 |
|---|---|
| M0 → M1 | 模块二 2.5–2.6（数据接入与可信） |
| **M1 → M2** | **模块二全部**（本体与语义） |
| M2 → M3 | 模块四 4.1–4.2 + 模块三（行动与智能） |
| M3 → M4 | 模块四 4.3、4.5（自治与运行） |
| 全程 | 模块四 4.4（四条治理约束） |

诊断工具与推进路线见 [实践](../20-实践/01-成熟度模型.md)。
