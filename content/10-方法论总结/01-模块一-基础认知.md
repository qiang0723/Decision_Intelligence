## 1.1 问题空间：企业 AI 到底卡在哪 {#11}

### 有证据支持的部分

**〔共识〕** 企业 AI 的规模化率极低，且失败原因高度集中在非模型环节。这一条现在可以用具体数字支撑：

| 数字 | 来源 |
|---|---|
| 88% 企业至少在一个职能用了 AI，但**仅 7% 完全规模化**；39% 报告有 EBIT 影响且多数 <5% | `E1` McKinsey 2025-11，n=1,993 |
| 仅约 **5%** 达到可产生变革性影响的成熟度；**60%** 报告收益甚微或没有 | `E2` BCG 2025-09，n>1,250 |
| **42%** 的公司放弃了多数 AI 计划（上年 17%）；平均**报废 46% 的 PoC** | `E3` S&P Global 2025-03，n>1,000 |
| 原型到生产平均 **8 个月**；仅 **48%** 的 AI 项目进入生产 | `E6` Gartner 2024-05 |
| 落地障碍分解：**与既有系统集成 46%、数据访问与质量 42%、变更管理 39%** | `E7` Anthropic + Material 2026 |
| 数据质量/就绪度 43%、技术成熟度不足 43%、技能缺口 35% | `E8` Informatica 2025 |

**〔判断〕** 最贴合本方法论论点的一条是 `E4`：Gartner 预测到 2026 年，缺乏 AI-ready 数据的 AI 项目将有 **60%** 被放弃，而 **63%** 的组织缺乏或不确定自己是否具备 AI-ready 数据实践（n=248）。**注意这是预测不是实测。**

对 agentic 场景，`E5` 预测到 2027 年底超过 **40%** 的 agentic AI 项目将被取消，原因是成本攀升、业务价值不明、风险控制不足——**同样是预测**。

### 两条必须交代的限定

**利益披露**：`E7`（障碍分解中模型能力不在首位）来自 Anthropic 的调研，而 Anthropic 售卖模型——「问题不在模型」这个结论对其有利。读者应当据此打折。

**曾经的错误**：本站在 2026-08-23 之前写过「企业 AI 项目的失败率**远高于消费级 AI 应用**」。核实后发现，所有可查的研究（MIT、Gartner、McKinsey、BCG、S&P、Deloitte、Informatica）**都只测企业侧**，没有任何一份用同一口径做过这个对比。该表述已删除。

### 三种主流的问题定义

不同流派对「卡在哪」的回答不同，这直接决定了他们的解法：

| 流派 | 问题定义 | 解法 | 盲区 |
|---|---|---|---|
| **数据派** | 数据没打通 | 数据湖 / 湖仓 / 中台 | 集中 ≠ 语义统一 |
| **知识派** | 模型不懂企业知识 | RAG / 知识库 / 微调 | 解决了「知道」，没解决「能做」 |
| **流程派** | 流程没自动化 | RPA / 工作流 / Agent 编排 | 自动化了动作，没自动化决策 |

**〔判断〕** 三种定义都对了一部分，但都不完整。我认为真正的问题是：

> 企业没有一层**机器可理解、且业务承认**的语义骨架，因此 AI 既不知道这家企业是什么，也不知道能对它做什么。

数据派解决了「数据在哪」，知识派解决了「知道什么」，流程派解决了「怎么执行」。三者之间缺的那一层——**这家企业由哪些东西构成、它们之间发生什么、能对它们做什么**——就是本体。

### 「瓶颈不在模型」的准确版本

**〔争议〕** 这是本方法论最核心、也最容易被过度陈述的一条。诚实的表述必须是有条件的：

> **对于结构化、可验证、短时程的企业流程**，边际瓶颈已从模型转移到集成、数据与组织（`E7`：46%/42%/39%；`E4`：AI-ready 数据）。
>
> **但对于长时程、跨系统、要求高可靠性的自主决策**，模型可靠性仍是硬约束。

反方证据必须列出，它们是有分量的：

- **`A16` METR 2026-01**：视觉/计算机操作类任务的 50% 可靠度时程比软件任务**低 40–100 倍**；**许多可靠性关键任务需要 98%+ 的成功率才值得自动化**，因此 50% 时程并不等于「可委托」。同时任务时程六年来每约 7 个月翻一番、2024–25 期间每约 4 个月翻一番——**说明能力仍是在变动的那个变量**。
- **`A17` run-to-run 方差是模型属性，治理层消除不掉**：pass^4 常比 pass^1 低 15–25 个百分点；90% 的基准分可能对应约 70% 的生产可靠性。这直接冲击本方法论把「稳定性：同一输入多次结果一致」列为可达标工程指标的做法（见 [模块三 3.6](03-模块三-Agentic系统设计与编排.md)）。
- **时间上的自我反驳**：2025–26 年 agent 得以部署的公认前提条件恰恰是**模型侧**的——推理模型、更长上下文、工具协议、成本坍塌。如果是能力升级解锁了部署，那么直到不久前能力都还是约束。**「瓶颈不在模型」因此是对此刻的描述，不是一条规律。**

### 一个有用的判别问题

**〔判断〕** 判断一个企业 AI 方案是否触及真问题，只需问一句：

> **这个系统被允许改变什么？**

- 答不上来 → 它是知识派或数据派的方案，价值上限是「更快地看见」
- 答得上来 → 它必须面对权限、审批、可逆、审计——也就是真正困难的部分

## 1.2 四代企业数据架构的演进 {#12}

**〔判断〕** **「数据架构分几代」不是领域共识，本节的四代分期是本站自建的教学装置。**

必须先说清它与已有分期的关系，否则就是对具名框架的未标注改写：

| 已有分期 | 内容 | 与本站分期的关系 |
|---|---|---|
| **Dehghani（Data Mesh 原文）** | 三代：① 私有企业数仓 + BI；② 大数据/数据湖生态；③ **现代云平台**（流式、Kappa、云托管存储与 ML） | **有实质冲突**。Dehghani 把 Data Mesh 定位为对**第三代失败的回应**，不是第三代本身；本站把 Data Mesh 当作自己的第三代，且把 Hadoop 湖与云上湖仓合并进第二代——恰好在她划分二/三代的那条线上合并了 |
| **Gartner** | EDW 时代 → 后 EDW（2000–2010）→ 逻辑数据仓库 → 主动元数据 | 维度不同，不可对齐 |
| **Inmon vs Kimball** | 不是代际关系，是**同时代的方法论之争** | 常被误当作代际，本站不采用 |

保留四代分期的理由只有一个：它是本站叙事的组织装置，用来说明「第四代的新问题是授权」。**它不是历史结论。**

### 第一代：报表时代（1980 年代末–2000 年代）

数据仓库 + BI 报表。特征：**面向汇总，事后回顾**。

时间锚点（`D1`–`D3`）：Devlin & Murphy 架构论文 **1988**，Inmon《Building the Data Warehouse》**1990/1992**，Kimball《The Data Warehouse Toolkit》**1996**。

> 本站此前写「1990s–2000s」，晚了约十年，已更正。

### 第二代：大数据与湖时代（2006–2010 年代末）

Hadoop（`D4`，**2006**）→ 数据湖（`D5`，James Dixon **2010-10-14** 提出该词）。特征：**面向规模，先存后用**。

**〔共识〕** 这一代解决了存储与计算的规模问题，也留下了最大的遗产问题：**数据沼泽**——数据都在，但没人知道哪个能用。

> **湖仓（Lakehouse）不属于这一代。**它是 **2020**（`D6`，Databricks 2020-01-30 博文，CIDR 论文 2021-01）。本站此前把湖仓放进「2010s」，错了整整十年，已更正。

### 第三代：语义与治理时代（2019–2023）

Data Mesh（`D7`，首篇 **2019-05**，四原则 **2020-12**）、数据合同（`D8`，**2022-08** 被推起来）、指标/语义层、MDM 复兴。特征：**面向可信，谁负责数据**。

> 两处必要的更正：
> - 本站此前写「2018–2023」，「2018」没有任何锚点，已改为 2019–2023。
> - **语义层与 MDM 都不是这一代的发明**（`D9`）：语义层可上溯至 1990 年代 Business Objects 的 universes 与 OLAP；MDM 是 2000 年代技术，Gartner 从约 2007 年起就有 MDM 魔力象限。这一代是它们的**复兴与治理化**，不是诞生。

**〔判断〕** 方向是对的，但它止于**数据供给**。它让「数字是可信的」，没有让「决策是自动的」。

> ⚠️ 关于 Data Mesh 有一处本站曾犯的稻草人化：说它「终点是把可信数据交给人」是不准确的。它的第四条原则**联邦式计算化治理**明确讲的就是把治理策略计算化地固化进平台。准确的差异表述是（`M2`）：**Data Mesh 自动化的是治理，不是决策。**

### 第四代：决策与行动时代

**〔判断〕** 这一代应当拆成两条线，本站此前笼统写「2023– 」是不准确的：

- **本体 / 决策智能：约 2021–22 起**。Gartner 早在 **2021-10** 就把 Decision Intelligence 列为 2022 年十大战略技术趋势（`D10`）；Palantir Foundry Ontology 更早，是 2010 年代中期。
- **Agentic：2023– 起**。ChatGPT 2022-11，Palantir AIP **2023-04**（`D11`）。

**〔争议〕** 这一代的边界还没有定论——放权到什么程度、责任如何分配、评测如何做，业界没有统一答案。

### 演进的一条主线

```
第一代  数据在哪      →  存取问题
第二代  数据有多少    →  规模问题
第三代  数据可不可信  →  治理问题
第四代  能不能自己动  →  授权问题   ← 当前所在
```

**〔判断〕** 每一代都没有取代上一代，而是叠加。`D12` 的社区调研（**自选样本，非严格抽样**）显示 2026 年云数仓仍占主环境 44%、湖仓 27%、混合 12%——数仓从未消失。

### 一条被降级的主张

本站此前写「第四代的失败案例，**绝大多数**是因为跳过了第三代」。

**〔假设〕**（原为〔判断〕，现降级）**没有任何研究测过这个因果。**最接近的支持只是相关性（`E4`）。而且有直接反证：MIT NANDA 报告把失败归因于**学习/记忆/反馈缺失**——"Tools fail not because of poor models, but because they don't learn, adapt, or integrate"——而不是治理缺失。这直接削弱「你失败是因为跳过了治理」这一叙事。

保留这个假设的理由是它与 `E4` 相容且可指导行动；**但它不能作为论证的支点使用。**

## 1.3 十条失败症状——以及本方法论覆盖不到的失败原因 {#13}

### 先说这份清单是怎么来的

**〔判断〕** 必须先诚实交代方法：

> **这十条是我按 [四条命题](../00-立场/01-核心命题.md) 的视角选出来的，因此下文任何「比例」都是构造的结果，不是统计结果。**

本站此前在这里写过「十条里只有一条半是模型问题。**这个比例本身就是这个领域最重要的事实**」。那是循环论证——症状是按已有的四条命题选的，根因是照着四条命题分的，然后比例被当成「事实」。**这句话已删除。**

真正有证据的版本在 1.1：`E7` 的障碍分解是 46%/42%/39%（集成 / 数据 / 变更管理），这是问卷实测，且**必须带上 Anthropic 的利益披露**。

### 十条症状（按根因归组）

| 根因 | 症状 | 表现 |
|---|---|---|
| **A · 缺少语义骨架** | 口径不唯一 | Agent 给的数与销售给的数不一致，会议在争论定义中结束 |
| | 数据湖谬误 | 数据都进来了，业务侧感受不到变化 |
| | 静默错误 | 上游改一个字段，下游算错了很久才发现 |
| **B · 缺少行动闭环** | 只读陷阱 | 做成会说话的看板，上线后很快无人使用 |
| | 组织没有承接 | 流程照旧，系统成了「多一个要看的东西」 |
| **C · 缺少边界与评测** | 没有评测 | 业务问准确率，回答是「感觉还不错」 |
| | 把 Agent 当员工 | 期望自主，却不给可核验的输入输出合同 |
| **D · 缺少治理纪律** | PoC 与生产的断崖 | PoC 很快做完，生产化遥遥无期（`E6`：平均 8 个月，仅 48% 进生产） |
| | 从数据出发 | 做出一堆没人要的能力 |
| | 范围与成本膨胀 | 本体越建越大，长期没有业务结果 |

> 原文中「12.4 万 vs 9.8 万」「指标悄悄降了 8%」等具体数字是**为说明而编造的示意值**，已删除或改为定性表述。

### 本方法论覆盖不到的失败原因

**〔判断〕** 这一节比上面那张表更重要。真实项目复盘里高频出现、但**一条都进不了上面十条**的失败原因至少包括：

| 失败原因 | 为什么它不在本方法论射程内 |
|---|---|
| **预算被砍 / 高层换人导致 sponsor 消失** | 这是组织政治，方法论提供不了对策。只能靠「选高频可逆场景快速出结果」间接对冲 |
| **关键人离职** | 本方法论的 Owner 制度反而放大了这个风险——单点依赖是它的副作用 |
| **合规或安全评审未通过** | 本站此前完全没有覆盖，现已补 [合规与安全前置](../20-实践/07-合规与安全前置.md)，但那仍是清单不是保证 |
| **供应商交付能力不足** | 见 [自建 vs 采购](../20-实践/09-自建vs采购与退出剧本.md) |
| **选定场景的业务价值本身被高估** | 见 [投入产出测算](../20-实践/08-投入产出测算.md)，但测算依赖的输入本身可能是错的 |
| **模型能力确实不够**（长尾语言理解、跨模态、长程一致性） | 见 1.1 的 `A16`/`A17`。**本方法论会系统性低估这一类**，因为它的整个叙事建立在「瓶颈不在模型」之上 |

**它们此前被排除，正是因为它们落不进四个预设根因。**把它们列出来，比多列十条能落进根因的症状更有价值。

## 1.4 概念坐标系：这些词到底什么关系 {#14}

**〔共识〕** 这个领域术语混乱，同一个词在不同语境下含义不同。先把坐标系立住。

### 按「解决什么问题」分类

| 概念 | 解决的问题 | 层次 |
|---|---|---|
| 数据湖 / 湖仓 | 数据在哪、怎么存算 | 基础设施 |
| MDM 主数据 | 名词的唯一与准确 | 数据治理 |
| 数据合同 / Data Mesh | 谁负责数据、变更怎么管 | 数据治理 |
| 语义层 / 指标平台 | 数字是什么（口径唯一） | 语义 |
| 知识图谱 | 关系是什么 | 语义 |
| **本体 Ontology** | **这家企业是什么，能对它做什么** | **语义 + 行动** |
| RAG / 向量库 | 模型如何取到相关文本 | 智能 |
| MCP / 工具协议 | 工具怎么被发现与调用 | 智能（互操作） |
| Agent 框架 | 多步任务如何编排 | 智能 |
| RPA / 工作流 | 已确定的流程怎么执行 | 行动 |
| **行动契约** | **系统被允许改变什么、怎么改** | **行动 + 治理** |

### 三组最容易混淆的概念

**本体 vs 知识图谱**
**〔共识〕** 技术实现上高度重叠，本体常用图结构承载。
**〔判断〕** 关键差异是**行动**：知识图谱通常只读、面向检索与推理；本体必须绑定可执行的行动并承载权限。**不能触发状态变更的本体，只是图谱。**

**本体 vs 语义层 / 指标平台**
**〔判断〕** 指标平台可视为本体的一个子集（管住指标口径唯一）；本体还要管对象、关系、生命周期状态机、行动与权限。**没有行动的语义层是 BI 的延伸，不是决策平台。**

**Agent vs RPA**
**〔共识〕** RPA 自动化的是**已确定的流程**，Agent 处理的是**需要判断的任务**。
**〔判断〕** 真正的分界不是技术，是问题类型：RPA 不问「该不该做」，只问「怎么做」。

### 定位图

```
            高｜决策与行动闭环
              │
              │   ┌──────────────────────────┐
              │   │  本体驱动的决策平台         │ ← 第四代
              │   └──────────────────────────┘
              │
              │        ┌─────────┐
              │        │   RPA   │  有动作，无决策语义
              │        └─────────┘
   ───────────┼──────────────────────────────────▶
              │  ┌──────────┐   ┌───────────┐   语义完整度   高
              │  │ BI / 报表 │   │ 语义层/指标 │
              │  └──────────┘   └───────────┘
              │
            低│  ┌──────────┐   ┌──────────┐
              │  │ 数据湖仓  │   │ 知识图谱  │
              │  └──────────┘   └──────────┘
```

**〔判断〕** 右上角是**本方法论关心的位置**。

> 本站此前写「右上角是**唯一有持续价值**的位置，其余象限的工具都会遇到价值天花板」。这个表述过强且无论证——**大量企业从 BI 获得的是长期、稳定、可观的价值**，`D12` 显示数仓从未消失。准确的说法是：其余象限的**价值上限**低于右上角，但不等于没有持续价值，也不等于应该被替换。

完整的范式对照见 [坐标系](../40-参考/01-坐标系.md)。

## 1.5 本方法论的适用边界 {#15}

**〔判断〕** 明确说清不适用的地方，比多列适用场景更有价值。

### 适用

- 决策**高频、可逆、有明确 Owner、有现成落点系统**的业务域
- 已达 **M1**（数据已集中、有可用的 BI/报表）的组织；M0 组织请先补数据工程
- 单 Agent 或确定性编排 + 模型节点的场景

### 不适用或覆盖不足

| 情形 | 说明 |
|---|---|
| **低频、不可逆的战略决策** | 是否进入新市场、是否收购——这是人的领域，本方法论不应被用于此 |
| **多 Agent 协作的审计** | [模块五 5.3](05-模块五-整合视图与展望.md) 承认这是未解问题。**本方法论当前只覆盖单 Agent 场景** |
| **模型能力本身是约束的任务** | 长程一致性、跨模态、需要 98%+ 可靠度的任务（`A16`） |
| **组织政治导致的失败** | sponsor 变更、预算被砍、关键人离职（见 1.3） |
| **托管大模型的严格可重放** | 本方法论承诺「给定代码版本 + 数据版本可重放」，这对托管模型不成立——模型会被下线、涨价、变更行为。见 [运行约束](../15-DIA框架详解/06-运行约束.md) |
