## 3.1 三种智能形态的选型 {#31}

**〔共识〕** 企业系统里「智能」有三种形态，各有适用边界。

| 形态 | 适用 | 不适用 | 成本 | 可解释性 |
|---|---|---|---|---|
| **确定性规则** | 逻辑明确、合规红线、阈值判断 | 规则数量爆炸、需要泛化 | 极低 | 完全 |
| **预测模型** | 有标签、有历史、结构化、需量化 | 缺历史、需解释推理链 | 中 | 中 |
| **生成/推理 Agent** | 非结构化输入、多步任务、需综合判断 | 高频简单判断、要求确定性输出 | 高 | 需专门设计 |

### 选型顺序

**〔判断〕** 按顺序问，不要跳步：

1. **能写成规则吗？** → 能就写规则
2. **规则写不下（组合爆炸或需泛化），有标签数据吗？** → 有就用预测模型
3. **输入非结构化、或需多步综合判断？** → 才用 Agent

> **能写死的不要用模型，能用小模型的不要用大模型。**
> 这不只是成本问题，更是可解释性与稳定性问题。**企业更看重「每次都一样」，而不是「大多数时候更聪明」。**

**成本的量级**（`A2`，Anthropic 公布）：Agent 约为 chat 的 **4 倍** token，多 Agent 约 **15 倍**。这个倍率应当直接进入选型判断，而不是等到上线后再发现。

### 混合是常态

```
Agent          负责理解意图与编排
  ├─ 规则      负责红线与硬约束（不可越过）
  ├─ 预测模型  负责量化判断
  └─ 行动契约  负责最终执行（固定、可审计）
```

**〔判断〕** 让模型负责「**选哪条路**」，让确定性代码负责「**走这条路**」。模型的输出应尽可能是一个受限的选择，而不是一段自由文本或自由代码。

## 3.2 设计模式速查（术语对照，非选型指南） {#32}

> **本节定位已下调。**它的用途是让你在别处读到这些术语时知道指的是什么，**不是**让你「挑一个图来用」。
> **企业里的可靠性主要不来自选对形状**，来自 3.4–3.7 讲的东西。

### 单 Agent

| 模式 | 是什么 | 2026 年的状态 |
|---|---|---|
| **Tool Use** | 模型输出结构化调用请求，运行时执行并返回 | 所有 Agentic 能力的地基。**〔判断〕** 工具设计是单项投入回报最高的一件事（见 3.5）。<br>⚠️ 本站此前写「企业里 **80%** 的价值来自这一个模式」——**这个数字是我编的，没有任何研究支持，已删除。**可支持的是 Anthropic 的主张：应在「Agent-计算机接口（ACI）」上投入与 HCI 同等的努力 |
| **ReAct** | 交替「思考」与「行动」，用观测驱动下一步 | **〔判断〕** **循环存活，名字在退场**（`A14`）。LangChain 已把 `create_react_agent` 更名为 `create_agent`；文字解析式的 `Thought:/Action:/Observation:` 脚手架已被原生 function calling + 供应商侧推理取代。<br>准确的说法是：**ReAct 没有过时，它被吸收了**；架构层剩下的工作是**给循环设边界**（迭代上限、成本上限、工具 schema、trace 可观测）。<br>⚠️ 本站此前把〔争议〕设为「显式 thought 输出是否还有必要」——**这个争论已经不活跃了**。真正在争的是**思维链作为安全监控手段有多脆弱**（`A14`，UK AISI/DeepMind/OpenAI/Anthropic/Meta 联署立场论文的议题） |
| **Plan-and-Execute** | 先产出完整计划，再逐步执行 | **〔判断〕** 它在 2026 年**首先是一个安全模式**：在摄入任何不可信内容**之前**把计划固定下来，注入内容就无法改变控制流——这是 `A9` 六种抗注入模式中的核心一种。见 3.6。<br>⚠️ 「计划可被人审查」这个优点**会随时间衰减**（`A10`）：批准率随时间上升而审查深度下降。**这直接冲击 L2「草拟 + 人工确认」作为长期稳定状态的假设**，见 3.6 末与 [模块四 4.3](04-模块四-行动闭环与企业采纳.md) |
| **Reflection / 自省** | 模型对自己的输出做批判并修订 | **〔判断〕** 在有客观真值的任务上，**用外部验证器替代自省**更便宜也更可靠。<br>这是本站论证最扎实的一条判断，现在可以坐实（`A4`）：Kamoi et al.（TACL）——「没有任何先前工作展示了仅靠 prompted LLM 反馈的成功自我纠正」，瓶颈在**反馈生成**；Huang et al.（ICLR 2024）《LLMs Cannot Self-Correct Reasoning Yet》仍然成立；进一步的研究指出失败在**错误检测**而非纠正。<br>补充：存在「生成—验证差距」，基于验证器的 test-time scaling 优于无验证器方案，**但收益上限由验证器质量决定** |
| **Router / 分类路由** | 先分类意图，再分发到专门路径 | **〔判断〕** 把「无所不能的 Agent」拆成「分类器 + 窄专家」，大幅提升可评测性与可审计性——每条路径可单独评测、单独放权。<br>⚠️ **它在 2026 年已部分下沉为基础设施**（Azure AI Foundry Model Router、vLLM Semantic Router），当前形态是成本/质量级联路由，不是应用层模式 |
| **Structured Output** | 强制输出符合 Schema | ⚠️ **本站此前把它列为「首要设计模式」，这个归类本身就暴露了年份。****2026 年它不是设计模式，是 API 的基础能力**——各家都已提供针对 JSON Schema 的约束解码。<br>它仍然重要（自由文本无法被下游可靠消费，也无法被断言校验），但应作为**默认设定**而非「模式选择」。<br>并且有一个本站此前忽略的真实权衡（`A13`）：**严格格式约束可能损害推理质量**。实践取向：让模型先自由推理、再产出结构化结果，而不是全程约束 |

### 多 Agent

| 模式 | 是什么 | 2026 年的状态 |
|---|---|---|
| **Supervisor / 主管** | 一个主管 Agent 调度若干专家 | **〔判断〕** 警惕**主管本身成为不可审计的黑箱**。企业里更好的做法是主管用确定性编排，专家用模型 |
| **Pipeline / 流水线** | 固定顺序的多个专门 Agent | 「无聊但可靠」。每段可独立评测、独立回滚 |
| **self-consistency**（采样多次取多数） | 同一模型采样 N 次，多数表决 | **便宜且可靠的那一个。**必须与下一行区分开 |
| **multi-agent debate** | 多个 Agent 辩论后收敛 | ❌ **本站此前标〔共识〕说它「能提升困难任务的正确率」——这条被证据直接否定，是本站唯一一处「标为共识但实际结论相反」的错误。**<br>`A5`（ICLR 2025，5 个 MAD 框架 × 9 个基准）：多数框架**既打不过 CoT 也打不过 self-consistency**；等 token 预算下几乎都不 scale。**归给「辩论」的收益大部分其实来自多数表决。**已记录的失败模式：谄媚性趋同最高 **85.5%**、上下文脆弱性最高 70%、共识坍塌；**竞争式辩论比单 Agent 低最多 15 个百分点**。<br>**仅在跨模型异构 + 中等难度 + 协作式（非竞争式）协议下才有效** |
| **共享状态**（blackboard） | 多 Agent 读写共享状态空间 | **〔判断〕** 不是过时术语，是活跃在研模式（`A12`：相对 supervisor 基线端到端成功率 **+13–57%**）；2026 年生产口径已改称 **session state / artifacts / 共享草稿板**。<br>⚠️ 本站此前说它的问题是「难调试」——**真正的权衡是读写不对称**：读操作天然可并行，**冲突的写决策后果远比冲突的读严重**。<br>⚠️ 它现在还是一个**具名安全风险**：OWASP ASI06 记忆与上下文投毒，见 3.6 |

### 检索

| 模式 | 2026 年的状态 |
|---|---|
| **RAG** | **〔判断〕**（原标〔共识〕说它是「默认方案」，已加时间限定）**这个默认在 2026 年已经动摇**：产业侧正在从「向量库 + RAG」转向 **agentic search / 检索即工具调用**。<br>不变的判断：**RAG 解决的是「知道」，不解决「能做」**——检索到的文本不能被权限约束、不能被断言校验、不能触发行动 |
| **GraphRAG** | 见 [模块二 2.2](02-模块二-语义与本体.md)。**微软已于 2026-08-14 转入维护模式**（`A8`）。企业里更实用的是**直接查本体**。<br>⚠️ 本站此前遗漏的一条告诫：**Text2Cypher 与 Text-to-SQL 有同样的准确率问题**——把 SQL 换成图查询语言只是**转移**了语义接地问题，没有消除它 |
| **Text-to-SQL** | ⚠️ **本站此前的禁令「企业生产环境不应使用，只应存在于隔离沙箱」是错的，已改。**<br>各大平台都已 GA 且带治理地大规模提供（Snowflake Cortex Analyst、Databricks AI/BI Genie、Google Looker Conversational Analytics、Microsoft Fabric Data Agents）。**「隔离沙箱」不是业界控制手段，也解决不了真正的失败模式。**<br>**真实的边界是「受治理 vs 不受治理」，不是「生产 vs 沙箱」。**受治理意味着：继承调用者 RBAC 的只读角色、受治理的语义层、已验证查询库、模型与数据库之间的确定性 SQL 校验、回归基准。<br>**但原有的直觉有数据支持**（`A6`/`A7`）：dbt 2026 基准 text-to-SQL **90.0%** vs 语义层 **98.2%**；GPT-5.3 Codex **84.1%** vs **100%**。BIRD 榜首 **81.95%** vs 人类基线 **92.96%**；LinkedIn SQL Bot 生产实测 schema-only 基线 **9%** → 专用系统 **48%**；Snowflake 自承 GPT-4o 在 Spider 上 90%+，在其真实 BI 集上掉到 **51%**。<br>**关键论据是失败模式不同**：text-to-SQL「有时给你一个貌似合理的错答案」，语义层**直接报错**——**这与本方法论的「失败关闭」原则是同一个论证**。<br>⚠️ **不要引用任何 text-to-SQL 排行榜名次**：CIDR 2026 发现 BIRD Mini-Dev 标注错误率 **52.8%**、Spider 2.0-Snow **62.8%**，纠正后排名位移 −9 至 +9 位 |

### 关于「模式优先级」的一处更正

**〔判断〕** 本站此前给出过一个固定排序（Structured Output + Router + Tool Use > Plan-and-Execute > Pipeline > 其余）。

**这是过度声明。**`A1`：Anthropic、OpenAI 都主张「从最简单开始、只在需要时增加复杂度」，但**没有任何一家发布过线性优先级排名**，他们发布的都是**决策判据**。把一个固定排序说成共识是不诚实的。

保留下来的、站得住的原则只有一条：

> **从最简单的方案开始，每增加一层复杂度都要说出它消除了哪个具体风险。**

## 3.3 编排范式：工作流 vs 自主体 {#33}

**〔争议〕** 这是当前领域最核心的分歧。

| | 确定性工作流 | 自主 Agent |
|---|---|---|
| 控制流 | 代码写死 | 模型决定 |
| 可预测性 | 高 | 低 |
| 可评测性 | 每步可测 | 端到端难测 |
| 调试 | 容易 | 困难 |
| 成本 | 可预算 | 波动大 |
| 失败模式 | 显式报错 | **悄悄走偏** |

### 这个争论 2025 年最著名的一次交锋，以及它的收敛结论

**〔共识〕** 2025-06，相隔 24 小时：Cognition 发表《Don't Build Multi-Agents》，Anthropic 发表《multi-agent research system》，给出相反建议（`A11`）。

**收敛结论是「任务决定架构」**：

> **并行、以读为主的工作**适合多 Agent 隔离；
> **共享状态、以写为主的工作**应当保持单线程。

**〔判断〕** 这个结论比我原先的表述更细一层，且直接支持它。合并后的立场是：

> **控制流应当是确定性的，判断应当是模型的；**
> **并行只读可以放开，共享状态的写必须收敛到单线程。**

理由是企业的三个硬约束：**可评测**（每步有明确输入输出）、**可归因**（出错能定位到步骤）、**可放权**（「在什么条件下自动」必须可陈述）。

### 什么时候确实需要自主编排

**〔判断〕** 三个条件同时成立时：步骤数与顺序**事前不可知**（真的不可知，不是懒得梳理）· 失败代价低且可逆 · 有人在回路做最终确认。

典型：研究型任务、探索性分析。
**反例**：补货决策、告警分级、订单拦截——步骤可枚举，用自主编排纯属自找麻烦。

### 实用折中：确定性骨架 + 模型节点

```
[确定性] 触发条件判断
      ↓
[模型]   理解与分类  ──→ 结构化输出
      ↓
[确定性] 路由到对应分支
      ↓
[模型]   在该分支内生成参数  ──→ 结构化输出
      ↓
[确定性] 参数边界校验、权限校验、不可信来源校验（见 3.6）
      ↓
[确定性] 调用行动契约
      ↓
[确定性] 审计留痕
```

模型只出现在两个受限位置，输出都是结构化的，前后都有确定性校验。

## 3.4 上下文经济学 {#34}

> **本节是重构新增。**本站此前的「上下文工程与记忆」停留在「放什么、不放什么」的提示词视角，没有把上下文当作**有限资源与预算**来处理。
> **2025–26 年多数 Agent 工程本质上是预算管理。**

### 核心命题

**〔判断〕**

> **上下文窗口是稀缺资源。**即使窗口足够大，塞满它也是错的——理由与「装不下」无关：
>
> - **成本**：上下文长度直接决定单次决策成本，且它是**每一步都要重付**的（Agent 每一轮都会重发历史）
> - **可归因**：塞进去 200 页，出错时无法知道模型用了哪一段
> - **权限**：塞进去的每一条都必须通过权限校验——**上下文越大，越权风险越大**
> - **注入面**：塞进去的每一条不可信内容都是一个攻击入口（见 3.6）

### 上下文的四个来源与优先级

| 来源 | 内容 | 企业里的取向 |
|---|---|---|
| **结构化事实** | 来自本体的对象、指标、关系 | **首选**——只有本体化的事实才带着口径、权限和时点 |
| 指令 | 角色、任务、约束、输出格式 | 必须版本化（见下） |
| 非结构化检索 | RAG 取回的片段 | 需标注来源与时效；**不能替代结构化事实**；来自外部方的必须标为不可信 |
| 记忆 | 历史交互、偏好、长期状态 | 权限与隐私的高风险区；见下「组织记忆」 |

**〔判断〕** 企业场景与消费场景最大的差别在于第一项的比重。消费级 Agent 的上下文主要靠检索，**企业级 Agent 的上下文应当主要来自本体**。

### 四种上下文预算技术

**〔共识〕** 2025 年底以来形成的组织性做法：

| 技术 | 做什么 | 企业里的注意点 |
|---|---|---|
| **压缩（compaction）** | 定期把历史压成摘要，释放窗口 | **压缩是有损的**——被压掉的内容如果是决策依据，证据链就断了。企业里应当**压缩对话、不压缩证据**：证据写入审计记录而不是留在上下文 |
| **结构化笔记 / 外部状态** | 把中间状态写到上下文之外（文件、状态库） | 这与「不要制造第二套真相」有张力：笔记可以存，但**不得成为业务状态的权威副本** |
| **子 Agent 上下文隔离** | 把子任务放进独立上下文，只回传结论 | 与 3.3 的「并行只读可放开」一致。注意回传结论必须带证据引用，否则主 Agent 无法追溯 |
| **即时检索**（just-in-time） | 需要时再取，而不是预先塞满 | 对应产业侧从「向量库 + RAG」转向 **agentic search** 的转变 |

### 代码执行即工具调用（code mode）

**〔判断〕** 这是本站此前完全遗漏、且对成本影响最大的一项。

把「逐个调用工具」改为「让模型写一段代码去调用工具」，循环、条件、错误处理随之移入代码：

- 直接后果：**Pipeline 与大半个 Plan-and-Execute 被吸收掉了**——它们变成了代码里的控制流，而不是编排层的模式选择
- 公开的量级：某些任务的 token 消耗从约 **15 万降到约 2 千**

**企业里的约束**：代码执行必须在沙箱内、无网络、权限受限，且**生成的代码本身应进入审计记录**——它是这次决策的推理过程。

### 组织记忆应当沉淀回本体

**〔判断〕** 记忆有三层：会话内 → 跨会话 → **组织记忆**（哪类告警通常是误报、哪个供应商经常延迟）。

第三层最有价值，也最被忽略。而它**不应该存在向量库里，应该沉淀回本体**——变成对象的属性或事件。

> 「这个供应商经常延迟」应当是供应商对象上的一个**派生属性**，可被查询、可被审计、可被质疑，而不是一段散落在记忆库里的文本。

这也是安全考虑：记忆库是 OWASP ASI06（记忆与上下文投毒）的攻击目标，而本体属性有权限、有血缘、有变更记录。

### 上下文即配置项

**〔判断〕** 提示词、模型版本、温度、检索策略、上下文模板、压缩策略——全部是会改变系统行为的配置，必须享受与代码同等的工程待遇：**版本化 · 绑定证据 · 变更即回归 · 可回滚**。

> 典型事故：有人「优化」了提示词，指标下降，很久之后才发现，且无法定位是哪次改动。根因是提示词不在版本控制里。
> （此前本站在此写「指标悄悄降了 8%」——**这个数字是示意，不是实测**，已删除。）

## 3.5 工具设计与互操作 {#35}

### 核心原则不变

```
❌  Agent + 数据库连接 + 「你可以写 SQL 查任何东西」
✅  Agent + 本体工具集 + 「你可以调用这些工具」
```

**〔判断〕** **Agent 的能力边界 = 本体暴露给它的工具集。**工具只来自两处：本体上的**只读投影**与本体上的**行动**。

这不是限制智能，是**让智能可以被授权**。企业里没有授权，就没有使用。

> 一处必要的软化：见 3.2 关于 Text-to-SQL 的更正。**受治理的自然语言查询在 2026 年是可用的**；本原则反对的是**不受治理的自由数据访问**，不是反对自然语言接口本身。

### 工具数量：用有出处的数字替换我原来编的阈值

⚠️ 本站此前写「〔共识〕工具过多会显著降低选择准确率」+「〔判断〕超过 **15–20 个**工具时应先用 Router 分域」。前者无出处，后者的数字是我发明的（**碰巧接近一条真实建议，但那是巧合**）。

**有出处的版本**（`A3`）：

> 工具选择准确率随暴露工具集增大而下降。
> **OpenAI** 建议单轮可用函数「目标少于 20 个，不过这只是一个软性建议」。
> **Anthropic** 建议超过约 **10 个工具**（或工具定义超过 1 万 token）即启用工具检索，并实测到准确率恢复：**Opus 4 从 49% 提升到 74%**、**Opus 4.5 从 79.5% 提升到 88.1%**，同时 token 减少 85%。
> **没有任何厂商公布硬性悬崖**，且有研究指出部分已报告的退化被候选集增大导致的随机基线漂移所混淆。

**可操作的取向**：超过约 10 个工具就该考虑工具检索或 Router 分域，而不是继续往一个 Agent 上堆。

### 工具设计的五条要点

1. **粒度贴合业务动作，不贴合数据表**
   ✅ `查询客户近 90 天履约异常`　❌ `select from t_order`
2. **返回必须包含证据引用**——数据来源、口径版本、时间戳
3. **失败必须显式且可被模型理解**
   `NOT_READY: 缺少 2026-08-20 的库存快照`
   **绝不能返回空结果**——空结果会被 Agent 当成「没有异常」
4. **数量克制**——见上
5. **区分可信与不可信来源**（新增，见 3.6）
   工具返回中凡包含**外部方提供的自由文本**（客户留言、供应商备注、邮件正文、网页内容），必须显式标记为不可信，且**不得直接决定行动参数**

### MCP：工具互操作的既成标准

**〔共识〕** Model Context Protocol 已于 **2025-12-09** 捐给 Linux Foundation 下的 Agentic AI Foundation，由 Anthropic、OpenAI、Block 共同发起，Google/微软/AWS 支持（`A15`）。

**〔判断〕** 它对本方法论是**同向的**，应当明确引用而不是回避：

- MCP 正是「**工具即本体行动**」这个主张的现成落地协议——把本体的查询与行动暴露为 MCP server，Agent 侧的接入成本从 N×M 降到 N+M
- 企业最关心的**网关级鉴权**在这一层有位置
- Palantir 自己已提供 Palantir MCP（`P5`）

**企业里的注意点**：MCP server 是一个新的攻击面与供应链依赖。第三方 MCP server 应当按引入外部依赖的标准审查（见 3.6 供应链一节）。

### Agent Skills：分发与策略单元

**〔判断〕** 以「技能包」形式封装能力（说明 + 脚本 + 资源，按需渐进披露），对企业最相关的一点不是它节省 token，而是**它是一个分发与策略单元**——可以按组织、按角色授予与回收，可以版本化，可以审计谁在用哪个版本。

这正是本方法论关心的东西，而 3.2 的模式谱系里没有槽位放它。

## 3.6 Agent 威胁模型与抗注入设计 {#36}

> **本节是重构新增，也是本站此前最严重的缺口。**
> 全站核心主张是「不要给 Agent 自由 SQL，要给它定义良好的工具」——**而工具化 Agent 恰恰是间接提示注入的主要攻击面**。
> 本站的权限模型能挡住**越权**，挡不住**权限内的被操纵行动**。

### 这不是假想：EchoLeak（CVE-2025-32711）

**〔共识〕** 2025 年 6 月披露的 **EchoLeak** 是**首个在生产环境 LLM 系统中被武器化、并造成实际数据外泄的提示注入**（`A18`）：

| 项 | 内容 |
|---|---|
| 目标 | Microsoft 365 Copilot（覆盖 Word / Excel / PowerPoint / Outlook / Teams） |
| 触发 | **零点击**——一封构造过的普通商务邮件，收件人**不需要做任何操作** |
| 后果 | Copilot 处理隐藏指令，静默外泄企业内部数据 |
| 评级 | CVSS **9.3** |
| 攻击链 | 绕过微软专门的跨提示注入分类器 **XPIA** → 用引用式 Markdown 规避链接脱敏 → 利用自动拉取的图片 → 滥用 CSP 允许的 Teams 代理 |
| 处置 | Aim Security 披露，微软服务端修复，确认无在野利用 |

**〔判断〕** 这个案例对本方法论有两条直接后果，比它本身的技术细节更重要：

> **① 检测式防御不可依赖。**
> EchoLeak **绕过了一个专门为提示注入设计的分类器**。任何「我们加了一个注入检测模型」的方案，都必须假设它会被绕过。
> **防线必须是结构性的**——不依赖「认出攻击」，而依赖「即使没认出来，也做不成事」。这正是下文六条规则的设计取向。
>
> **② 攻击链由若干各自合理的功能拼成。**
> Markdown 渲染、图片自动加载、CSP 白名单——每一项单独看都是正常特性。**因此逐个审查功能不足以发现问题**，必须按「不可信内容能走到哪里」这条路径整体审查。

### 为什么权限模型不够

把 EchoLeak 换成本方法论的语境：设想一个已经完全符合本方法论的系统——Agent 继承调用者权限、只能调用本体行动、参数有范围约束、行动可逆、全程审计。

一个供应商在订单备注里写一句话。Agent 读取订单对象时把这句话带进上下文，随后触发了一次**完全在权限内、参数完全在范围内、审计完整**的调价或补货。

**没有任何一条既有约束被违反，但决策是被外部人操纵的。**

**〔判断〕** 这类攻击的存在，意味着本方法论的四条治理约束还需要补第四类防线：**输入可信度**。

### 威胁分类

**〔共识〕** OWASP 已针对 Agentic 应用发布专门的风险清单。对本方法论最相关的几类：

| 威胁 | 在本方法论架构中的落点 |
|---|---|
| **间接提示注入** | 任何把外部方文本带进上下文的工具返回（3.5 要点 5） |
| **记忆与上下文投毒**（ASI06） | 组织记忆、共享状态、跨会话记忆（3.4） |
| **工具滥用 / 参数操纵** | 行动契约的参数边界（[模块四 4.1](04-模块四-行动闭环与企业采纳.md)） |
| **越权升级** | 权限约束（模块四 4.4）——**这是唯一一类现有约束已覆盖的** |
| **供应链**（第三方工具 / MCP server / 技能包） | 3.5。EchoLeak 中被滥用的 Teams 代理就是一个「已被信任的通道」 |
| **成本型拒绝服务**（诱导无限循环或高成本调用） | [运行约束](../15-DIA框架详解/06-运行约束.md)的配额与熔断 |

### 六条可落地的抗注入设计规则

**〔判断〕** 以下每一条都与本方法论已有的强项同源，写起来是顺理成章的延伸，不是外挂：

| # | 规则 | 与既有原则的关系 |
|---|---|---|
| **1** | **不可信内容必须显式标记。**来自外部方（客户、供应商、公开网页、收件邮件）的自由文本，从进入上下文的那一刻起就带标记 | 延伸自「血缘可追」 |
| **2** | **不可信内容不得决定行动参数。**参数必须来自结构化事实或用户的直接指令 | 延伸自「结构化输出优先」 |
| **3** | **高风险行动前做独立复算。**校验「这个参数能否由本体事实独立推导出来」——不能则拒绝 | 延伸自「双算校验」 |
| **4** | **先定计划，再读内容**（Plan-Then-Execute，`A9`）。在摄入任何不可信内容之前把计划固定下来，注入内容就无法改变控制流 | 延伸自「控制流确定性」 |
| **5** | **不可信内容触发的行动降一级自治。**读到外部文本的那一轮，自治级别自动从 L3 降到 L2 | 延伸自「分级自治」与「失败关闭」 |
| **6** | **对抗性用例进评测集。**金标准集必须包含注入尝试，且这些用例的通过判据是「拒绝」而不是「答对」 | 延伸自「评测集必须覆盖失败模式」 |

**〔判断〕** 注意这六条**没有一条是「检测注入」**。这是刻意的：EchoLeak 证明了检测会被绕过。
六条守的都是「即使注入成功进入上下文，它也无法改变行动参数、无法改变控制流、无法在无人复核的情况下执行」。

### 一条对 L2 的重要修正：人工确认会退化

**〔判断〕** `A10`：2026-06 的纵向研究显示，对 Agent 输出的**批准率随时间上升，而审查深度下降**。业界正在形成的经验规则是：

> **批准率 ≥95% 时，这个检查点已经是「确认剧场」，应改为抽样复核。**

这直接冲击本方法论把 L2（草拟 + 人工确认）当作**长期稳定状态**的假设。修正后的取向：

- L2 不是终点，是**过渡态**。长期停留在 L2 的场景，人工确认的实际保护力会衰减到接近零
- **必须监控批准率**。批准率是一个应当进入 [运行约束](../15-DIA框架详解/06-运行约束.md) 可观测指标的数字，与「人工推翻率」并列
- 批准率过高时，正确的动作是**要么晋级到 L3 + 抽检，要么承认这个检查点无效并重新设计**——而不是维持一个形式上的确认按钮

### 供应链

**〔判断〕** 第三方工具、MCP server、技能包都是新的供应链依赖，应按引入外部依赖的标准审查：来源可信度、版本锁定、变更通知、可撤销、最小权限。

**一条硬规则**：**第三方工具不得直接绑定 R2/R3 行动**。它们可以提供信息，行动必须由本企业自己定义的行动契约执行。

## 3.7 harness：运行期工程 {#37}

> **本节是重构新增。**

**〔判断〕** 2026 年的实践共识是：

> 团队从 **harness 改造**拿到的可靠性提升，**大于**从「ReAct 换成 Plan-and-Execute」拿到的。

harness 指的是包裹模型的那层运行框架——它决定了循环怎么开始、怎么结束、错误怎么处理、上下文什么时候重置、工具长什么样、权限在哪里检查。

### 企业里 harness 的六个必备件

| 件 | 内容 | 缺失的后果 |
|---|---|---|
| **循环边界** | 最大迭代数、最大耗时、最大成本 | 一次失控循环烧掉一天预算 |
| **上下文重置策略** | 什么时候压缩、什么时候开新会话 | 长任务后期质量断崖式下降 |
| **验证闸** | 每一步的输出在进入下一步前被确定性校验 | 错误逐步放大，最后一步才暴露 |
| **工具人体工学** | 工具名、参数名、错误信息是否对模型友好 | 模型反复调错工具，token 与准确率双输 |
| **权限门** | 权限检查发生在工具执行处，而不是入口处 | 中途身份切换导致越权 |
| **trace 可观测** | 每一步的输入输出、耗时、成本可回放 | 出错无法归因（见 3.8） |

**〔判断〕** 这六件与本方法论的关系：它们是**四条治理约束在运行期的具体实现位置**。约束定义了「必须做到什么」，harness 是「在哪里做到」。

## 3.8 评测方法总结 {#38}

**〔共识〕** 没有评测就没有生产。生成式系统尤其容易「看起来对」，人的直觉在这里系统性失效。

### 三层评测

| 层 | 时机 | 内容 |
|---|---|---|
| **离线金标准集** | 上线前 | 专家标注的历史案例，**必须覆盖失败模式**：缺数据、口径歧义、极端值、**注入尝试**（新增，见 3.6） |
| **影子运行** | 上线中 | 真实数据流上产出建议但不执行，与人的实际决策比对 |
| **在线抽检** | 上线后 | 持续按比例人工复核已执行动作 |

**〔判断〕** 金标准集**冻结后不得因结果不好而修改**——改了就失去了裁决能力。

**〔判断〕** 影子运行阶段，**分歧比一致更有价值**。每个人机分歧应归因为三类之一：系统错 / 人错 / 口径不清。**第三类是本体建设最好的输入。**

### 评测方法谱系

| 方法 | 适用 | 局限 |
|---|---|---|
| 精确匹配 / 结构校验 | 结构化输出 | 只能测格式与取值 |
| **确定性验证器** | 有客观真值的任务 | **〔判断〕** 企业场景应优先用这个——比 LLM 判分便宜且稳定，且 `A4` 表明验证器质量决定收益上限 |
| 人工标注对照 | 需要业务判断 | 成本高，但金标准集只需建一次 |
| LLM-as-Judge | 开放式输出 | **〔争议〕** 与人的一致性因任务而异；存在**自我偏好偏差**。**〔判断〕** 只应作为补充，不应作为上线判据的唯一依据 |
| **轨迹 / trace 评测** | Agent 多步任务 | **〔判断〕** 2026 年企业侧的评测重心已从终态正确性转向**过程正确性**——终态对但过程错的 Agent 在分布外会失败 |
| A/B 分流 | 需要因果结论 | 唯一能证明业务价值的方法，但需要业务方接受实验 |

> ⚠️ **一处引用禁忌**：OpenTelemetry 的 GenAI 语义约定**仍处于 1.0 之前**，2026-06 迁至独立仓库且无 tagged release——**不要把它当作稳定标准引用**。

### 指标维度

| 维度 | 说明 |
|---|---|
| 正确性 | 基础 |
| **弃权率** | 主动说「不确定」的比例。**一个从不弃权的系统是危险的**——它不知道自己不知道 |
| **错误分布** | 高准确率但错在高价值样本上，等于不可用 |
| **稳定性** | 同一输入多次结果一致。⚠️ **这不是一个可以靠工程达标的指标**：`A17` 表明 run-to-run 方差是模型属性，pass^4 常比 pass^1 低 15–25 个百分点，90% 的基准分可能对应约 70% 的生产可靠性。**应作为需要测量并接受的事实，而不是需要达标的目标** |
| **人工批准率** | 新增，见 3.6。≥95% 意味着确认环节已失效 |
| 时延 / 单次成本 | 决策有窗口期；成本要能算过来（见 [投入产出测算](../20-实践/08-投入产出测算.md)） |

**〔判断〕** 上线后最诚实的指标是**人工推翻率**——它直接度量业务方的真实信任度，通常比技术指标更早报警。

评测集模板见 [模板库](../20-实践/04-模板库.md)。
