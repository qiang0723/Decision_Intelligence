## 5.1 整合：决策智能架构 DIA {#51}

**〔判断〕** 本节是我个人的整合框架。前四个模块总结的是领域现状，这一节是我认为它们应该如何合成。

### 一句话

> 决策智能架构，是把企业的**事实**与企业的**行动**，通过一层业务承认的**本体**缝合起来，
> 并在权限、证据、可逆、运行四条约束下，交给分级授权的智能体去驱动的架构。

记忆锚点：**一个中心，两个方向，四条约束。**

### 分层

```
                    ┌─────────────────────────────────┐
                    │   D  决策界面                    │  谁在决策 · 依据什么 · 谁担责
                    └───────────────┬─────────────────┘
                                    │  决策需求向下驱动
                    ┌───────────────┴─────────────────┐
                    │   A  行动                        │  可写回 · 可逆 · 可审批
                    └───────────────┬─────────────────┘
                    ┌───────────────┴─────────────────┐
                    │   I  智能                        │  规则 · 模型 · Agent
                    └───────────────┬─────────────────┘
    ╔═══════════════════════════════╧═════════════════════════════════╗
    ║                        O  本体  Ontology                         ║  ★ 中心
    ╚═══════════════════════════════╤═════════════════════════════════╝
                    ┌───────────────┴─────────────────┐
                    │   F  事实                        │  口径 · 血缘 · 时点正确
                    └─────────────────────────────────┘
                                    ▲  事实向上支撑

    横切四约束（贯穿全部五层）：
      权限 Authority ｜ 证据 Evidence ｜ 可逆 Reversibility ｜ 运行 Runtime
```

> **两处必须说明的读图规则**（2026-08-23 补，此前缺失导致误读）：
>
> 1. **纵轴表示「离决策的远近」，不表示调用方向。**正文说「智能层调用行动」，而图上 A 在 I 之上——在分层架构惯例里调用方在上，此处正好相反。这是刻意的：这张图组织的是**职责的远近**，不是调用栈。
> 2. **运行不再是一层。**此前本站把 R 运行层画在 F 之下，但它的内容（隔离、成本、发布回滚、可观测）**作用于所有层**，与「事实层之下」这个位置没有任何关系；而且它包含的「权限落到运行时」与约束一重复。现升格为第四条横切约束。

### 五层与前四模块的对应

| 层 | 核心问题 | 来自哪个模块 |
|---|---|---|
| **D** 决策界面 | 谁在做什么决策，错了谁担责？ | 模块四 4.6 |
| **A** 行动 | 系统被允许改变什么？ | 模块四 4.1–4.2 |
| **I** 智能 | 用规则、模型还是 Agent？放权到哪一级？ | 模块三全部 + 4.3 |
| **O** 本体 | 企业由哪些对象和关系构成？ | 模块二 2.1–2.4 |
| **F** 事实 | 这个数从哪来，什么时候的口径？ | 模块二 2.5–2.6 |
| **横切 · 权限/证据/可逆** | 凭什么敢让它做？ | 模块四 4.4、4.4b |
| **横切 · 运行** | 谁能跑、花多少、错了怎么退？ | 模块四 4.5 |

### 为什么本体必须在中心

**〔判断〕** 一旦本体只是「一个可选的语义层」，就会立刻出现绕过它的捷径：报表直连数据库、Agent 写自由 SQL、前端硬编码业务公式。三个月后企业就有了第二套、第三套口径。

架构判据只有一条：

> **除本体外，不存在第二条通往业务语义的路径。**

### 与传统数据架构的差异

| 维度 | 传统数据中台 / BI | 决策智能架构 |
|---|---|---|
| 起点 | 有哪些数据 | **有哪些决策** |
| 中心 | 数据仓库 / 湖仓 | **本体** |
| 终点 | 报表与看板（只读） | **行动与写回** |
| 语义 | 分散在报表与 SQL 里 | 集中在本体，唯一权威 |
| AI 的位置 | 数据之上的一个应用 | 本体之上的一类执行者 |
| 权限 | 表级 / 接口级 | 对象 / 关系 / 行动级 |
| 成功标志 | 数据接入完成率 | **被自动或半自动执行的决策数量** |

### 使用方式

**〔判断〕** **不要自上而下建全套。**五层是描述性骨架，不是建设顺序。

正确方式是**沿着一个真实决策，把五层打穿一次**：选一个高频可逆的决策 → 定义 3–5 个对象 → 定义 1 个行动 → 接入最小数据集 → 智能层从 L1 起步 → 运行层给出隔离与回滚 → 交付人机权责矩阵并取消一个旧动作。

逐层深入见 [DIA 框架详解](../15-DIA框架详解/00-架构总览.md)，
执行节奏见 [实践 · 首个 120 天](../20-实践/02-首个120天.md)。

## 5.2 在范式版图中的位置 {#52}

### 与主要范式的关系

| 范式 | 关系 | 关键差异 |
|---|---|---|
| **Palantir Foundry/AIP** | 同一象限，思想来源 | 借鉴其 **semantic + kinetic 两分法**内核（`P1`；本站此前误写为「semantic-kinetic-dynamic 三层」，已更正）；**不照搬**重服务模式、全平台锁定、全企业本体优先 |
| **Data Mesh** | 互补 | 解决「谁负责数据」；止于数据供给，不涉及行动闭环 |
| **Lakehouse** | 底座 | 解决存储与计算，**不解决语义** |
| **语义层 / 指标平台** | 本体层的子集 | 管指标口径；**没有行动的语义层是 BI 的延伸** |
| **知识图谱** | 技术手段之一 | 面向检索推理、只读；本体必须可执行、承载权限 |
| **MDM 主数据** | 前置能力 | MDM 是**名词的正确性**；本体是**名词 + 动词 + 权限的完整性** |
| **RPA / 工作流** | 行动层的实现手段 | RPA 自动化已确定的流程；本架构自动化**决策本身** |
| **Agent 框架** | 智能层的实现工具 | 框架解决编排；**Agent 的能力边界应由本体决定，而不是由框架能力决定** |

### 相对 Palantir 的补充

**〔判断〕** 这一节此前的叙事是「Palantir 三层回答了『是什么』，我补上『怎么跑起来』」。**这个对照的前提有两处错，已更正：**

1. **不存在 semantic-kinetic-dynamic 三层**，官方是两分法（`P1`）。
2. **「工程细节公开材料里基本没有」是错的**——Palantir 文档逐条覆盖了参数校验、撤销回退、审批链（Ontology proposals，官方类比 Pull Request）、权限传播、幂等、时点正确、本体分支（`P4`）。

**站得住的对照是**：Palantir 把这些作为**Foundry 的产品特性**文档化，而不是作为一套**可迁移到任意技术栈的工程方法论**。对不采用 Foundry 的企业，那些文档的可移植价值有限。本框架试图提供的是后者。

在这个前提下，本框架相对公开材料补上的是：

| 补充 | 解决什么 |
|---|---|
| 对象准入五判据 | 本体膨胀 |
| 业务 Owner 制度 | 本体腐化 |
| **行动十一要素契约** | 让 kinetic 层能真正上生产 |
| **可逆性分级 + 人闸** | 「敢不敢开权限」这个真问题 |
| 分级自治 L0–L4 | dynamic 层的放权依据 |
| 四条横切约束 | 权限传播（含无人值守身份）、证据链、失败关闭、运行 |
| 组织承接 | 人机权责 + 被取消的旧动作 |

> **Palantir 提供的是一个产品里的实现；本框架试图提供的是一套不绑定产品的工程纪律。**
> 这个定位比原来的「它回答是什么、我回答怎么做」诚实，也更站得住。

完整对照见 [研究 · 坐标系](../40-参考/01-坐标系.md)。

## 5.3 未解问题与研究方向 {#53}

**〔判断〕** 一份不列出自己盲区的方法论总结，是不可信的。以下是我认为这个领域尚无好答案的问题。

### 已有明确分歧的问题〔争议〕

**① 编排范式的边界在哪**
确定性工作流 vs 自主 Agent，两派都能举出成功与失败案例。目前没有可操作的判别标准，多数团队靠试错。（我的暂定立场见 [模块三 3.3](03-模块三-Agentic系统设计与编排.md)：控制流确定性，判断交给模型。）

**② 生成式系统的评测方法论尚未成熟**
LLM-as-Judge 与人工判断的一致性因任务而异；离线评测与在线表现的相关性弱。**目前没有一个企业敢说自己的评测体系是充分的。**

**③ 本体的构建应该多自动化**
用 LLM 从数据库 schema 自动生成本体的尝试很多，但生成的是「数据模型的镜像」，不是业务语义。自动化与「业务承认」之间的矛盾没有解决。

### 缺少数据的问题

**④ 本体的「复利」从第几个场景开始显现？**
增量派的核心论据是复用，但复用率随场景数增长的曲线形态，没有公开数据。这是我最想研究的一个问题。

**⑤ M1 → M2 的真实成本**
组织层面的口径裁决权分配，需要多长时间、多高层级的推动，没有可参考的基准。国内企业的起点普遍低于欧美，成本差异有多大也不清楚。

**⑥ 弃权率的合理区间**
过低说明系统不知道自己不知道，过高说明没有价值。中间区间在哪里，取决于什么，没有答案。

### 我认为会成为焦点的问题

**⑦ 责任分配的法律与制度形态**
「担责者永远是人」目前是一条工程原则，但当自动执行规模扩大后，它需要制度化的支撑（岗位定义、保险、审计标准）。目前完全空白。

**⑧ 组织记忆的表达形式**
「这个供应商经常延迟」这类经验，应当沉淀为本体属性还是留在记忆库里？前者可审计但笨重，后者灵活但不可查。这个权衡还没有共识。

**⑨ 多 Agent 系统的审计**
单 Agent 的证据链已经清楚。当多个 Agent 协作时，「谁做的决定」变得难以回答。企业级的多体审计方法基本没有。

## 总结全文的三句话

**〔判断〕**

1. **企业 AI 的瓶颈不是模型，是企业没有一层机器可理解、且业务承认的语义骨架。**
2. **只读的智能存在价值上限；价值发生在写回，而写回的门槛是治理，不是技术。**
3. **自主不是能力描述，是授权描述；放权的依据是可逆性与证据，不是准确率与信心。**
