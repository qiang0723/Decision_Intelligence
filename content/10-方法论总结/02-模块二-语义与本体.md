## 2.1 本体是什么、不是什么 {#21}

### 定义

**〔共识〕** 知识工程中的标准定义来自 Gruber：本体是「**概念化的显式规范**」（an explicit specification of a conceptualization）——有哪些实体、它们的属性与关系。OWL/RDF 传统沿用这一定义。

**〔判断〕** 这个标准定义没有缺陷，**但它服务的是知识表达与推理，不服务于企业决策执行**。本方法论使用的是厂商语境下的、有意偏离标准的用法：

> 本体是企业的**可执行语义层**——它不仅描述企业由什么构成，还定义了**能对它做什么**，并承载权限。

差别在于最后半句。一个只描述不执行的本体，无法解决 [模块一](01-模块一-基础认知.md) 中「只读陷阱」的问题。

> **术语提示**：本站说「本体」时指的是**可执行语义层**，与 Gruber/OWL 传统的 ontology 不是同一个概念。这是有意的偏离，不是对标准定义的修正。与知识工程背景的同事讨论时，这个歧义需要先说明。

### 三个常见误解

| 误解 | 区别 |
|---|---|
| **本体 = 数据模型** | 数据模型服务于存储与事务效率；本体服务于业务语义与决策。数据模型里没有「这个客户处于流失预警状态」这种东西 |
| **本体 = 知识图谱** | 图谱通常只读、面向检索与推理；本体必须绑定行动，是可执行的 |
| **本体 = 元数据目录** | 目录描述「有哪些表和字段」，服务于找数据；本体描述「这家企业由什么构成」，服务于做决定 |

一句话区分：

> 数据模型回答「怎么存」，知识图谱回答「知道什么」，元数据目录回答「在哪找」，
> **本体回答「这家企业是什么，以及能对它做什么」。**

### 为什么它必须在架构中心

**〔判断〕** 一旦本体只是「一个可选的语义层」，就会立刻出现绕过它的捷径：报表直连数据库、Agent 写自由 SQL、前端硬编码业务公式。三个月后企业就有了第二套、第三套口径，本体退化成文档。

架构判据只有一条：

> **除本体外，不存在第二条通往业务语义的路径。**

## 2.2 三种本体范式对照 {#22}

**〔共识〕** 目前有三条主流路线，各自来自不同的传统。它们不是互斥的，但侧重点差别很大。

### 范式一：语义-动能-智能（Palantir 路线）

Palantir 的官方表述把本体分为三层：

> ⚠️ **本站曾在此处写错，2026-08-23 更正。**
> 此前本站写「Palantir 官方的本体表述是三层：Semantic / Kinetic / **Dynamic（绑定到对象上的模型）**」。
> **官方没有 Dynamic 层。**该三层说法出自第三方博客转述，本站未经核实即采用，并据此给转述来源打了高分——这是「用二手材料做一手判断」的典型代价。更正说明见 [参考站调研](../40-参考/03-参考站调研-RebootingWithAI.md)。

**官方表述是两分法**（`P1`）：

| 元素 | 内容 |
|---|---|
| **Semantic elements**（语义 / 名词） | objects、properties、links |
| **Kinetic elements**（动能 / 动词） | actions、functions、**dynamic security** |

关键点：**"dynamic" 指的是 dynamic security**——运行时计算的细粒度权限策略，是 kinetic 的**子项**，讲的是**权限，不是模型**。

名词—动词的比喻是官方自己的说法（`P2`）："Data elements are the nouns… actions are the verbs"。「组织的数字孪生」也是官方表述（`P3`，原文为 digital twin of the organization）。

- **强项**：**〔判断〕**（原标〔共识〕，已降级）把「行动」作为本体一等公民、并让权限沿语义传播，这个组合抓住了要害。
  > 此前本站写它是「**唯一一个**」这么做的主流范式——这可被证伪：Microsoft Fabric IQ Ontology、AWS 的 ontology + 推理指引、SHACL/SWRL、agentic MDM 都在做同一件事。「唯一」已删除。
- **弱项**：**〔判断〕** 它是**产品文档，不是可迁移的工程方法论**。
  > ⚠️ 此前本站写「幂等、参数边界、可逆性、审批链、权限传播、时点正确性……这些**公开材料里基本没有**」——**这是错的，且是明显的稻草人化**。Palantir 公开文档逐条覆盖（`P4`）：参数校验（Action rules / submission criteria）、撤销与回退（Undo or revert Actions）、**审批链**（Ontology proposals，官方明确类比 Pull Request 的评审与批准流程）、权限传播（markings 沿数据管线传播）、幂等（推荐幂等操作并定义并发冲突失败语义）、时点正确（time-series 属性与 edits history）、本体分支与版本。
  > **站得住的说法是**：Palantir 把这些**作为 Foundry 的产品特性**记录在文档里，而不是作为一套**可迁移到任意技术栈的工程方法论**；对不采用 Foundry 的企业，这些文档的可移植价值有限。
- **当前形态**：**〔判断〕** 本站此前把 Palantir 描述成一个静态概念框架，落后于实际。Ontology 现同为 Foundry 与 AIP 的核心，且已有 Ontology SDK / Platform SDK / **Palantir MCP**（Agent 访问通道）/ AIP Analyst / AIP Autopilot（`P5`）。
- **真正的洞察**：**〔判断〕** 多数人以为 Palantir 卖的是数据整合。它实际卖的是——**让「分析」和「操作」发生在同一个语义空间里**。你在看板上看到的那个订单，就是你能直接操作的那个订单，权限、审计、回滚一并跟着。

### 范式二：指标语义层（数据工程路线）

代表：dbt Semantic Layer、Cube、各类指标平台。

- 核心主张：把指标定义从报表里抽出来，集中管理，保证口径唯一
- **强项**：**〔判断〕** 工程成熟、落地成本相对低、与现有数据栈衔接顺畅（「成本低」是比较级评价，此前误标〔共识〕）
- **弱项**：**〔判断〕** 只管「数字」，不管「对象、关系、状态、行动」。它能让你不吵口径，不能让系统做决定。**没有行动的语义层是 BI 的延伸**

### 范式三：企业知识图谱（知识工程路线）

代表：各类企业 KG、图数据库方案。

- 核心主张：用图结构表达实体与复杂关系，支持推理与检索
- **强项**：**〔判断〕** 关系表达能力强，适合多跳查询与关联发现（「最强」是比较级评价，此前误标〔共识〕）
- **⚠️ 现状更新**（`A8`）：**微软已于 2026-08-14 将 GraphRAG 转入维护模式**（不再接受新 PR、不再实现新功能），理由是前沿模型能力已变；**LazyGraphRAG 从未在开源版发布**。GraphRAG-Bench（ICLR 2026）的量化决策规则：简单事实检索 文本 60.9 vs 图 60.1（打平）；复杂推理 图 **+10.5**；上下文摘要 图 **+13.1**；代价是 **3–5 倍索引成本**
- **弱项**：**〔判断〕** 传统 KG 是只读的、面向认知的。它回答「知道什么」，不回答「能做什么」。落到企业决策，还差行动与权限两层

### 对照表

| 维度 | 语义 + 动能（Palantir 路线） | 指标语义层 | 知识图谱 |
|---|---|---|---|
| 主要表达 | 对象 + 行动 + 权限 | 指标与维度 | 实体 + 关系 |
| 绑定行动 | ✅ 核心 | ❌ | ❌ 通常不 |
| 承载权限 | ✅ | 部分 | 通常不 |
| 状态机 | ✅ | ❌ | 部分 |
| 落地成本 | 高 | 低 | 中 |
| 成熟工具 | 少（多为商业平台） | 多 | 多 |
| 适合起点 | 有行动闭环诉求 | 先解决口径战争 | 关系密集型业务 |

**〔判断〕** 三者不是选一个。现实中合理的组合是：

> **以语义-动能-智能为架构目标，用指标语义层解决口径唯一，用图结构承载复杂关系。**
>
> 但必须明确：只有第一条路线是终点，另外两条是手段。把手段当终点，就会停在「不吵口径的 BI」或「查得很爽的知识库」。

## 2.3 本体的六个构成要素 {#23}

**〔共识〕** 无论哪条范式，一个可用于决策的本体大致由六类要素构成。

### 2.3.1 对象类型（Object Type）
企业中的核心名词：客户、订单、SKU、门店、仓库、供应商、工单、合同、员工、需求、事故、服务。

### 2.3.2 属性（Property）
必须区分三类，混淆会直接导致口径失控：

| 类型 | 说明 | 关键约束 |
|---|---|---|
| **源属性** | 直接来自权威系统 | 指明源系统与字段 |
| **派生属性** | 由计算得出（LTV、毛利） | **只能有一个权威实现** |
| **状态属性** | 生命周期状态 | **必须有明确的状态机** |

### 2.3.3 关系（Link）
对象之间的连接。

**〔判断〕** 关系是本体相对于数据表最大的价值：它把跨系统的语义缝合起来。一条跨七个系统的订单履约链路，在本体里是一条可遍历的关系路径，而在数据仓库里是七次 JOIN 加三次人工确认。

### 2.3.4 事件（Event）
发生了什么，带时间戳且不可变：下单、发货、退款、告警、审批通过、价格变更。

事件是重放、审计与时点正确性的载体。

### 2.3.5 指标（Metric）
业务度量。**〔共识〕** 每个指标只允许一个权威实现，有唯一 Owner；查询层只做只读投影。

**〔判断〕** 最常见的破口是「Agent 提示词里重新拼公式」——这和在报表里重算是同一类错误，但更隐蔽，因为它不在任何代码评审的视野里。

### 2.3.6 行动（Action）
可以改变企业状态的操作。**行动绑定在对象上**——不是「系统能调价」，而是「SKU 对象上有一个调价行动」。

**〔判断〕** 这个绑定关系不是设计上的优雅，而是**权限与自治能够被精确表达的前提**。绑定之后，下面这些问题才有答案：谁能对哪些 SKU 调价？Agent 能调多大幅度？上周那次调价依据什么？能撤销吗？

行动的完整契约见 [模块四 4.1](04-模块四-行动闭环与企业采纳.md)。

## 2.4 对象准入判据与本体膨胀 {#24}

### 最常见的失败模式

**〔判断〕**（原标〔共识〕，因无出处已降级）本体建设最普遍的失败是**范围失控**：建设周期长期拖延而迟迟不上线，或者「有 300 张表就建 300 个对象」。

> 此前本站在此写「建了 **12–18 个月**还没上线」。这个数字没有出处，是我的经验印象，**已改为定性表述**。相关的、有出处的数字是 `E6`：原型到生产平均 **8 个月**，仅 **48%** 进入生产。

**〔判断〕** 根因是缺少准入闸门。任何没有准入判据的建模活动，都会自然膨胀——因为每个业务方都能说出「我们这个也很重要」。

### 五条准入判据

一个候选对象必须**同时**满足五条，否则不予纳入：

| # | 判据 | 不满足的后果 |
|---|---|---|
| 1 | **有唯一真身**：权威源系统 + 主键 | 出现多个版本的「客户」，口径战争 |
| 2 | **有稳定标识**：跨系统 ID 映射规则明确，含历史变更 | 关系连不起来，数据看着有其实用不了 |
| 3 | **有明确生命周期**：状态集合与合法转移已定义 | 行动的前置条件无法表达 |
| 4 | **有绑定行动或明确决策用途** | **本体膨胀** |
| 5 | **有业务 Owner**：一个具体的人，不是一个部门 | 变更无人裁决，本体腐化 |

**〔判断〕** 判据 4 是最常被跳过、也最致命的一条——它是防止膨胀的唯一闸门。

### 从决策倒推，不做全企业本体

**〔争议〕** 这是本领域一个真实分歧：

- **全景派**：先建完整的企业本体，再谈应用。理由是避免重复返工、保证一致性
- **增量派**：从一个决策倒推，只建它需要的对象，逐步生长

**〔判断〕** 我站增量派，理由不是技术而是组织：全景本体要很久才有第一个业务结果，而 `E3` 显示 42% 的企业已经放弃了多数 AI 计划、平均报废 46% 的 PoC——**耐心额度是真实且有限的约束**。而增量派的返工风险，可以通过「第二个场景刻意复用第一个场景的对象」来检验和控制。

```
选定一个决策
   ↓
做这个决策需要知道哪些东西？   → 对象（3–7 个）
它们之间是什么关系？           → 关系
决策依据哪几个数？             → 指标
决策的结果是对什么做什么？      → 行动
   ↓
只建这些。其余一概不建。
```

健康的第一版规模：**5 个以内对象，3 个以内关系，1 个行动。**

### 本体是产品，不是项目产物

**〔判断〕** 一旦本体成为企业语义权威，它必须具备产品的全部特征：版本、合同、变更流程、废弃策略、Owner、业务语言的文档。

> **没有变更流程的本体，会在六个月内退化成一份没人看的文档。**

### 权限沿本体传播

**〔共识〕** 权限应当定义在语义层而非接口层。四个维度：对象级、行级、属性级、行动级。

**〔判断〕** 最关键的一条规则是：**Agent 继承调用者权限，不存在超级 AI 身份。**

销售 A 通过 Agent 查询时，Agent 看到的必须恰好是销售 A 能看到的那个世界。这条如果破了，整个系统在合规上不可用——而且泄漏不会触发任何传统安全告警。

## 2.5 事实基础：口径、血缘、时点正确性 {#25}

本体是语义骨架，事实层是它的地基。**〔共识〕** 三个必须：

### 必须一：口径权威唯一

同一度量全企业只有一个权威计算实现，有唯一 Owner；查询层、报表、前端、Agent 提示词一律只做只读投影。

**〔判断〕** 发现第二处实现应按**缺陷**处理，不按「灵活性」处理。这是一个组织决定，不是技术决定。

### 必须二：血缘可追

任何数字能在 5 分钟内回答：来自哪个源、经过什么加工、什么口径版本、数据时点、上次成功更新时间。

**〔判断〕** 血缘必须是**可查询的运行时元数据**，不是一张架构图。画在 PPT 上的血缘，在事故排查时没有任何用处。

### 必须三：时点正确（Point-in-Time）

**〔判断〕** 这是企业里最容易被忽略、也最容易造成静默错误的一条，而且在 Agentic 时代危害被放大——因为系统会基于污染的历史评估自动放权。

典型错误：用**今天**的主数据解释**昨天**的业务。

| 错误 | 后果 |
|---|---|
| 用今天的客户分级分析上季度转化 | 结论被未来信息污染 |
| 用今天的类目回溯半年前的品类表现 | 类目调整过，对不上 |
| 用今天的组织架构归因去年业绩 | 人员已换部门 |
| 用修正后的财报评估当时的判断 | 高估了当时的可判断性 |

实现要点：主数据保留**有效期区间**；事实记录保留**双时间轴**（业务发生时间 + 系统可知时间）；回溯查询必须显式指定「以哪个时点的认知为准」。

> **时点错误的可怕之处在于：它不报错。**
> 系统会给你一个看起来完全正常、并且偏乐观的数字，直到上线后效果对不上。

### 一个唯一权威 Owner 在集团型企业里如何成立

**〔判断〕** 「一个指标一个权威 Owner」这条规则在单一法人主体内很直接，在**集团—事业部—区域**三级结构里会立刻被追问。这是大型客户的第一个问题，本站此前完全没有回答。

可用的处理方式（择一，需在项目开始时明确）：

| 模式 | 规则 | 适用 |
|---|---|---|
| **集团定义 + 事业部实例化** | 集团定义指标的**语义与计算口径**，事业部只能定义**过滤范围**（我的区域/我的品类），不得改公式 | 集团要求横向可比 |
| **分层指标** | 同名指标显式分为 `集团口径` 与 `事业部口径` 两个**不同的指标**，各有 Owner，禁止混用 | 两级确有不同的管理需要 |
| **联邦式**（借鉴 Data Mesh 第四原则 `M1`） | 集团只定义**元规则**（必须有 Owner、必须可追溯、变更必须通知），具体口径下放 | 事业部差异极大、集团管控弱 |

**不可接受的做法**：不做选择、让同名指标在各层自然分叉。这就是口径战争的起点。

**跨法人主体的额外约束**：数据能否跨主体流动是**法律问题不是技术问题**，必须先于本体设计确认。见 [合规与安全前置](../20-实践/07-合规与安全前置.md)。

## 2.6 数据合同与断言校验 {#26}

### 数据合同（Data Contract）

**〔判断〕**（原标〔共识〕，已降级）上游变更不能静默破坏下游，这个**原则**争议不大；但「数据合同」作为具体实践在 2026 年仍是少数派，远未成为定论（`D8`：该词 2022-08 才被推起来）。一份数据合同包含：

| 项 | 内容 |
|---|---|
| Schema | 字段、类型、可空性 |
| **语义** | 每个字段的业务含义与枚举值含义（`status=3` 是什么） |
| 质量承诺 | 完整性、及时性、唯一性的可度量承诺 |
| 变更流程 | 提前通知期、兼容期、迁移路径 |
| Owner | 上游负责人，具体到人 |
| **违约处理** | 合同被破坏时下游的行为 |

**〔判断〕** 最后一项最常被省略，也最重要。没有定义违约行为的合同，在被违反时只会产生一场会议，不会产生任何自动保护。

### 断言式校验

在数据进入本体之前跑一组自动断言，每条输出 PASS / FAIL + 异常清单。

**〔判断〕** 设计原则是**不抽样看趋势，而是对账**。抽样监控能发现「数据变化了」，发现不了「数据一直是错的」。

| 类型 | 例子 |
|---|---|
| **完整性对账** | 应有记录数 − 实际记录数 = 已归因缺失数（差额必须为 0） |
| **量纲断言** | 金额/数量比值落在合理区间——防止差 100 倍的静默错误 |
| **双算校验** | 关键派生量用两条独立实现各算一遍并比对 |
| 唯一性 / 参照完整性 | 主键唯一；订单引用的客户必须存在 |
| 枚举合法性 | 状态值必须在已定义集合内 |
| 时序逻辑 | 发货时间 ≥ 下单时间；状态转移合法 |
| 跨源交叉 | 与独立数据源比对，偏差超阈值报警 |

**〔判断〕** 量纲断言与双算校验是投入产出比最高的两条——它们抓的是「看起来完全正常」的那一类错误，恰恰是最贵的那一类。

### 失败关闭

**〔判断〕** 断言 FAIL 的默认行为必须是**阻断下游，不出结论**，而不是「告警后继续」。

这一原则贯穿整个架构，在 [模块四 4.4](04-模块四-行动闭环与企业采纳.md) 展开。

### 不可变 + 可重放

**〔共识〕** 原始数据只增不改，修正通过新增记录表达；给定代码版本 + 数据版本能重算出完全相同的结果。

没有这两点，永远无法回答「三周前它为什么给出那个建议」。
