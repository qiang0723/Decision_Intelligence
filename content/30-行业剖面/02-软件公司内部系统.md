# 行业剖面｜软件公司内部系统

> 这是一个特殊的场景：**你的客户就是你自己**。
> 优点是决策链短、可以快速迭代；缺点是容易变成技术自嗨，没有真实的业务纪律约束。

---

## 为什么值得做

三个理由：

1. **最好的第一个客户**：可以在自己身上把整套方法论跑通，产出真实证据。
2. **决策链短**：不需要说服采购委员会，能验证「组织承接」这一环。
3. **可对外复制**：软件公司的内部管理问题（需求交付、事故响应、客户健康度）在同行里高度同构。

但要警惕一个陷阱：**在自己公司做，最容易跳过治理**（反正都是自己人）。而治理恰恰是这套方法论的价值所在。所以在内部做时，要**刻意保持外部项目的纪律**——同样的决策卡、同样的评测集、同样的证据链。否则做出来的东西无法对外复制。

---

## 四个价值域与决策清单

### 域一｜需求到交付的价值流

| 决策 | 决策者 | 频次 | 落点 | 可逆 |
|---|---|---|---|---|
| ★ **这个需求进不进本迭代** | PM/TL | 每周 | 更新迭代计划 | R1 |
| ★ **这个 PR 该谁 review** | 系统/TL | 每日数十 | 指派 reviewer | R1 |
| **这个需求的工作量估计** | TL | 每周 | 更新工时估算 | R1 |
| **这个迭代能不能按时交付** | PM | 每周 | 发出风险预警 | R1 |
| **要不要拆分这个需求** | PM/TL | 每周 | 拆分工单 | R1 |

这一域几乎全是 R1，是**最安全的起步区**。

### 域二｜事故与稳定性

| 决策 | 决策者 | 频次 | 落点 | 可逆 |
|---|---|---|---|---|
| ★ **这个告警要不要升级为事故** | 值班 | 每日 | 创建/升级事故单 | R2 |
| ★ **这个事故该找谁** | 值班 | 每次事故 | 指派责任人 | R1 |
| **这次变更风险有多高，要不要灰度** | 发布负责人 | 每次发布 | 调整发布策略 | R2 |
| **要不要回滚** | 值班 | 事故中 | 触发回滚 | R2 |
| 是否对外发布故障公告 | 负责人 | 低频 | 发布公告 | **R3** |

告警分级是**投入产出比最高的第一个场景**：高频、可逆、痛感强、效果立刻可见。

### 域三｜客户健康度与交付质量

| 决策 | 决策者 | 频次 | 落点 | 可逆 |
|---|---|---|---|---|
| **这个客户是否有流失风险，要不要介入** | 客户成功 | 每周 | 创建跟进任务 | R1 |
| **这个客户的工单是否需要升级** | 支持 | 每日 | 升级工单 | R1 |
| **交付项目是否偏离，要不要预警** | 交付经理 | 每周 | 发出预警 | R1 |
| 是否接受这个定制需求 | 销售/产品 | 每周 | 更新报价/排期 | R2 |

### 域四｜知识与代码资产

| 决策 | 决策者 | 频次 | 落点 | 可逆 |
|---|---|---|---|---|
| **这段代码/模块是否需要重构** | TL | 每月 | 创建技术债工单 | R1 |
| **这个问题的答案在哪个文档里** | 全员 | 每日 | 返回引用 | R1（只读） |
| **新人这周该看什么** | TL | 每周 | 生成学习路径 | R1 |

> 注意：域四中的「知识问答」是**唯一适合对话式界面**的场景（探索性）。
> 其余三个域都应该嵌入现有工作流（工单系统、IM、CI/CD），不要做成聊天。

## 本体草图

```
   ┌────────┐        ┌────────┐        ┌────────┐
   │  客户   │──有──▶│  项目   │──含──▶│  需求   │
   └────────┘        └───┬────┘        └───┬────┘
                         │                 │ 实现为
                         │                 ▼
                    ┌────▼────┐       ┌─────────┐
                    │  工单    │       │ 代码变更 │
                    └────┬────┘       └────┬────┘
                         │                 │ 部署为
                    ┌────▼────┐       ┌────▼────┐
                    │  事故    │◀─关联─│  服务    │
                    └─────────┘       └─────────┘
                         │
                         ▼
                    ┌─────────┐
                    │   人员   │
                    └─────────┘
```

**关键陷阱**

| 对象 | 陷阱 |
|---|---|
| **需求** | 需求在 PRD、Jira、代码 commit、发布说明里是四个不同的东西。标识映射是主要工作量 |
| **人员** | 组织架构会变。评估历史绩效必须用**当时**的归属（时点正确性） |
| **服务** | 服务拓扑随时间变化，事故归因要用当时的拓扑 |
| **客户** | 销售视角的客户 ≠ 交付视角的项目 ≠ 支持视角的账号 |

## 推荐的第一个场景：告警分级与责任人指派

**为什么是它**

- 高频（每天几十到几百）
- R1/R2 可逆
- 有明确 Owner（值班负责人）
- 有现成落点（事故/工单系统）
- 痛感强（误报疲劳是所有团队的共同痛点）
- 数据现成（告警历史 + 处理记录 = 天然的金标准集）

**最后一点尤其宝贵**：历史处理记录直接构成评测集，不需要额外标注。这在其他行业是很奢侈的条件。

**推进节奏**

| 阶段 | 自治级别 | 内容 |
|---|---|---|
| 第 1–2 周 | L0 | 只做分析，输出告警聚类与历史模式 |
| 第 3–6 周 | L1 | 给出分级建议与责任人建议，人工决定 |
| 第 7–10 周 | L2 | 自动生成事故单草稿，值班一键确认 |
| 第 11 周+ | L3 | 低级别告警自动归档/自动指派，高级别升级人工。**必须先定岗位委托身份**：以「值班岗」的身份运行，权限等于值班人员的人工权限，岗位空缺则降级 L2（见 [模块四 4.4b](../10-方法论总结/04-模块四-行动闭环与企业采纳.md)） |

**被取消的旧动作**：值班人员逐条人工浏览告警列表并判断的动作。

## 特别提醒：不要跳过治理

在自己公司做，最容易出现的三个偷懒：

| 偷懒 | 后果 |
|---|---|
| 「都是自己人，权限就不做了」 | 无法对外复制；且薪酬、客户合同等敏感数据会泄漏 |
| 「效果我们自己看得出来，不做评测集了」 | 无法证明价值，也无法回答客户「你们怎么验证的」 |
| 「改个提示词而已，直接上」 | 与外部项目相同的事故来源 |
| 「自己人，自动执行不用定身份」 | L3 一上线就是无主自动执行；对外复制时这一段要重做 |

> 内部项目的真正价值，不是省下的那点人力，而是**产出一个可对外展示的、完整的方法论证据**。
> 偷掉治理，就偷掉了这个价值的全部。
