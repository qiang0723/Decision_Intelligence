# A｜行动层 Action Layer

> 核心问题：**这个系统被允许改变什么？**
> 这是分隔「会说话的看板」与「决策智能平台」的那条线。

---

## 1. 行动是一等公民

在传统数据架构里，「写回」是一个边缘功能。在决策智能架构里，**行动是本体的一部分**，与对象、属性同等重要。

原因见 [核心命题二](../00-立场/01-核心命题.md)：只读的智能存在价值上限。

设计上的体现：行动不是「一个 API」，而是**绑定在本体对象上的、有完整契约的操作**。不是「系统能调价」，而是「SKU 对象上有一个 `调整售价` 行动」。

这一绑定使得下面这些问题可以被精确回答：

- 谁能对哪些 SKU 调价？（对象级 + 行级权限）
- Agent 能不能调价？能调多大幅度？（行动级权限 + 参数约束）
- 上周那次调价是谁触发的、依据什么？（证据链）
- 能撤销吗？（可逆性）

## 2. 行动契约：十一个必备要素

> **2026-08-23 更新**（与 [模块四 4.1](../10-方法论总结/04-模块四-行动闭环与企业采纳.md) 同步）：补第 10「频次上限 / 速率限制」与第 11「数据依赖与新鲜度」。
> 前者是本站自己在 [电商剖面](../30-行业剖面/01-电商.md) 诊断出的薅羊毛事故根因，却一直没在契约里留位置；后者缺失导致「数据缺失则失败关闭」在运行时无从判定。

一个行动在进入生产前，必须完整定义以下九项。缺任何一项都不允许上线。

| # | 要素 | 说明 |
|---|---|---|
| **1** | **前置条件** | 什么状态下允许执行。用本体的状态机表达，如「订单状态 ∈ {待发货}」 |
| **2** | **参数模式** | 输入的结构、类型、取值范围。**范围约束是安全边界**，如调价幅度 ∈ [-15%, +15%] |
| **3** | **权限** | 人工触发时继承调用者身份；**自动执行时以担责岗位的委托身份运行**（见 [模块四 4.4b](../10-方法论总结/04-模块四-行动闭环与企业采纳.md)）。禁止使用权限大于担责人的自动执行身份 |
| **4** | **副作用** | 会改变哪些对象的哪些状态，会触发哪些下游 |
| **5** | **幂等键** | 重复执行必须不产生重复效果。分布式环境下这是硬需求 |
| **6** | **可逆性** | 可撤销 / 可补偿 / 不可逆（见下节） |
| **7** | **审批链** | 需要谁批准，什么条件下免批 |
| **8** | **审计记录** | 触发者、时间、参数、依据、结果、关联的决策与模型版本 |
| **9** | **失败语义** | 失败时的状态如何、是否重试、是否需人工介入 |
| **10** | **频次上限 / 速率限制** | 按对象、按执行者、按全局分别设限。**参数范围管单次幅度，管不了「一天 5000 次，每次都在范围内」** |
| **11** | **数据依赖与新鲜度** | 本行动依赖哪些对象/指标、要求多新的数据。没有它，「数据缺失则失败关闭」无从判定 |
| **10** | **频次上限 / 速率限制** | 按对象、按执行者、按全局分别设限。**参数范围管单次幅度，管不了「一天 5000 次，每次都在范围内」** |
| **11** | **数据依赖与新鲜度** | 本行动依赖哪些对象/指标、要求多新的数据。没有它，「数据缺失则失败关闭」无从判定 |

模板见 [模板库](../20-实践/04-模板库.md#行动契约)。

## 3. 可逆性分级

这是整套架构中**授权决策的核心依据**。

| 级别 | 定义 | 例子 | 授权取向 |
|---|---|---|---|
| **R1 可撤销** | 一键回到原状态，无外部影响 | 修改内部标签、调整优先级、更新预测 | 可较早开放自动执行 |
| **R2 可补偿** | 不能直接撤销，但有明确的反向操作 | 调价（可再改回）、创建工单（可关闭）、库存调拨（可再调回） | 限额内自动，超限需审批 |
| **R3 不可逆** | 一旦执行，外部世界已改变 | 已发货、已付款、已发送客户通知、已提交监管报送 | **永远需要人** |

> **〔争议〕2026-08-23 更正。**此前本站写「R3 永远需要人闸，不可协商」。
> **这作为对现实的描述是错的**：程序化广告、算法交易、自动放款与扣款、自动触达、自动物流调度——大量 R3 行动今天就在全自动执行，通行做法是**限额 + 速率限制 + 熔断 + 事后补偿 + 保险**，不是人闸。本站自己在电商剖面也写了「小额退款自动」，那本来就是一个例外。
>
> **修正后的规则**（更有力，因为它说清了真正要守的是「可承担的损失上界」，而不是「必须有人点确认」）：
>
> **R3 开放自动执行需同时满足四条：**
> 1. 单次影响有硬上限
> 2. 单位时间总量有硬上限（对应第 10 要素）
> 3. 有可执行的事后补偿路径（已实现并演练过，不是理论上可补偿）
> 4. 有实时异常熔断，以及一个具名担责人
>
> **四者缺一，即保留人闸。**

### 一个重要的设计技巧：把 R3 拆成 R2 + R3

很多看似不可逆的动作，可以被拆解：

```
「自动发货」        = R3，不能自动
拆解后：
「自动创建发货单」   = R2（可作废）      → 可以自动
「确认发货」        = R3（不可逆）      → 保留人闸，一键确认
```

这样 AI 承担了 95% 的工作量，人只保留最后那个不可逆的确认动作。**这是企业 AI 落地最实用的一个模式。**

## 4. 写回原则：不要制造第二套真相

**行动必须写回权威系统**（ERP、OMS、WMS、CRM），而不是只写在平台内部。

如果平台自己存了一份「我们认为的库存」，而 ERP 里是另一份，那么企业就有了两套真相。这比没有 AI 更糟：

- 对账工作量增加
- 出问题时无法定位哪一套对
- 业务方会自然地相信旧系统，新系统被架空

**判据**：关掉这个 AI 平台，企业的业务数据是否完全不受影响？
- 是 → 写回设计正确（平台是决策者与执行者，不是记录者）
- 否 → 制造了第二套真相，必须重构

例外：平台可以保留**决策记录与证据链**（谁在什么时候基于什么做了什么决定）。这部分是平台独有的、有价值的资产，不与业务系统冲突。

## 5. 审批链设计

审批不是「加一个审批环节」，而是按风险动态确定的。

推荐模式——**按金额/影响面/偏离度三档**：

```
条件                                     处理
─────────────────────────────────────────────────────
在历史正常区间内 + 影响面小 + R1/R2      →  自动执行，事后可查
超出正常区间 或 影响面中等               →  单人审批（决策者本人一键确认）
超出硬阈值 或 影响面大 或 R3            →  多级审批 / 强制人工
异常：数据缺失、口径不明、置信度低       →  失败关闭，不执行，报告原因
```

**关键设计**：最后一行。系统在不确定时的默认行为必须是**不动作 + 明确报告**，而不是「按最佳猜测执行」。见 [四条横切约束 · 失败关闭](07-四条横切约束.md)。

## 6. 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 行动没有幂等键 | 重试导致重复下单、重复调价 | 幂等键是必填项，不是优化项 |
| **没有频次上限** | 每次都在参数范围内，但一天调用五千次——薅羊毛与失控循环的形态 | 第 10 要素必填 |
| 参数没有范围约束 | 一个小数点错误导致调价 100 倍 | 范围约束是安全边界，必须在契约里 |
| 审批链写死在代码里 | 业务规则变更要发版 | 审批规则配置化 |
| 平台自己存业务状态 | 第二套真相 | 写回权威系统 |
| 只记录成功的行动 | 无法排查「为什么它没做」 | 拒绝、失败、跳过同样入审计 |
| R3 行动在不满足四条件时开放自动 | 一次事故毁掉整个项目的信任 | 四条件缺一即保留人闸 |

## 7. 检验

1. 每个行动是否都有完整的十一要素契约？
2. 关掉平台，业务数据是否完全不受影响？
3. 开放为自动的 R3 行动，是否 100% 满足四条件（单次上限、总量上限、已演练的补偿路径、熔断 + 具名担责人）？
4. 系统在数据缺失时的默认行为是「不动作」还是「按猜测执行」？
5. 能否查到上周某一次自动执行的完整依据链（输入、口径版本、模型版本、触发者、**自动执行时用的是谁的委托身份**）？
