# 决策智能架构（DIA）总览

> **Decision Intelligence Architecture**
> 以本体为中心的企业 AI 落地架构。
>
> 记忆锚点：**一个中心，两个方向，四条约束。**
>
> **2026-08-23 重构。**此前是「六层 + 三条约束」。外部审查指出三处交叉重叠：
> ① **权限出现在三个地方**（本体层、运行层、约束一），读者不知道该在哪一层做设计；
> ② **R 运行层本质是第四条横切约束，被误画成了最底层**——它的内容作用于所有层，与「事实层之下」这个位置无关，把它画在底部只是因为分层图需要一个底；
> ③ **「一个中心两个方向」覆盖不了六层**——向上是 A 和 D、向下是 F，那 I 和 R 在哪个方向？
> 现改为 **五层（D/A/I/O/F）+ 四条横切约束（权限 · 证据 · 可逆 · 运行）**。

---

## 一句话定义

> 决策智能架构，是把企业的**事实**与企业的**行动**，通过一层业务承认的**本体**缝合起来，
> 并在权限、证据、可逆四条约束下，交给分级授权的智能体去驱动的架构。

它要回答的不是「我们如何用上大模型」，而是：

> **企业里每天在做的那些决策，如何变成一条可被机器承接、可被人审计、可被逐级放权的闭环。**

### 两条读图规则（此前缺失，导致误读）

1. **纵轴表示「离决策的远近」，不表示调用方向。**
   正文说「智能层调用行动」，而图上 A 在 I 之上——分层架构惯例里调用方在上，此处正好相反。这是刻意的：这张图组织的是**职责的远近**，不是调用栈。按调用方向读会以为 A 是 I 的上游，那是误读。
2. **权限只定义一次。**
   权限的**模型**（对象/行/属性/行动四维）定义在本体上，权限的**强制执行**在运行约束里，但**规范只有一条**——即约束一。本体层与运行约束都不重复定义它，只引用。

## 一个中心：本体

本体是整个架构唯一的**语义权威**。它不是数据模型，不是知识图谱，不是元数据目录，而是**企业的可执行语义层**：

- 对上，它定义了智能层能看到什么、能做什么；
- 对下，它定义了事实层必须供给什么、以什么口径供给；
- 对内，它承载权限模型——权限沿对象与关系传播，而不是沿表和 API 传播。

**为什么本体必须在中心，而不是在旁边？**

因为一旦本体只是「一个可选的语义层」，就会立刻出现绕过它的捷径：报表直连数据库、Agent 写自由 SQL、前端硬编码业务公式。三个月后，企业里就有了第二套、第三套口径，本体退化成文档。

架构上的判据只有一条：

> **除本体外，不存在第二条通往业务语义的路径。**

详见 [O 本体层](04-O-本体层.md)。

## 两个方向

### 向下：连接事实（F → O）

本体的每一个对象、属性、指标，必须能追溯到权威数据源，并满足三个条件：口径唯一、血缘可追、时点正确。

这是**可信度**的来源。没有这一层，本体是一个漂亮的空壳。

详见 [F 事实层](05-F-事实层.md)。

### 向上：驱动行动（O → A → D）

本体的对象上绑定**行动（Action）**——可以改变企业状态的操作。智能层调用行动，人在决策界面层审批或复核行动。

这是**价值**的来源。没有这一层，本体是一个更贵的数据仓库。

详见 [A 行动层](02-A-行动层.md)、[D 决策界面层](01-D-决策界面层.md)。

## 四条约束

这三条贯穿所有层，不是某一层的功能，而是整套架构的设计前提。

### 1｜权限 Authority

权限定义在本体上（对象级 / 属性级 / 行级 / 行动级），而不是定义在接口或页面上。

**Agent 永远继承调用者的权限，不得拥有独立的超级身份。**一个用户看不到的数据，Agent 替他看也不行。

### 2｜证据 Evidence

任何一个结论，必须能回答：输入是什么、用了哪个版本的口径与模型、什么时候算的、谁触发的。

**失败与拒绝同样留痕。**系统说「我不知道」也是一条正式记录，不能被静默吞掉。

### 3｜可逆 Reversibility

默认可撤销。行动按可逆性分级：可撤销 / 可补偿 / 不可逆。

**不可逆的行动永远需要人。**自治级别的提升，本质上是「在哪一类可逆性上放权」的提升。

### 4｜运行 Runtime

**能力必须能被停下来、退回去、算清楚。**环境隔离、配额与熔断、发布与回滚、可观测性。

此前它是「R 运行层」，现升格为约束。实际后果：**任何一层的设计评审都必须回答「这一层出问题时怎么停、怎么退、成本怎么算」**，而不是把这些问题推给「底层去解决」。

详见 [四条横切约束](07-四条横切约束.md) 与 [运行约束](06-运行约束.md)。

## 五层职责速查

| 层 | 名称 | 核心问题 | 交付物 |
|---|---|---|---|
| **D** | 决策界面层 | 谁在做什么决策，错了谁担责？ | 决策清单、决策卡、人机权责矩阵 |
| **A** | 行动层 | 系统被允许改变什么？ | 行动契约、审批链、幂等与补偿设计 |
| **I** | 智能层 | 用规则、模型还是 Agent？放权到哪一级？ | 工具集定义、评测集、自治级别证据 |
| **O** | 本体层 | 企业由哪些对象和关系构成？ | 本体规范、对象 Owner、版本与变更流程 |
| **F** | 事实层 | 这个数从哪来，是什么时候的口径？ | 数据合同、血缘、时点正确性、断言 |

**横切约束**（不是层）：

| 约束 | 核心问题 | 交付物 |
|---|---|---|
| 权限 | 谁能做什么？无人值守时以谁的身份？ | 四维权限模型、委托身份规则 |
| 证据 | 能不能被采信、能不能改进？ | 证据链、坏消息留痕、证据链自身的治理 |
| 可逆 | 能自动做到什么程度？ | R1/R2/R3 分级、失败关闭 |
| 运行 | 谁能跑、花多少、错了怎么退？ | 环境隔离、配额熔断、发布与回滚 |

## 与传统数据/AI 架构的关键差异

| 维度 | 传统数据中台 / BI | 决策智能架构 |
|---|---|---|
| 起点 | 有哪些数据 | 有哪些决策 |
| 中心 | 数据仓库 / 湖仓 | 本体 |
| 终点 | 报表与看板（只读） | 行动与写回（可改变） |
| 语义 | 分散在报表与 SQL 里 | 集中在本体，唯一权威 |
| AI 的位置 | 数据之上的一个应用 | 本体之上的一类执行者 |
| 权限 | 表级 / 接口级 | 对象级 / 关系级 / 行动级 |
| 成功标志 | 数据接入完成率 | 被自动或半自动执行的决策数量 |

## 如何使用这套架构

**不要自上而下建全套。**五层是描述性的骨架，不是建设顺序。

正确的推进方式是**沿着一个真实决策，把五层打穿一次**：

1. 从 [决策清单](../20-实践/03-决策清单工作坊.md) 中选出 1 个高频、可逆、有明确 Owner 的决策；
2. 定义它需要的 3–5 个本体对象（不多做）；
3. 定义 1 个行动契约；
4. 接入支撑这些对象的最小数据集，满足事实层三条件；
5. 智能层从 L1（草拟建议）起步，配套评测集；
6. 运行约束给出隔离、配额与回滚；
7. 交付人机权责矩阵，并明确取消掉的旧动作。

完整节奏见 [首个 120 天](../20-实践/02-首个120天.md)，能力评估见 [成熟度模型](../20-实践/01-成熟度模型.md)。
