# 四条横切约束：权限 · 证据 · 可逆 · 运行

> **2026-08-23 更新**：由三条扩为四条（运行升格），并补入无人值守身份、证据链自身治理、R3 条件化三处修正。

> 这四条不属于某一层，而是整套架构的设计前提。
> 五层可以裁剪、可以简化，这四条不可以。
>
> **本页是权限规范的唯一出处。**本体层与运行约束都只引用，不重复定义。

---

## 约束一｜权限 Authority

### 原则

**权限定义在本体上，Agent 继承调用者权限，不存在超级 AI 身份。**

### 展开

- 权限的四个维度：对象级、行级、属性级、行动级（见 [本体层](04-O-本体层.md)）
- 身份上下文必须贯穿：用户 → Agent → 工具 → 数据 → 行动。中间任何一处退化成服务账号，模型即破。
- 越权的返回必须是**明确拒绝**，不是空结果。

### 为什么不能妥协

企业里一旦出现「AI 能看到所有数据」的事实，合规、法务、HR 会在第一时间叫停项目，而且这个信任一旦失去很难重建。

更隐蔽的风险是**信息通过 AI 泄漏**：销售 A 问「我们最大的客户是谁」，如果 Agent 用超级权限回答了，就等于绕过了原有的权限体系。这类泄漏不会触发任何传统的安全告警。

### 无人值守时的身份（此前的漏洞）

**〔判断〕** 「Agent 继承调用者权限」在人工触发时成立。但 **L3/L4 是定时或事件触发的自动执行——此时没有调用者**。本站此前六处陈述这条约束，**没有任何一处回答这个问题**，而这正是「超级 AI 账号」在现实中真正诞生的地方。

**规则：岗位委托身份。**

> 自动执行以**担责岗位**的身份运行；
> 权限**恰好等于**该岗位的人工权限，不多一分；
> 该岗位的担责人对每一次自动执行**事后可见、可撤回**；
> **岗位空缺或担责人离职时，该自动执行自动降级为 L2**，直到指定新的担责人。

两条配套硬约束：

| # | 约束 |
|---|---|
| 1 | **权限下界原则**：服务多个岗位时，权限取这些岗位的**交集**，不是并集 |
| 2 | **绝对禁止**：不得使用权限**大于**其担责人的自动执行身份。无例外——一旦允许，「不存在超级 AI 身份」就失效 |

**〔争议〕** 业界正在成型的标准化 Agent 身份委派（A2A、OAuth Cross-App Access 一类）与本规则不冲突——那是**实现机制**，本规则定的是**权限边界**。标准成熟后应优先采用标准。

### 自查

- 同一个问题，两个不同权限的人问，答案是否不同？（应该不同）
- 系统里是否存在一个拥有全量权限的服务账号被 Agent 使用？
- **每一个 L3/L4 自动执行，能否说出它以哪个岗位、哪个具体的人的身份在跑？**

## 约束二｜证据 Evidence

### 原则

**任何结论可追溯到输入与版本；失败与拒绝同样留痕。**

### 一条完整的证据链包含

```
决策/结论
  ├── 触发：谁、什么时候、通过什么入口
  ├── 输入：用了哪些对象与指标，各自的取值与时间点
  ├── 口径：指标的权威实现版本、本体版本
  ├── 推理：规则版本 / 模型版本 / 提示词版本
  ├── 输出：建议或已执行的行动、参数
  ├── 人的介入：谁审批的、是否被推翻、推翻理由
  └── 结果：执行成功/失败、后续影响
```

### 「坏消息不可隐藏」

这是本约束下最容易被违反的一条：

- 系统拒绝回答，要留痕
- 数据缺失导致跳过，要留痕
- 置信度低而弃权，要留痕
- 人推翻了系统建议，要留痕，**且推翻理由是最有价值的训练与改进信号**
- 失败的尝试、被否决的方案，要留痕

**界面可以降噪，但不能删除或改写权威状态。**做一个只展示成功案例的看板，等于主动放弃了系统改进的唯一信息来源。

### 证据链本身也需要被治理

**〔判断〕** 证据链是全架构中**唯一允许平台自己长期存储的数据**，且必然包含用户提问、数据取值、决策依据、被推翻的理由——**这是一个新创建的高敏感数据存储**。方法论创造了一个新风险，就必须治理它：

| 项 | 要求 |
|---|---|
| **留存期限** | 等保与行业监管有**下限**要求，个人信息保护有**上限**要求，两者要同时满足 |
| **访问权限** | 证据链的读取权限**不等于**业务数据的读取权限，需单独定义 |
| **个人信息** | 提问内容与决策依据可能含个人信息，需纳入数据分类分级 |
| **不可篡改** | 证据链自身必须追加式，修改证据链的操作本身要留痕 |

**这同时是一个卖点**：等保对审计留存的要求与证据链设计高度重合，**证据链本来就能满足大部分审计要求**。见 [合规与安全前置](../20-实践/07-合规与安全前置.md)。

### 为什么不能妥协

企业采信一个系统的前提是**可问责**。「它为什么这么建议」如果回答不了，那么第一次出错就是项目的终点——因为无法区分「偶发错误」和「系统性缺陷」，只能整体不信任。

### 自查

- 随机挑一次三周前的自动执行，能否还原完整证据链？
- 系统上一次「拒绝/弃权」有没有记录？
- 人工推翻的理由是否被结构化收集？

## 约束三｜可逆 Reversibility

### 原则

**默认可撤销；不可逆行动的自动化必须有可承担的损失上界。**

> **〔争议〕2026-08-23 更正。**此前写「不可逆行动**永远**需要人」。产业界大量 R3 行动（程序化广告、算法交易、自动放款与扣款、自动触达、物流调度）今天就在全自动执行，通行做法是限额 + 速率限制 + 熔断 + 事后补偿 + 保险。
> 修正后：**R3 开放自动需同时满足四条**——单次影响有硬上限、单位时间总量有硬上限、有已演练的事后补偿路径、有实时熔断与具名担责人。**四者缺一即保留人闸。**

### 展开

- 行动按 R1 可撤销 / R2 可补偿 / R3 不可逆 分级（见 [行动层](02-A-行动层.md)）
- 自治级别的开放，本质是「在哪一类可逆性上放权」
- **不满足四条件的 R3 最高只能到 L2**（草拟 + 人工确认），无论指标多好
- 设计技巧：把 R3 动作拆成 R2 前置 + R3 确认，让 AI 承担 95% 工作量，人保留最后一击

### 失败关闭（Fail-Closed）

可逆性约束的运行时体现：**系统在不确定时的默认行为是「不动作 + 明确报告」。**

触发失败关闭的情形：

| 情形 | 正确行为 | 错误行为 |
|---|---|---|
| 数据缺失 | 返回 `NOT_READY` + 缺什么 | 用 0 或前值填充后继续 |
| 口径不明 | 返回 `NOT_EVALUATED` | 按最可能的口径猜一个 |
| 权限不足 | 返回 `DENIED` | 返回空结果 |
| 置信度低 | 弃权，转人工 | 输出最佳猜测 |
| 断言失败 | 阻断下游 | 告警但继续出结论 |
| 上游合同违约 | 停止接入 | 尽力解析 |

> **降级成「看起来成功」是最危险的失败模式。**
> 一个明确的错误会被立刻发现和修复；一个看起来正常的错误会持续污染决策数月。

### 为什么不能妥协

企业环境里，**一次不可逆的错误动作，其损害可以超过系统一年创造的全部价值**，并且会永久性地摧毁业务方的信任。

可逆性是「允许犯错」的前提。一个允许犯错的系统才能被逐步放权；一个不允许犯错的系统只能永远停在建议级别。

### 自查

- 是否存在任何 R3 行动被开放为全自动？
- 数据缺失时，系统给出的是明确的不可用，还是一个数字？
- 上一次系统说「我不确定」是什么时候？

## 约束四｜运行 Runtime

### 原则

**能力必须能被停下来、退回去、算清楚。**

### 展开

| 项 | 要求 |
|---|---|
| **环境隔离** | 研究环境**凭据级**不得写生产；生产只运行受控发布的不可变版本 |
| **配额与熔断** | 预算、配额、**熔断必须是「停」不是「提醒」**、成本可归因 |
| **发布与回滚** | 代码/配置/提示词/模型/本体定义/评测集全部版本化；**回滚不需要审批，需要审批的是发布** |
| **可观测** | 技术指标 + 质量指标（含弃权率、**人工批准率**）+ 业务指标 |

### 为什么它是约束而不是层

**〔判断〕** 它的内容作用于所有层，与「事实层之下」这个位置没有任何关系。作为约束的实际后果是：**任何一层的设计评审都必须回答「这一层出问题时怎么停、怎么退、成本怎么算」**，而不是把这些问题推给「底层去解决」。

**〔判断〕** 还有一条本站此前没写的边界：**「给定版本可重放」对托管大模型不成立**——模型会被下线、涨价、在同一版本号下变更行为。可行的是「可追溯」而不是「可重放」。详见 [运行约束](06-运行约束.md)。

### 自查

- 研究环境能否写生产数据？
- 一次生产事故，能否在 10 分钟内回滚？
- 成本能否归因到具体场景？熔断是「停」还是「提醒」？
- 模型版本变更时，评测集会被强制重跑吗？

## 四条约束的相互关系

```
        权限  ──决定──▶  能做什么
          │
          ▼
        可逆  ──决定──▶  能自动做到什么程度
          │
          ▼
        证据  ──决定──▶  能不能被采信、能不能改进
          │
          ▼
        运行  ──决定──▶  出事时能不能停下来、退回去、算清楚
```

- **没有权限**，系统不能被授权使用；
- **没有可逆**，系统不能被授权自动；
- **没有证据**，系统不能被采信，也无法晋级；
- **没有运行约束**，前三条在出事时都兑现不了。

四者共同构成企业 AI 的**信任基础设施**。技术能力决定上限，这四条决定能不能开始。

**〔争议〕** 需要承认：四条约束的**完整实施成本很高**，而产业界大量成功的自动化系统（广告投放、风控、推荐）并没有全部做到——它们用限额、熔断与事后补偿替代了其中几条。本方法论的立场是「在可写回企业权威系统的场景下四条都需要」，**但这是判断，不是共识**。

## 落地检查表

在任何一个场景上线前，逐条打勾：

- [ ] Agent 的身份是委托身份，不是服务账号
- [ ] 同一问题对不同权限的人给出不同答案
- [ ] 越权返回明确拒绝，不是空结果
- [ ] 每个结论可还原完整证据链
- [ ] 拒绝、弃权、失败、人工推翻均有记录
- [ ] 人工推翻理由被结构化收集
- [ ] 所有行动标注了可逆性级别
- [ ] 开放为自动的 R3 行动 100% 满足四条件（单次上限 / 总量上限 / 已演练的补偿 / 熔断 + 具名担责人）
- [ ] 每个 L3/L4 自动执行都能说出其岗位委托身份与具体担责人
- [ ] 不存在权限大于其担责人的自动执行身份
- [ ] 证据链的留存期限、访问权限、个人信息处理已定义
- [ ] 熔断是「停」不是「提醒」；回滚不需要审批
- [ ] 数据缺失/口径不明时系统不动作并明确报告
- [ ] 自治级别的降级条件已定义且自动生效
