# O｜本体层 Ontology

> 整套架构的中心。企业的可执行语义骨架。
> 一句话：**让机器认识这家企业。**

---

## 1. 本体不是什么

先排除三个最常见的误解，因为它们会把项目直接带偏：

| 它不是 | 区别 |
|---|---|
| **数据模型** | 数据模型服务于存储与事务效率，本体服务于**业务语义与决策**。数据模型里没有「这个客户处于流失预警状态」这种东西。 |
| **知识图谱** | 知识图谱通常是只读的、面向检索与推理的；本体必须**绑定行动**，是可执行的。不能触发状态变更的本体只是图谱。 |
| **元数据目录** | 目录描述「有哪些表和字段」，本体描述「这家企业由哪些东西构成、它们之间发生什么」。目录服务于找数据，本体服务于做决定。 |

一句话区分：

> 数据模型回答「怎么存」，知识图谱回答「知道什么」，**本体回答「这家企业是什么，以及能对它做什么」。**

## 2. 本体的六个构成要素

### 2.1 对象类型（Object Type）
企业中的核心名词：客户、订单、SKU、门店、仓库、供应商、工单、合同、员工、需求、事故。

### 2.2 属性（Property）
对象的特征，分三类，必须区分清楚：

- **源属性**：直接来自权威系统（订单金额、下单时间）
- **派生属性**：由权威计算得出（客户 LTV、订单毛利）——**只能有一个权威实现**
- **状态属性**：生命周期状态（订单状态、客户健康度）——必须有明确的状态机

### 2.3 关系（Link）
对象之间的连接：订单 → 客户、订单 → SKU、工单 → 责任人、SKU → 供应商。

关系是本体相对于数据表最大的价值：**它把跨系统的语义缝合起来**。跨七个系统的订单履约链路，在本体里是一条可遍历的关系路径。

### 2.4 事件（Event）
发生了什么，带时间戳且不可变：下单、发货、退款、告警、审批通过、价格变更。

事件是重放与审计的基础，也是时点正确性的载体。

### 2.5 指标（Metric）
业务度量：GMV、履约时效、缺货率、客户健康分。

**每个指标只允许一个权威实现，有唯一 Owner。**查询层只做只读投影，禁止在报表、前端或 Agent 提示词里重新拼公式。

### 2.6 行动（Action）
可以改变企业状态的操作：调价、创建补货单、拦截订单、指派工单、发起审批。

**行动绑定在对象上**——不是「系统能调价」，而是「SKU 这个对象上有一个调价行动」。这一绑定关系，是权限与自治能够被精确表达的前提。

行动的完整契约见 [A 行动层](02-A-行动层.md)。

## 3. 一个对象是否合格？五条准入判据

不是所有业务名词都该进本体。每个候选对象必须同时满足五条，否则不予纳入：

| # | 判据 | 不满足时的后果 |
|---|---|---|
| **1** | **有唯一真身**：指明权威源系统与主键 | 出现多个版本的「客户」，口径战争 |
| **2** | **有稳定标识**：跨系统 ID 映射规则明确，含历史变更处理 | 关系连不起来，数据看着有其实用不了 |
| **3** | **有明确生命周期**：状态集合与合法转移已定义 | 状态语义靠猜，行动的前置条件无法表达 |
| **4** | **有绑定行动或明确的决策用途** | 本体膨胀，做了一堆没人用的对象 |
| **5** | **有业务 Owner**：一个具体的人，不是一个部门 | 变更无人裁决，本体腐化 |

> **判据 4 是最常被跳过、也最致命的一条。**
> 它是防止「本体膨胀」的唯一闸门。见 [反模式](../20-实践/05-反模式.md#本体膨胀)。

## 4. 本体从哪里开始：从决策倒推，不做全企业本体

最常见的失败路径是「先把全公司的本体建完，再谈应用」。这条路会消耗 12–18 个月，且几乎必然在业务侧失去耐心之前无法产生结果。

正确做法：

```
选定一个决策
   ↓
问：做这个决策，需要知道哪些东西？        → 对象（通常 3–7 个）
问：这些东西之间是什么关系？              → 关系
问：决策依据哪几个数？                    → 指标
问：决策的结果是对什么做什么？             → 行动
   ↓
只建这些。其余一概不建。
```

一个健康的第一版本体规模：**5 个以内对象，3 个以内关系，1 个行动**。

本体按决策需要**增量生长**。第二个决策会复用第一个决策的对象，第三个开始产生网络效应——这是本体真正的复利所在，但它必须由业务结果拉动，不能由建模冲动推动。

## 5. 本体是产品，不是项目产物

这是最容易被低估的一条。本体一旦成为企业语义权威，它就必须具备产品的所有特征：

| 产品特征 | 在本体上的具体要求 |
|---|---|
| **版本** | 本体有语义版本号；对象/属性/行动的变更显式版本化 |
| **合同** | 公共契约变更必须给出兼容期、迁移路径、旧版本退出条件 |
| **变更流程** | 谁能提议、谁能批准、如何评审影响面 |
| **废弃策略** | 对象与属性如何下线，下游如何被通知 |
| **Owner** | 每个对象有业务 Owner，整个本体有一个总负责人 |
| **文档** | 每个对象的语义定义是业务语言，不是字段注释 |

**没有变更流程的本体，会在六个月内退化成一份没人看的文档。**

## 6. 权限模型：权限沿本体传播

> **2026-08-23 收敛。**权限此前在本体层、运行层、横切约束三处各写一遍。
> 现在：**本体层只定义权限的四个维度（因为它们依附于本体结构）；规范、传播规则与无人值守身份统一在 [约束一](07-四条横切约束.md)。**

传统权限定义在表、接口、页面上，结果是权限与业务语义脱节，无法回答「这个销售能不能看到这个客户的毛利」。

本体权限的四个维度：

- **对象级**：能否看到「合同」这类对象
- **行级**：能看到哪些合同（我负责的 / 我部门的 / 全部）
- **属性级**：能看到合同的哪些字段（金额可见，成本不可见）
- **行动级**：能对合同执行哪些行动（可查看，不可作废）

**权限的规范见 [约束一](07-四条横切约束.md)**：Agent 继承调用者权限、无人值守时的岗位委托身份、权限下界原则、绝对禁止的情形。本节不重复。

## 7. 常见的本体设计错误

| 错误 | 表现 | 纠正 |
|---|---|---|
| **表到对象的一一映射** | 有 300 张表就建 300 个对象 | 对象是业务概念，通常远少于表；一个对象可能由 8 张表拼成 |
| **只读本体** | 建完了没有任何行动 | 无行动的对象必须有明确决策用途，否则删掉 |
| **IT 定义本体** | 语义定义来自字段注释 | 本体由业务定义、IT 实现；Owner 必须是业务方 |
| **忽略标识映射** | 假设各系统 ID 能对上 | 标识映射是本体最脏也最关键的工程，要单独立项 |
| **没有状态机** | 状态是一个自由文本字段 | 状态集合与合法转移必须显式定义 |
| **属性口径分裂** | 「毛利」在三处各算一遍 | 派生属性只允许一个权威实现 |

## 8. 交付物清单

建设本体层时，每个对象应产出一份**对象规范卡**（模板见 [模板库](../20-实践/04-模板库.md#本体对象规范卡)），包含：

- 业务定义（业务语言，一段话）
- 权威源系统与主键
- 标识映射规则
- 属性清单（区分源 / 派生 / 状态）
- 生命周期状态机
- 关系
- 绑定行动
- 权限规则
- 业务 Owner
- 版本与变更记录

## 9. 检验：本体是否真的立住了

用这五个问题自查：

1. 有没有任何一条通往业务语义的路径**绕过了**本体？（有 → 本体没立住）
2. 随机挑一个指标，能否在 5 分钟内说出它的权威实现与 Owner？
3. 随机挑一个对象，业务方能否用自己的话说清它的定义？
4. 上游系统改一个字段，本体层会**报错**还是**静默算错**？
5. 过去三个月本体有没有发生过一次受控变更？（完全没变 → 可能已经没人用了）
