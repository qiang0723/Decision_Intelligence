# 约束四｜运行 Runtime

> 核心问题：**谁能跑、跑多久、花多少、错了怎么退？**
> 最不性感，但它是 PoC 与生产之间那道断崖的主体。
>
> **2026-08-23 升格。**此前它是「R 运行层」，画在事实层之下。但它的内容（隔离、成本、发布回滚、可观测）**作用于所有层**，与那个位置没有任何关系；且它包含的「权限落到运行时」与约束一重复。现为第四条横切约束。

---

## 1. 环境隔离

至少三套环境，边界必须是机制性的，不是约定性的：

| 环境 | 数据 | 允许的行动 | 谁能进 |
|---|---|---|---|
| **研究/沙箱** | 生产数据的脱敏或只读副本 | **只读，零写回** | 分析师、开发 |
| **预生产** | 生产数据只读 + 影子写回（记录不执行） | 影子行动 | 开发、业务评审 |
| **生产** | 生产数据 | 完整行动，受权限与自治级别约束 | 受控发布 |

**硬规则：**
- 研究环境**不得**拥有任何生产写权限。这条不能靠自觉，要靠凭据隔离。
- 生产只运行**受控发布的不可变版本**，不挂载开发工作树。
- 任何「临时在生产上改一下」的通道都必须不存在。

---

## 2. 权限的强制执行点

> 权限的**规范**在 [约束一](07-四条横切约束.md)，本节只说**强制执行发生在哪里**。

- **强制点在工具执行处，不在入口处**——入口鉴权挡不住中途身份切换
- **身份上下文一路传递**：用户 → Agent → 工具 → 数据 → 行动
- **无人值守时使用岗位委托身份**（见 [模块四 4.4b](../10-方法论总结/04-模块四-行动闭环与企业采纳.md)）

---

## 3. 成本、配额与熔断

生成式系统的成本结构与传统系统不同：**边际成本不可忽略，且可以在无人察觉时指数增长。**

必须在运行层强制的四件事：

| 机制 | 说明 |
|---|---|
| **预算** | 每个场景/团队有明确的月度预算 |
| **配额** | 单次调用、单批次、单用户的调用上限 |
| **熔断** | 触及阈值自动停止，而不是告警后继续跑 |
| **成本归因** | 成本可归因到场景、用户、决策类型 |

> **熔断必须是「停」，不是「提醒」。**
> 一个只发告警不停止的成本保护，在夜间和周末等于不存在。

同时应当在决策卡里记录**单次决策成本**，并与该决策的业务价值对比。一个每次花 3 元、每天做 500 次、但只节省 2 分钟人工的场景，经济上不成立。

## 4. 发布与回滚

要求：

- **版本化交付物**：代码、配置、提示词、模型、本体定义、评测集，全部有版本，且**一次发布对应一组确定的版本组合**。
- **可回滚**：任意一次发布能一键退回上一个已知良好状态。回滚不需要审批。
- **灰度**：新版本先在小比例流量或小范围对象上运行。
- **发布即证据**：每次发布记录变更内容、评测结果、审批人。

**特别提醒**：提示词和本体定义的变更，与代码变更享受同等待遇。它们同样会改变系统行为，却经常被当成「配置微调」而绕过流程——这是生成式系统里最常见的事故来源。

---

## 5. 可观测性

三类信号，缺一不可：

| 类型 | 内容 |
|---|---|
| **技术指标** | 时延、错误率、吞吐、资源占用、成本 |
| **质量指标** | 准确率/一致率、弃权率、人工推翻率、抽检结果 |
| **业务指标** | 该决策对应的业务成效（履约时效、缺货率、毛利） |

> **「人工推翻率」是最诚实的指标。**
> 它直接度量业务方对系统的真实信任度。这个数字上升，说明出问题了——通常比技术指标更早报警。

## 5b. 模型供应商与版本风险

> **2026-08-23 新增。**外部审查指出一处承诺与现实的冲突。

**〔判断〕** 本方法论承诺「给定代码版本 + 数据版本可重放」。**对托管大模型，这个承诺不成立**：

| 风险 | 后果 |
|---|---|
| 模型被下线 | 依赖它的评测结论与自治级别证据全部失效 |
| 同一版本号下行为变化 | 重放得到不同结果，证据链断裂 |
| 定价变化 | 单次决策成本模型失效，可能直接击穿 [投入产出测算](../20-实践/08-投入产出测算.md) 的否决线 2 |
| 供应商政策变化（留存、训练用途、可用区域） | 触发合规重审 |

**必须承认的边界**：run-to-run 方差本身就是模型属性（pass^4 常比 pass^1 低 15–25 个百分点，见 [引用 `A17`](../40-参考/04-引用与数据来源.md)）。**严格可重放对托管模型不可得**——据我所知没有办法做到，这一点我不确定是否有例外。

### 行为漂移：一类不会自己暴露的失效

**〔判断〕** 上表的风险都是「会被发现的」。**行为漂移不会**（`H2`）。

模型版本更新后，理解口径可能发生细微偏移——同样的输入，分类结果、抽取字段、判断倾向出现系统性变化。表现是**错误标注长期累积而无人察觉**，直到某次对账或投诉才暴露，届时已需要大规模人工返工。

**必须与 run-to-run 方差区分开**：

| | run-to-run 方差（`A17`） | 行为漂移（`H2`） |
|---|---|---|
| 范围 | 同一模型版本内的随机性 | **跨版本的系统性偏移** |
| 可观测性 | 多次采样即可测量 | **不会自己暴露** |
| 应对 | 测量并接受，写进评测预期 | **主动监测** |

**三条监测手段**（缺一不可）：

1. **金标准集定期重跑，而不只在变更时重跑**——因为托管模型可能在你不知情时更新
2. **人工推翻率与人工批准率的趋势**——漂移通常先表现为这两个数字的缓慢变化
3. **输出分布监控**——分类占比、弃权率、参数取值分布的漂移，往往早于准确率下降

> **〔判断〕** 第 1 条最容易被省掉，也最关键。「只在我们改动时才重跑评测」这个习惯，恰好漏掉了**别人改动时**的情形——而托管模型的变更权不在你手里。

**可行的缓解，不是解决**：

- 证据链记录**模型标识 + 版本 + 调用时间**，承认「可追溯」而不承诺「可重放」
- 关键决策的**输入与输出快照**入证据链，使结论本身可复核（即使不可重算）
- 模型版本变更时**强制重跑评测集**，把模型变更当作代码变更对待
- 高价值场景考虑私有化部署换取版本可控（代价见 [自建 vs 采购](../20-实践/09-自建vs采购与退出剧本.md)）

## 6. 常见错误

| 错误 | 纠正 |
|---|---|
| 研究环境有生产写权限 | 凭据级隔离，不靠约定 |
| Agent 用服务账号访问数据 | 委托身份贯穿全链路 |
| 成本只告警不熔断 | 熔断必须是停止 |
| 提示词/本体变更绕过发布流程 | 与代码同等待遇 |
| 只监控技术指标 | 加上质量与业务指标，尤其是人工推翻率 |
| 回滚需要审批 | 回滚不需要审批；需要审批的是发布 |

## 7. 检验

1. 研究环境能否写生产数据？（能 → 立即修复）
2. 一次生产事故，能否在 10 分钟内回滚？
3. 上个月的成本能否归因到具体场景？
4. 提示词的最近一次变更，能否找到对应的评测结果与审批人？
5. 人工推翻率是多少？趋势如何？
6. **人工批准率**是多少？≥95% 说明确认环节已成「确认剧场」（见 [模块三 3.6](../10-方法论总结/03-模块三-Agentic系统设计与编排.md)）
7. 模型版本变更时，评测集会被强制重跑吗？
