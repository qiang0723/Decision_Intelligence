# D｜决策界面层 Decision Surface

> 核心问题：**谁在做什么决策，依据什么，错了谁担责？**
> 这一层决定项目的方向。方向错了，下面五层做得再好也是白做。

---

## 1. 为什么从决策开始

企业 AI 项目有两种起点：

- **正向推导**：我们有哪些数据 → 能做什么分析 → 产出一堆可能性清单，然后没人要。
- **反向推导**：企业在做哪些决策 → 哪些决策做得不好 → 需要什么才能做好。

只有第二种能产出需求。

**判据**：如果一个功能被砍掉，没有任何一个具体的人的具体动作会改变，那它不是需求。

---

## 2. 决策清单（Decision Inventory）

决策清单是这一层的核心资产，也通常是咨询交付的第一个成果。

对企业里每一个真实决策，记录八个字段（★ 为工作坊现场必填的 4 个）：

| 字段 | 说明 | 为什么重要 |
|---|---|---|
| ★ **决策名称** | 用动词，如「是否给这个 SKU 补货」 | 名词化的描述会滑向「数据需求」 |
| ★ **决策者** | 具体岗位，不是部门 | 没有具体岗位 = 没有用户 |
| ★ **频次** | 每天/每周/每月，多少次 | 频次决定自动化的价值上限 |
| **当前依据** | 现在靠什么做决定（经验/报表/Excel） | 暴露真实痛点 |
| **决策耗时** | 单次平均耗时 | 计算节省 |
| **错误代价** | 做错一次损失多少，可逆吗 | 决定自治级别与审批设计 |
| ★ **现有系统落点** | 决策结果最终写进哪个系统 | 这就是未来的**行动**接口 |
| **口径争议** | 是否存在定义分歧 | 预警本体建设难度 |

清单产出方式见 [决策清单工作坊](../20-实践/03-决策清单工作坊.md)。

---

## 3. 决策的四象限：选谁先做

用**频次**和**错误可逆性**两个轴给决策分类：

```
              错误可逆                     错误不可逆
          ┌──────────────────────┬──────────────────────┐
   高频次 │  ★ 第一批            │   谨慎：需强审批链    │
          │  自动化价值最高       │   适合 L1–L2 自治     │
          │  可快速积累证据       │   如：大额付款、发货   │
          ├──────────────────────┼──────────────────────┤
   低频次 │  价值有限            │   ✗ 不要碰            │
          │  除非单次价值极高     │   战略决策，人的领域   │
          └──────────────────────┴──────────────────────┘
```

**第一批场景必须落在左上象限**：高频 + 可逆。

理由：高频提供快速的证据积累，可逆提供犯错空间。这两点是自治级别得以晋升的前提。

低频 + 不可逆的战略决策（是否进入新市场、是否收购）**不应该是企业 AI 的目标**。把它写进方案是一个危险信号。

---

## 4. 决策卡（Decision Card）

每个进入建设的决策，产出一份决策卡。这是 D 层向下游（A/I/O/F）传递需求的**唯一接口文档**。

结构：

```
决策卡 · <决策名称>
────────────────────────────────
1. 决策陈述     一句话：在什么情况下，对什么，做什么决定
2. 决策者       岗位 + 人数 + 频次
3. 触发条件     什么时候需要做这个决策（定时 / 事件驱动 / 人工发起）
4. 判断依据     需要哪些指标与事实，各自的口径与 Owner
5. 可选动作     决策的输出空间（离散选项 / 连续参数）
6. 约束条件     业务规则、合规红线、不可越界的边界
7. 落点行动     结果写回哪个系统的哪个操作           → 交给 A 层
8. 涉及对象     需要本体中的哪些对象与关系           → 交给 O 层
9. 错误代价     做错的损失、可逆性、发现时延
10. 成功度量    这个决策做得更好，用什么指标证明
11. 人机权责    见下节
12. 目标自治级  起步级别与晋升条件                   → 交给 I 层
```

模板见 [模板库](../20-实践/04-模板库.md#决策卡)。

## 5. 人机权责矩阵

这是**组织落地**的核心工具，也是最常被跳过的一步。

对每个决策，明确四个角色：

| 角色 | 定义 | 可以是 AI 吗 |
|---|---|---|
| **建议者** | 提出方案 | ✅ 可以，且通常从这里开始 |
| **决定者** | 拍板 | 取决于自治级别 |
| **执行者** | 实际操作系统 | ✅ 通过行动层执行 |
| **担责者** | 出问题时负责 | ❌ **永远是人** |

> **不可协商的一条：担责者永远是人。**
>
> 任何一个「AI 自动执行」的场景，都必须能指出一个具体的人，他对这个自动化的结果负责。
> 找不到这个人，就不要上自动执行。

### 交付时必须回答的问题

> **哪一个旧动作因此被取消了？**

如果答案是「没有，只是多了一个参考」，那么这个场景在组织意义上没有落地，它会在三个月内消亡。

新增一个动作而不取消任何动作，是净增加负担。落地的标志是**减法**。

## 6. 决策界面的形态

决策界面不一定是一个新系统。按优先级排序：

1. **嵌入现有工作流**（最优）：在业务人员已经每天打开的系统里出现——ERP 的待办、企业微信/飞书的卡片、工单系统的推荐。
2. **推送到人所在的地方**：告警、日报、审批流。
3. **独立控制台**（次选）：只有当决策需要复杂的上下文探索时才做。
4. **对话式界面**（谨慎）：适合探索性分析，**不适合日常高频决策**——高频决策需要的是一键确认，不是打字。

> 常见错误：把所有场景都做成 Chat。
> 对话是探索的界面，**不是执行的界面**。一个每天要做 200 次的决策，界面应该是一个按钮和一行理由，不是一个输入框。

---

## 7. 检验

1. 决策清单里的每一条，能否指出一个具体的人？
2. 第一批场景是否都落在「高频 + 可逆」象限？
3. 每个决策卡是否都写出了**落点行动**（写回哪个系统）？写不出来的，说明它还是个只读需求。
4. 每个场景是否都指明了**被取消的旧动作**？
5. 每个自动化场景是否都有一个具体的担责者？
