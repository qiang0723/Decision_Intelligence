# I｜智能层 Intelligence Layer

> 核心问题：**用规则、模型还是 Agent？放权到哪一级？凭什么晋级？**

---

## 1. 三种智能各归其位

企业里最常见的浪费，是用大模型解决一个 `if` 语句能解决的问题。

| 形态 | 适用 | 不适用 | 成本 | 可解释性 |
|---|---|---|---|---|
| **确定性规则** | 逻辑明确、合规红线、阈值判断 | 规则数量爆炸、需要泛化 | 极低 | 完全 |
| **预测模型** | 有标签、有历史、结构化、需要量化 | 缺乏历史、需要解释推理链 | 中 | 中 |
| **生成/推理 Agent** | 非结构化输入、多步任务、需要综合判断与自然语言 | 高频简单判断、要求确定性输出 | 高 | 需专门设计 |

**选型原则（按顺序问）：**

1. 能写成规则吗？→ 能就写规则。
2. 规则写不下（组合爆炸或需要泛化），有标签数据吗？→ 有就用预测模型。
3. 输入是非结构化的、或任务需要多步综合判断？→ 才用 Agent。

> **能写死的不要用模型，能用小模型的不要用大模型。**
> 这不只是成本问题，更是可解释性与稳定性问题。企业更看重「每次都一样」，而不是「大多数时候更聪明」。

现实中的最佳结构通常是**混合**：Agent 负责理解与编排，规则负责红线，模型负责量化，最终动作走行动层的固定契约。

## 2. Agent 的能力边界 = 本体暴露的工具集

这是本层最重要的一条设计原则。

```
❌  Agent + 数据库连接 + 「你可以写 SQL 查任何东西」
✅  Agent + 本体工具集 + 「你可以调用这 12 个工具」
```

工具集来自两处，且只来自这两处：

- **查询工具**：本体上的只读投影（查对象、遍历关系、取指标）
- **行动工具**：本体上的行动（见 [A 行动层](02-A-行动层.md)）

### 为什么不给自由 SQL

| 问题 | 说明 |
|---|---|
| **口径失控** | Agent 自己拼的公式与财务口径不一致，结论不可采信 |
| **权限失控** | 行级/属性级权限无法在自由 SQL 上强制 |
| **不可审计** | 无法回答「这个数是怎么算出来的」 |
| **不可回归** | 同一问题两次可能给出不同 SQL、不同答案 |
| **性能与成本** | 一条失控的查询可以拖垮生产库 |

自由 SQL 只应存在于**隔离的分析沙箱**中，供分析师探索，且其产物不能直接进入决策路径。

### 工具设计要点

- 工具粒度贴合**业务动作**，不贴合数据表。（`查询客户近 90 天履约异常` 而不是 `select from t_order`）
- 工具的返回必须包含**证据引用**（数据来源、口径版本、时间戳），供追溯与展示。
- 工具的失败必须是**显式的、可被 Agent 理解的**（`NOT_READY: 缺少 2026-08-20 的库存快照`），而不是返回空结果——空结果会被 Agent 当成「没有异常」。

## 3. 分级自治（L0–L4）

自治不是一个开关，是一个阶梯。每一级的晋升必须由证据驱动。

| 级别 | 名称 | 系统做什么 | 人做什么 | 典型准入条件 |
|---|---|---|---|---|
| **L0** | 观察 | 只输出分析与解释 | 全部决策与执行 | 上线即可 |
| **L1** | 建议 | 给出推荐动作与理由 | 决策 + 执行 | 离线评测达标 |
| **L2** | 草拟 | 生成待执行的动作草稿（参数已填好） | 审批 + 一键执行 | 影子运行期通过 |
| **L3** | 限额自动 | 在阈值内自动执行，超限升级 | 例外处理 + 抽检 | 连续 N 期在线指标达标，且限额内 |
| **L4** | 全自动 | 全量自动执行 | 监控 + 定期审计 | 长期稳定 + 仅限 R1/R2 行动 |

**硬规则：**

- **R3（不可逆）行动最高只能到 L2。**
- 晋级必须有**预先定义**的量化条件，不能在看到结果后临时议定。
- 晋级是可逆的：触发降级条件时自动退回上一级，且降级不需要审批。
- 每一次晋级/降级都是一条审计记录。

> **晋级靠证据，不靠信心。**
> 「我们觉得它已经挺准了」不是晋级理由。晋级条件应当在上线之前就写进决策卡。

## 4. 评测：没有评测集就不上线

这是本层的不可协商项。生成式系统尤其容易「看起来对」，人的直觉在这里系统性失效。

### 三层评测

**① 离线金标准集（上线前）**
- 由业务专家标注的历史案例集，覆盖正常场景与已知边界场景
- 规模不必大，但必须**覆盖失败模式**：缺数据、口径歧义、极端值、恶意输入
- 金标准集**冻结后不得因结果不好而修改**——改了就失去了裁决能力

**② 影子运行（上线中）**
- 系统在真实数据流上产出建议，但不执行
- 与人的实际决策比对，统计一致率与分歧原因
- 分歧比一致更有价值：每一个分歧都要归因（系统错 / 人错 / 口径不清）

**③ 在线抽检（上线后）**
- 持续按比例人工复核已执行的动作
- 抽检率随自治级别提升而设定，L3/L4 不能取消抽检

### 指标不只是准确率

| 维度 | 指标 | 为什么 |
|---|---|---|
| 正确性 | 准确率 / 一致率 | 基础 |
| **弃权率** | 主动说「不确定」的比例 | 一个从不弃权的系统是危险的 |
| **错误分布** | 高代价错误 vs 低代价错误 | 90% 准确率但错的都是大单，等于不可用 |
| 稳定性 | 同一输入多次结果一致性 | 企业要可预测 |
| 时效 | 端到端时延 | 决策有窗口期 |
| 成本 | 单次决策成本 | 见 [运行层](06-运行约束.md) |

> **弃权率是被严重低估的指标。**
> 让系统学会说「这个我不确定，请人来看」，比让它多对几个百分点更有价值。
> 见 [四条横切约束 · 失败关闭](07-四条横切约束.md)。

## 5. 提示词与模型版本也是配置项

生成式系统里，提示词、模型版本、温度参数与传统代码一样会改变系统行为，因此必须享受同等的工程待遇：

- **版本化**：提示词入版本控制，不允许在生产界面里手改
- **绑定证据**：每条输出记录所用的提示词版本、模型版本
- **变更即回归**：改提示词必须重跑评测集
- **可回滚**：能一键回到上一个版本

> 一个常见事故：有人「优化」了提示词，指标悄悄降了 8%，两周后才发现，且无法定位是哪次改动。
> 根因是提示词不在版本控制里。

## 6. 常见错误

| 错误 | 纠正 |
|---|---|
| 什么都用大模型 | 先问能不能写成规则 |
| 给 Agent 自由 SQL | 只给本体工具集 |
| 用演示效果代替评测 | 没有评测集不上线 |
| 一步跳到全自动 | 从 L1 起步，逐级晋升 |
| 工具返回空结果表示失败 | 失败必须显式，否则被误读为「无异常」 |
| 追求零弃权 | 弃权是安全特性，不是缺陷 |
| 提示词在生产环境手改 | 提示词是代码，进版本控制 |

## 7. 检验

1. 每个场景是否问过「能不能写成规则」？
2. Agent 是否只能调用本体工具，没有自由数据访问？
3. 有没有一个冻结的评测集，且它是在结果出来之前定的？
4. 自治晋级条件是否在上线前就写死了？
5. 系统上一次说「我不确定」是什么时候？（从不 → 有问题）
6. 提示词与模型版本是否可追溯、可回滚？
