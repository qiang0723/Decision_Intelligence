# F｜事实层 Foundation Layer

> 核心问题：**这个数从哪来、谁算的、是什么时候的口径？**
> 这一层不产生价值，但它决定上面所有价值是否可信。

---

## 1. 事实层的三个必须

不是「数据接入」，而是三个可验证的性质：

### 必须一｜口径权威唯一

同一个业务度量，全企业只允许存在**一个权威计算实现**。

- 权威实现在后台，有唯一 Owner
- 查询层、报表层、前端、Agent 提示词一律**只做只读投影**，禁止重算
- 发现第二处实现，按缺陷处理，不按「灵活性」处理

**判据**：随便挑一个指标，问三个部门，答案是否一致？

### 必须二｜血缘可追

任何一个数字，能在 5 分钟内回答：

```
来自哪个源系统的哪个接口/表
经过了哪几步加工，每步用的什么规则
用的是哪个版本的口径
数据的时间点是什么
上一次成功更新是什么时候
```

血缘不是一张架构图，是**可查询的运行时元数据**。

### 必须三｜时点正确（Point-in-Time）

**这是企业里最容易被忽略、也最容易造成静默错误的一条。**

典型错误：用**今天**的主数据去解释**昨天**的业务事实。

- 用今天的客户分级，去分析上个季度的成交转化 → 结论被未来信息污染
- 用今天的 SKU 类目，去回溯半年前的品类表现 → 类目调整过，对不上
- 用今天的组织架构，去归因去年的销售业绩 → 人员已经换了部门
- 用修正后的财报，去评估当时的判断质量 → 高估了当时的可判断性

**规则：任何用于回溯分析、模型训练或效果评估的数据，必须能还原到「当时可知」的状态。**

实现要点：
- 主数据保留**有效期区间**（valid_from / valid_to），而不是只存当前值
- 事实记录同时保留**业务发生时间**与**系统可知时间**（双时间轴）
- 任何回溯查询必须显式指定「以哪个时点的认知为准」

> 时点正确性问题的可怕之处在于：**它不报错。**
> 系统会给你一个看起来完全正常、并且偏乐观的数字，直到上线后效果对不上。

## 2. 数据合同（Data Contract）

上游系统的变更不能静默破坏下游。数据合同把这条从「靠沟通」变成「靠机制」。

一份数据合同包含：

| 项 | 说明 |
|---|---|
| **Schema** | 字段、类型、可空性 |
| **语义** | 每个字段的业务含义与枚举值含义（`status=3` 是什么） |
| **质量承诺** | 完整性、及时性、唯一性的可度量承诺 |
| **变更流程** | 提前通知期、兼容期、迁移路径 |
| **Owner** | 上游负责人，具体到人 |
| **违约处理** | 合同被破坏时下游的行为（见「失败关闭」） |

**没有数据合同的接入，本质上是把上游团队的随意变更权，接进了你的决策系统。**

## 3. 断言式校验：把静默错误变成显式失败

在数据进入本体之前，跑一组自动断言。每条断言输出 PASS / FAIL + 异常清单。

断言的设计原则：**不抽样看趋势，而是对账。**

推荐的断言家族：

| 类型 | 例子 |
|---|---|
| **完整性对账** | 应有记录数 − 实际记录数 = 已归因缺失数（差额必须为 0） |
| **唯一性** | 主键唯一、业务唯一键唯一 |
| **参照完整性** | 订单引用的客户 ID 必须存在于客户对象 |
| **量纲断言** | 金额/数量的比值落在合理区间（防止差 100 倍的静默错误） |
| **双算校验** | 关键派生量用两条独立实现各算一遍，比对一致 |
| **枚举合法性** | 状态值必须在已定义的状态集合内 |
| **时序逻辑** | 发货时间 ≥ 下单时间；状态转移合法 |
| **跨源交叉** | 与独立数据源比对，偏差超阈值报警 |

> **量纲断言与双算校验是投入产出比最高的两条。**
> 它们抓的是「看起来完全正常」的那一类错误——恰恰是最贵的那一类。

**任一断言 FAIL 的默认行为：阻断下游，不出结论。**详见 [失败关闭](07-四条横切约束.md)。

## 4. 不可变 + 可重放

可信的地基有两个性质：

- **不可变（Immutable）**：原始落地数据只增不改。修正通过新增记录表达，不覆盖历史。
- **可重放（Replayable）**：给定代码版本 + 数据版本，能重新算出完全相同的结果。

带来的能力：
- 出问题能定位到具体批次
- 能回答「上个月那个结论，用当时的数据和当时的代码，是否成立」
- 口径变更可以对历史重算，且新旧结果并存对比，而不是悄悄覆盖

**反面**：直接 UPDATE 生产表的架构，永远无法回答「三周前它为什么给出那个建议」。

## 5. 标识映射（Identity Resolution）

跨系统把「同一个东西」认出来，是事实层最脏、也最关键的工程。

它值得**单独立项**，不要藏在 ETL 里。

要点：
- 明确每类对象的**权威标识**与各系统标识的映射表
- 映射本身有版本与生效时间（今天认定 A=B，不代表上个月就该合并）
- 保留**未匹配**与**冲突**清单，且它们必须有人处理，不能默默丢弃
- 匹配置信度低的，进人工复核队列，而不是强行合并

> 强行合并造成的数据污染，比不合并更难修复。宁可留下「未匹配」，不要制造错误的「已匹配」。

---

## 6. 接多少数据：按本体需要接

与本体一样，事实层**不追求全量接入**。

```
决策 → 本体对象 → 支撑这些对象所需的最小数据集 → 接入
```

**判据**：每接入一个数据源，能否说出它支撑哪个对象的哪个属性、服务哪个决策？说不出来的不接。

「先把数据都接进来再说」是 [数据湖谬误](../00-立场/02-为什么企业AI停在PoC.md)，会消耗掉项目的全部耐心额度。

## 7. 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 用当前主数据回溯历史 | 结论被未来信息污染，且不报错 | 双时间轴 + 有效期区间 |
| 缺数据时用 0 或前值填充 | 静默错误，指标虚假正常 | 缺失就是缺失，标记为不可用 |
| 直接 UPDATE 历史数据 | 无法重放，无法追溯 | 只增不改，修正用新记录表达 |
| 没有数据合同 | 上游一改，下游静默算错三周 | 合同化 + 断言校验 |
| 强行做标识匹配 | 制造错误关联，难以修复 | 低置信度进人工队列 |
| 「先接全量数据」 | 一年半没有业务结果 | 按本体需要接 |

---

## 8. 检验

1. 随便挑一个指标，5 分钟内能否说清它的来源、口径版本与 Owner？
2. 能否把三个月前的某个结论用当时的数据与代码完整重放？
3. 上游改一个字段，系统会**报错**还是**静默算错**？
4. 数据缺失时，系统给出的是「不可用」还是一个看起来正常的数字？
5. 每一个接入的数据源，能否说出它服务哪个决策？
