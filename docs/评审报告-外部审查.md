## 1. 总体判断

这套方法论的**结构质量明显高于内容质量**：六层框架、三条约束、四套模板、L0–L4 与 R1–R3 分级构成了一个自洽、可讲、可交付的骨架，模块四（行动闭环与企业采纳）确实填补了公开材料里最薄的一块，这部分我认为是有真实价值的原创贡献。

但它目前**不是一份可以交给 CIO 的方法论，而是一份写得很好的立场陈述**。最大的问题只有一个，且是结构性的：**全库 31 个文件、41 处〔共识〕标注、上百个具体数字，没有一条外部引用、没有一个真实案例、没有一处可核验的证据**。「区分共识与个人判断」被写在 README、about 页和信息架构里当作全站可信度的核心机制，但〔共识〕在没有出处的情况下只是一个更用力的断言，读者仍然无法评估可靠性——这恰恰是作者自己反对的那件事。

次严重的问题是：**方法论最外层的概念地基（Palantir 的 semantic-kinetic-dynamic 三层框架）是错的，而且错误来源是作者自己调研的那个竞品站的二手转述**（第 4.1 节）。第三是**权限模型与分级自治在 L3/L4 上自相矛盾**（第 3.3 条），第四是**合规、安全、成本三个买方一票否决项整块缺失**（第 6 节）。第五是**模块三是一份 2024 年的分类学**——它盘点了提示词编排模式，却完全没有 2025–26 年真正在变的东西（上下文经济学、MCP、code mode、harness、Agent 威胁模型），而作者恰恰是用「参考站的 Agentic 部分是二手知识」作为自己的差异化理由（第 3.6 条）。

还有一个跨越全局的观察：**这套方法论的很多主张，在 2026 年已经被产品化了，而文中把它们当成自己的原创发现在讲。**「不要给 Agent 自由 SQL，给它受治理的语义接口」——Cube、dbt、Snowflake、Databricks、微软全部在卖这个；「失败时报错而不是给一个貌似合理的错答案」——dbt 已经把它做成了可量化的基准对比（语义层 98.2% vs text-to-SQL 90.0%，且失败模式不同）。**这对作者其实是好消息**：它证明命题是对的，且有第三方数据可引。但前提是文中要承认它们的存在，而不是把版图停留在「本体 vs BI 的延伸」这个 2023 年的对立上。

一句话定位：**这是一份优秀的「方案评审用检查清单」，被误当成了「方法论」在写。**它的判据部分（12 问、反模式、检验清单）质量很高且立刻可用；它的论证部分（四条命题、四代演进、范式对照）经不起一个懂行的人追问三句。

### 3.1 【致命】全库零证据：41 处〔共识〕无一条出处，上百个数字全是杜撰

**文件与小节**：全库。集中体现于 `10-方法论总结/01-模块一.md` 1.1、1.3；`02-模块二.md` 2.4；`03-模块三.md` 3.2 A1、3.5 工具设计要点 4；`00-立场/02-为什么企业AI停在PoC.md` 全篇。

**具体问题**：

- 与此同时，全库有 41 处〔共识〕标注。「企业 AI 项目的失败率远高于消费级 AI 应用」（1.1）、「本体建设最普遍的失败是范围失控：建了 12–18 个月还没上线」（2.4）、「工具过多会显著降低选择准确率」（3.5）——都是可以被具体研究支持或反驳的经验命题，但都以「各家调研的口径不同，但结论一致」这种方式带过。

**为什么是问题**：这不是学术洁癖。它直接摧毁全站的核心差异化主张。README 和 about 页都把「区分〔共识〕〔争议〕〔判断〕」写成本站相对同类站的护城河，理由是「一份不区分共识与个人观点的方法论总结，读者无法评估它的可靠性」。但一个没有出处的〔共识〕标签，读者同样无法评估——它只是把「我认为」换成了「大家都认为」，可信度反而低于诚实的〔判断〕。一个挑剔的 CIO 只要问一句「这个 12–18 个月是哪来的」，整套标注体系就失效了。`docs/内容路线图.md` 自己已经承认「全站目前缺叙事性证据，决策者最吃这个」——但它把这列为「第二批」，这是优先级判断错误，这是第一批。

**建议怎么改**：
1. 立一条硬规则：**〔共识〕标签必须附至少一条可点击来源，否则降级为〔判断〕**。按这条规则重跑全库，我估计 41 处里能保住〔共识〕的不超过 15 处。可用的锚点：MIT / Gartner / BCG 的企业 AI 落地调研、Anthropic《Building Effective Agents》、Palantir 官方文档、Dehghani 的 Data Mesh 原文、dbt/Cube 官方文档。
2. 所有杜撰数字二选一：**要么删掉数字只留定性表述**（「本体建设周期常常拖过一年」），**要么明确标注为示意**（「以下数字为示意，非实测」）。尤其是「60% 复用率」这类被用作判据的数字，必须改成「由团队在第一个场景结束时自行设定阈值并冻结」。
3. `内容路线图.md` 里的「一个完整的匿名案例」提到第一优先级。哪怕是作者自己二十年经历中的一个脱敏项目复盘（哪怕失败的），也比现在全篇零案例强。**没有案例，这套东西在买方眼里就是 PPT。**

### 3.2 【致命】Palantir 三层框架的表述是错的，且来源是竞品站的二手转述

**文件与小节**：`content/10-方法论总结/02-模块二.md` 2.2「范式一：语义-动能-智能（Palantir 路线）」；`content/40-参考/01-坐标系.md` 第一节；`content/10-方法论总结/05-模块五.md` 5.2；`content/40-参考/03-参考站调研.md` 第二节第 3 条。

**具体问题**（核实过程与来源见 4.1）：
- 文中三处写「**Palantir 官方**的本体表述是三层结构：Semantic / Kinetic / **Dynamic（智能）= 绑定到对象上的模型**」。Palantir 官方文档里**没有 Dynamic 层**。官方是**两分法**：semantic elements（对象、属性、链接）+ kinetic elements（actions、functions、**dynamic security**）。文中的「Dynamic」实际来自官方术语 **dynamic security**——运行时动态计算的细粒度权限策略，它是 kinetic 的一个子项，而且讲的是**权限，不是模型**。
- 更要命的是来源链条：`40-参考/03-参考站调研.md` 第 47–56 行显示，作者是从 rebootingwithai.com 抄来 "semantic-kinetic-dynamic system" 和 "digital operational twin" 两句，并在评分表里给该站「概念准确性 ★★★★☆／本体三层框架表述准确」。也就是说：**作者把一个第三方博客的转述认定为 Palantir 官方表述，给它打了高分，然后把它当作自己整套方法论的概念地基**。（该三层说法可溯源到一篇 Medium 文章，而即便在那篇文章里，dynamic 层指的也是「业务规则、策略、工作流与权限」，不是模型。）

**为什么是问题**：整个 `40-参考/01-坐标系.md` 和 5.2 的叙事骨架是「Palantir 三层回答了『是什么』，我补上『怎么跑起来』」。如果那三层根本不是 Palantir 说的，这个对照的合法性就没了。而且 Palantir 是这个圈子里被读得最多的公司，任何读过 palantir.com/docs 的架构师会在第一页发现这个错误——那之后他不会再相信这份材料里任何一句关于外部世界的陈述。这是「用二手材料做一手判断」的典型代价，对一个把「诚实标注内容性质」当卖点的站尤其致命。

**建议怎么改**：
1. 把三处「Palantir 官方的三层结构」改成官方的两分法（semantic elements / kinetic elements），并明确 dynamic security 是 kinetic 下的权限机制。
2. 如果仍想保留「名词 + 动词 + 智能」这个三分的讲法（它作为教学框架是好用的），**明确标注为「本方法论对 Palantir 模型的再表述，非官方术语」**，并附官方文档链接。
3. 修订 `40-参考/03-参考站调研.md` 对该站「概念准确性」的评分与理由——现在这一条是在为一个错误背书。
4. 顺带把 5.2 的对照表更新到 2026 年的实际形态：Ontology 现在同时是 Foundry 与 AIP 的核心，Ontology SDK / Palantir MCP / AIP Autopilot 都已存在。文中把 Palantir 描述成一个静态的概念框架，落后于它的实际状态。

### 3.3 【致命】权限模型与分级自治在 L3/L4 上自相矛盾，这是架构级漏洞

**文件与小节**：`10-方法论总结/02-模块二.md` 2.4 末「权限沿本体传播」；`04-模块四.md` 4.3 分级自治、4.4 约束一；`15-DIA框架详解/06-R-运行层.md` 第 2 节；`15-DIA框架详解/07-三条横切约束.md` 约束一。

**具体问题**：全库反复强调、并列为三条不可裁剪约束之首的一条是：

> 「Agent 继承调用者权限，不存在超级 AI 身份」「Agent 没有独立身份，只有委托身份」「中间任何一处退化成服务账号，模型即破」

同时，L3（限额自动）和 L4（全自动）的定义是系统**自动执行**——`30-行业剖面/02-软件公司内部系统.md` 明确给出「第 11 周+：L3，低级别告警自动归档/自动指派」，`01-电商.md` 的补货场景同样指向定时批量自动执行。

**在无人值守的定时/事件触发自动执行里，没有「调用者」。**那么此时 Agent 用谁的身份？全库六个文件反复陈述这条约束，**没有任何一处回答这个问题**。而这恰恰是企业安全评审第一个会问的问题，也是「超级 AI 账号」在现实中真正诞生的地方——绝大多数团队会在这里悄悄配一个服务账号，按作者自己的说法就是「模型即破」。

**为什么是问题**：这不是措辞瑕疵，是两个核心构件（权限模型 / 自治阶梯）在最重要的交界处没有对接。它使得 M4 成熟度、L3/L4 自治、以及「三条约束不可裁剪」三者不能同时成立。一个 CIO 的安全架构师会在十分钟内发现它，而这一条一旦被指出，「三条横切约束」的权威性就受损。

**建议怎么改**：在 `04-模块四.md` 4.4 与 `15-DIA/07` 里新增一小节「无人值守时的身份」，给出明确规则。可用的解法（择一或组合，需作者自己定）：
- **岗位委托身份**：自动执行以「担责岗位」的身份运行，权限恰好等于该岗位的人工权限，且该岗位的人对每一次自动执行事后可见、可撤回——这与 4.6「担责者永远是人」天然衔接，我认为这是最贴合本方法论的解。
- **行动级独立主体 + 权限下界**：自动执行主体的权限必须是其所服务岗位集合权限的**交集**（下界），而不是并集。
- 明确禁止：不得使用任何权限大于其担责人的自动执行身份。
无论选哪种，都要同步补进 `20-实践/04-模板库.md` 的行动契约模板第 3 项（现在只写了「Agent 执行时继承：<调用者身份>」，在 L3/L4 下这个字段填不出来）。

### 3.4 【致命】失败分类学是循环论证，「只有一条半是模型问题」是伪经验结论

**文件与小节**：`00-立场/01-核心命题.md` 末「由此得到的方法论骨架」表；`00-立场/02-为什么企业AI停在PoC.md` 末「十条症状对应的四个根因」表；`10-方法论总结/01-模块一.md` 1.3。

**具体问题**：论证链条是这样闭合的——
1. `01-核心命题.md` 先立四条命题（缺语义骨架 / 必须能改变 / 需要边界 / 是治理问题）；
2. `02-为什么企业AI停在PoC.md` 列十条失败症状，末尾把它们归成**恰好四个**根因，并写明「这四个根因，正是四条命题的镜像」；
3. `01-模块一.md` 1.3 把同样十条重排一遍，然后以〔判断〕下结论：「**十条里只有一条半是模型问题。这个比例本身就是这个领域最重要的事实。**」

十条症状是作者自己选的，四个根因是照着已有的四条命题分的，然后「模型问题只占一条半」这个比例被当成「这个领域最重要的**事实**」提出来。这是标准的循环论证：结论已经写进了取样规则。

而且这个症状集合是**被裁剪过的**——真实项目复盘里高频出现、但一条都没进这个清单的失败原因至少包括：预算被砍 / 高层换人导致 sponsor 消失、关键人离职、合规或安全评审未通过、供应商交付能力不足、选定场景的业务价值本身被高估、模型能力确实不够（长尾语言理解、跨模态、长程一致性）。这些被排除，正是因为它们落不进四个预设根因。

**为什么是问题**：立场篇是全站的地基，被 README 称为「后面所有分层、模板和路线图都是这四条命题的推论」。地基是循环的，上面所有推论的说服力就只能靠读者本来就同意作者。对一个持怀疑态度的 CIO 来说，「只有一条半是模型问题」这句话读起来不像洞察，像是在给「所以你需要我这套治理方法论」铺路。

**建议怎么改**：
1. 删掉「这个比例本身就是这个领域最重要的事实」这句话，或者改成诚实的表述：「**这十条是我按四条命题的视角选出来的，因此比例是构造的结果，不是统计结果。**」——作者有勇气写这句话，反而会大幅提升可信度，这与他自己的内容纪律一致。
2. 在十条之外增设一节「**本方法论覆盖不到的失败原因**」，明确列出 sponsor 变更、预算、合规否决、供应商能力、场景价值高估、模型能力边界这几类，并说明为什么它们不在本方法论射程内。这一节会成为全站可信度最高的段落之一——理由与作者自己写「未解问题」一节的理由完全相同。
3. 把「模型不是瓶颈」从命题降级为**有条件的判断**：在语义与治理未就绪的企业里模型不是瓶颈；在已经做完 M2、场景选对的企业里，模型能力（长程一致性、可靠的结构化输出、成本）重新成为主要约束。当前的绝对化表述在 2026 年已经开始站不住。

### 3.5 【致命】合规、安全、成本三个买方一票否决项整块缺失

| 变更管理 | 1 次 |

**具体问题**：
- **合规**：目标读者是中国企业的 CIO/CTO。一个把业务数据喂给大模型、并能反向写回 ERP/OMS 的平台，在立项阶段必然要过等保、数据分类分级、个人信息处理影响评估、（若用境外模型）数据出境安全评估；金融、医疗、汽车等行业还有各自的监管口径。全库对此**零字**。`15-DIA/07` 里提了一句「合规、法务、HR 会在第一时间叫停项目」，但只是用来论证权限的重要性，没有给任何应对。
- **安全**：这一点尤其刺眼。全套方法论的核心主张是「不要给 Agent 自由 SQL，要给它定义良好的工具」——**而工具化 Agent 恰恰是间接提示注入（indirect prompt injection）的主要攻击面**。一个供应商在订单备注里写一句话，被 Agent 读进上下文，就可能触发一次「合法权限内」的调价或补货。作者的权限模型能挡住越权，挡不住**权限内的被操纵行动**。全库对这类攻击零提及，而它是 2024 年以来 Agentic 系统最主要的安全议题。
- **成本**：`15-DIA/06-R-运行层.md` 讲了运行期的预算/配额/熔断，这很好，但那是**单次决策成本**。买方要的是**项目级投入产出**：这 90 天要几个人、多少钱、什么时候回本、不做会损失什么。`docs/内容路线图.md` 把「投入产出测算模型」列为「高优先级、规划中」——它应该是已完成项，因为 `20-实践/06-开工前12问.md` 的 Q12「什么情况下你们会叫停这个项目」要求客户给出量化失败判据，而全站不提供任何测算工具来支撑这个回答。这是自相矛盾的。

**为什么是问题**：这三项不是「锦上添花的补充章节」。它们是**否决项**：合规过不了，项目根本不会立项；安全评审过不了，权限开不出来；ROI 算不出来，预算批不下来。一份宣称「把治理当一等公民」的方法论，把治理限定为「口径权威 + 证据链 + 可逆性」这三条内部工程纪律，而完全不碰外部监管与对抗性安全，在买方眼里是把「治理」这个词用窄了。

**建议怎么改**：新增三块内容，优先级高于 `内容路线图.md` 里现有的任何一条「第二批」：
1. **`20-实践/07-合规与安全前置.md`**：数据分类分级如何映射到本体的属性级权限；哪些对象/属性触发个人信息处理评估；模型部署形态（公有云 API / 私有化 / 混合）与数据出境的关系；等保对日志留存与审计的要求如何与「证据链」设计合并（这里有真正的协同点，证据链本来就能满足大部分审计要求，这是个卖点而不是负担）。
2. **在 `10-方法论总结/03-模块三.md` 3.5 工具设计里增加第 5 条要点：对抗性输入**。规则至少包括：来自外部方（客户、供应商）的自由文本进入上下文前必须标记为不可信；不可信内容不得影响行动参数；行动参数必须能追溯到结构化事实而非文本；高风险行动前做一次「参数是否可由本体事实独立复算」的校验。这一条与作者已有的「结构化输出优先」「参数范围即安全边界」是同源的，写起来顺理成章。
3. **`20-实践/08-投入产出测算.md`**：给一个粗算模板——决策频次 × 单次节省时间 × 人力成本 vs（实施人月 + 年运行成本 + 治理人力），以及「什么条件下算不过来就不要做」。这个工具的商业价值不亚于 12 问。

### 3.6 【致命】模块三是一份 2024 年的分类学：整章没有「上下文经济学」和「威胁模型」两个概念

**文件与小节**：`content/10-方法论总结/03-模块三-Agentic系统设计与编排.md` 全章，尤其 3.2 模式谱系、3.4 上下文工程与记忆、3.5 工具设计。

**具体问题**：模块三自述取向是「总结模式谱系，标出企业语境下哪些能用、哪些是玩具」。它列的 13 种模式（Tool Use / ReAct / Plan-and-Execute / Reflection / Router / Structured Output / Supervisor / Pipeline / Debate / Blackboard / RAG / GraphRAG / Text-to-SQL）**每一条描述的都是「推理循环的形状」**。而 2025–2026 年 Agentic 工程真正在争论的东西，是**基础设施层**：上下文预算、互操作协议、能力封装、harness、以及 Agent 专属安全。这一层在模块三里完全没有位置。

具体缺失（按对企业读者的重要性排序，核实来源见 4.2）：

| # | 缺失概念 | 为什么对企业读者是必需的 |
|---|---|---|
| 1 | **Agent 专属威胁模型**（OWASP Top 10 for Agentic Applications 2026、「致命三element」、六种抗注入设计模式） | 见 3.5。一份没有威胁模型的企业 Agentic 方法论不成其为方法论。 |
| 2 | **上下文工程（context engineering）** | 这是 2025 年底以来该领域的组织性概念——compaction、结构化笔记、子 Agent 上下文隔离、即时检索。模块三 3.4 名为「上下文工程与记忆」，但内容仍停在「放什么不放什么」的提示词视角，没有把上下文当作**有限资源与预算**来处理。 |
| 3 | **MCP（Model Context Protocol）与工具互操作** | 已于 2025-12-09 捐给 Linux Foundation 下的 Agentic AI Foundation，由 Anthropic、OpenAI、Block 共同发起，Google/微软/AWS 支持。企业最关心的 N×M → N+M 集成问题和网关级鉴权，全在这里。模块三 0 次提及。 |
| 4 | **代码执行即工具调用（code mode / CodeAct）** | 直接推翻模块三把「Tool Use」当成一个扁平方格的做法：循环、条件、错误处理移入代码后，Pipeline 与大半个 Plan-and-Execute 被吸收掉了。公开的量级是 token 消耗从约 15 万降到约 2 千。 |
| 5 | **harness（运行框架）概念** | 2026 年的实践共识是：团队从 harness 改造（上下文重置、验证闸、工具人体工学、权限门）拿到的可靠性提升，**大于**从「ReAct 换成 Plan-and-Execute」拿到的。一份只让读者「挑一个图」的谱系，回答不了他们真正的运行期工程问题。 |
| 6 | **Agent Skills / 渐进式披露** | 对企业最相关的一点是它是**分发与策略单元**，有组织级治理——这正是本方法论关心的东西，但谱系里没有槽位放它。 |
| 7 | **可观测性与 AgentOps**、**沙箱与最小权限**、**长任务的持久化执行与确定性重放**、**A2A 与 Agent 身份委派（OAuth Cross-App Access）** | 最后一项尤其关键：企业真正卡住的地方就是「怎么把用户身份委派给 Agent」——这与本报告 3.3 指出的 L3/L4 身份漏洞是同一个问题，而业界已有正在成型的答案，方法论却没有引用。 |

**为什么是问题**：作者的差异化叙事建立在「参考站的 Agentic 部分是二手知识、严重同质化」（`40-参考/03-参考站调研.md` 短板 2）之上。但模块三本身正是同一类二手整理，而且**是更旧的那一版**——它盘点的是 2024 年的提示词编排模式，缺席的是 2025–26 年真正在变的东西。一个 Agent 工程师（README 明确把他列为三类目标读者之一）读完模块三，会认为作者的领域信息停在两年前，进而怀疑模块二与模块四的时效性。而模块四恰恰是全库最有价值的部分。**这是一处「用次品拖累正品」的结构性风险。**

**建议怎么改**（这是我认为投入产出比最高的一次改动）：
1. **不要再扩充模式清单**。把 3.2 压缩到现在的一半，明确定位为「读者可能在别处见到的模式术语速查」，并加一句：「这些模式描述推理循环的形状；企业里的可靠性主要不来自选对形状。」
2. **把腾出的篇幅给三节新内容**：（a）上下文经济学——上下文是有限预算，四种技术（压缩、结构化笔记、子 Agent 隔离、即时检索）；（b）Agent 威胁模型与抗注入设计模式；（c）harness 与运行期工程。这三节没有一节是同质化内容，且都能直接接到作者已有的强项（结构化输出、参数边界、失败关闭、证据链）。
3. **把 MCP 与 Agent 身份委派接进模块二/模块四**——MCP 是「工具即本体行动」这个主张的现成落地协议，A2A/OAuth 身份委派是 3.3 那个漏洞的现成解法。作者的架构主张与这两个标准是同向的，引用它们只会加强论证。

### 3.7 【严重】实践部分不可执行：没有前置条件、没有人和工时、90 天第三阶段排期不成立

**文件与小节**：`20-实践/02-首个90天.md` 三个阶段；`20-实践/03-决策清单工作坊.md` 流程时间表。

**具体问题**：
1. **无前置条件**。90 天路线默认企业已经有可查询的集中数据、有数据团队、有能指定业务 Owner 的高层背书。按作者自己的成熟度模型，这是 **M1 已达成**的企业。但 `02-首个90天.md` 从头到尾没有写「本路线适用于 M1 及以上；M0 企业请先做 X」。一个 M0 的读者照着做，会在阶段二直接卡死。
2. **无团队与工时**。全篇（以及整个 `20-实践/`）没有一处说明这 90 天需要什么角色、几个人、多少投入。扫描确认：`20-实践/` 下「团队/人数/工时/FTE」的有效出现次数为 0（唯一命中的「人数」是工作坊参会人数和决策卡模板字段）。CIO 无法据此立项，因为立项文件的第一页就是人和钱。
3. **阶段三排期不成立**。Day 61–90 共 30 天，要交付 9 项产出，其中第 5 项是「**影子运行 2–4 周的比对报告**」。影子运行必须发生在行动契约（第 1 项）、智能层实现（第 2 项）、权限贯穿（第 3 项）、证据链（第 4 项）全部完成之后。即取最乐观的 2 周影子期，前四项必须在 14 天内完成，同时还要在剩余时间做完决策界面、人机权责矩阵、晋级条件、环境隔离与回滚。这个排期在任何真实企业里都不成立，而作者在 `05-反模式.md` A4 里恰恰批评了「宽而浅的 PoC」——这里犯的是对称的错误：**窄而不可能完成**。
4. **阶段二同样乐观**。Day 31–60 要求「与每个上游系统签数据合同」。数据合同的本质是让上游团队承诺 schema 稳定性与变更通知期——这是跨部门谈判，不是技术工作。30 天内完成多个上游的合同签署，需要的组织权力远超一个试点项目通常拥有的。
5. **工作坊时间预算算不过来**。`03-决策清单工作坊.md`：1:20–2:00 共 **40 分钟**，要对「合并后通常 30–60 条」决策**逐条补全八个字段**。即每条 40–80 秒填 8 个字段，其中包括「错误代价」「口径争议」这种需要讨论的字段。不可能。
6. **「八个字段」实际只列了七个**。`03-决策清单工作坊.md` 第 59 行的括号里是：决策者、频次、当前依据、耗时、错误代价、落点系统、口径争议 = 7 项，漏了 `15-DIA/01-D` 里定义的第一个字段「决策名称」。术语表也写「八字段」。这是个小错，但它出现在最核心的可交付物定义上。

**为什么是问题**：`20-实践/` 是全站宣称「可以独立交付、不依赖方法论」的一条主线，也是 about 页四项服务里三项的直接内容。一个陌生团队拿去照做会在第 40 天发现自己排期崩了。可执行性是这套东西相对参考站的核心差异化——差异化不能只体现在「有模板」，还要体现在「排期是真的」。

**建议怎么改**：
1. 在 `02-首个90天.md` 开头加「**适用前提**」：目标域已达 M1；已有一名 VP 级以上 sponsor；已有可指定的业务 Owner 候选人；上游系统有可对话的责任人。并给 M0 企业一条一句话的前置路径。
2. 加一张「**投入估算**」表：按角色列出（业务 Owner 兼职、数据工程、平台工程、AI 工程、项目经理），给出人数区间与投入比例。哪怕是作者的经验估计，也要写明「基于经验估计，非实测」。
3. **重排阶段三或改成 120 天**。诚实的做法是：把影子运行独立成第四阶段（Day 91–120），90 天的终点改为「L1 上线 + 影子运行开始」。这与「第 90 天有人取消一个旧动作」的判据冲突，需要一并调整（见 3.10）。
4. 工作坊：把「补全八个字段」缩减为现场只填 4 个必填字段（决策名称、决策者、频次、落点系统），其余 4 个由主持人会后 3 天内补全并回签——这与现有的「结束后 3 个工作日交付」本来就衔接。
5. 修正「八个字段」的列举，与 `15-DIA/01-D` 和术语表对齐。

### 3.8 【严重】开工前 12 问的评分机制会否决自己的目标客户，且混淆了「现状诊断」与「设计承诺」

**文件与小节**：`20-实践/06-开工前12问.md`，特别是末尾「评分与结论」表。

**具体问题**：
1. **评分会把目标客户全部劝退**。现行规则是「3–5 个危险信号 = 不要开工；6+ = 组织尚未准备好，不谈 AI 自动化」。现在把一家典型的 M1 中国企业（也就是这套方法论的目标买方）代入：Q5（上游改字段怎么发现）大概率答「对账时能发现」= 危险；Q6（回溯用当时可知数据）大概率「听不懂」= 危险；Q8（怎么证明它对）答「做了几个 demo」= 危险；Q9（上次说不确定是什么时候）答不上来 = 危险；Q11（三周前的执行能否还原）答「日志里应该有」= 危险。**五个危险信号，还没算 Q4 口径裁决权。**结论是「不要开工」。作者写这套东西的目的是让企业开工。
2. **一半的问题问的不是现状，是尚不存在的系统**。Q8（冻结的金标准集）、Q9（弃权率）、Q11（三周前的自动执行）问的都是「你们现在的 AI 系统怎么样」——但立项评审发生在系统存在之前。这几问实际上是**设计承诺**（你们打算怎么做），被误放进了**现状诊断**的评分表里，且与其他问题等权计分。
3. **权重相同但重要性差一个数量级**。Q1（被允许改变什么）和 Q6（时点正确性）在评分上各算一票。前者答错意味着项目方向错了，后者答错意味着有一个具体的技术债要补。等权是错的。

**为什么是问题**：这是全库商业价值最高的工具，也是 about 页明确的服务入口之一（「方案评审」「成熟度诊断」）。工具本身的判据质量很高，但**评分机制把一个诊断工具变成了拒绝工具**。而且它自相矛盾：`01-成熟度模型.md` 明确说 M1→M2 是最难的一步、是绝大多数企业所在的位置，12 问却把处在这个位置的企业判为「不要开工」。

**建议怎么改**：
1. 拆成两组并分别计分：**Q1–Q4、Q10、Q12 = 前提组**（问的是组织现状与意愿，任何一条不过关都应该真正叫停）；**Q5–Q9、Q11 = 设计组**（问的是打算怎么做，答不上来不是叫停理由，是「这几项必须写进方案」的待办清单）。
2. 相应改写结论表：前提组 ≥2 个危险信号 → 先做诊断与工作坊，不要立项；设计组的危险信号 → 逐条转为立项文件里的必做项与验收条件。
3. 明确 Q1 是**否决项**（单独一条不过就不开工），其余不是。
4. 顺带修 Q6 的判据。「听不懂这个问题」被列为危险信号，但时点正确性在中国企业里的普及度很低，把「听不懂」判为危险信号等于判所有人危险。改成：「听不懂 → 不是危险信号，是必须在阶段二补的一课；**听懂了但说『我们不需要』→ 才是危险信号**。」

**文件与小节**：`20-实践/04-模板库.md` 四套模板；对照 `30-行业剖面/01-电商.md` 末「常见失败」表与 `20-实践/05-反模式.md`。

| 模板 | 缺失字段 | 证据 |

### 3.10 【严重】「第 90 天有人取消一个旧动作」与「从 L1 起步」互相矛盾

**文件与小节**：`20-实践/02-首个90天.md` 开头判据与阶段三里程碑；`20-实践/06-开工前12问.md` Q3；`10-方法论总结/04-模块四.md` 4.6。

**具体问题**：
- 90 天的唯一成功判据是「第 90 天，有一个具体岗位的人，因为这个系统，取消了一个旧动作」。
- 同一份文件的阶段三写「上线时从 **L1 或 L2** 起步，不要一步到位」。
- L1 的定义（4.3）是「系统给出推荐动作与理由，**人做决策 + 执行**」。
- Q3 的危险信号是「**不取消，只是多一个参考**」。

L1 按定义就是「多一个参考」。所以按 12 问的判据，一个严格执行 90 天路线并在 L1 上线的项目，在第 90 天会命中自己的危险信号。

**为什么是问题**：这两条都是全站反复强调的招牌主张（「落地的标志是减法」和「晋级靠证据不靠信心」），它们在时间上撞车。这不是理论瑕疵——它决定了咨询交付第 90 天的验收怎么写。作者会在第一个真实项目上被客户问住。

**建议怎么改**：区分**被取消的动作的层次**。L1 阶段能取消的不是「决策动作」，而是「**决策前的信息搜集动作**」——人工拉数、跨系统比对、每周对数会。把判据改写为：
- 第 90 天（L1/L2）：取消一个**信息搜集类**旧动作（例：值班人员逐条浏览告警列表；采购每天早上从三个系统导数拼 Excel）。
- L3 之后：取消一个**决策/执行类**旧动作。
`30-行业剖面/02-软件公司内部系统.md` 里写的「被取消的旧动作：值班人员逐条人工浏览告警列表并判断的动作」其实已经是这个思路，但它被挂在了 L2/L3 阶段，且方法论正文没有把这个区分显式化。同时修 Q3 的危险信号表述，把「多一个参考」限定为「连信息搜集动作都没减少」。

### 3.11 【严重】「R3 不可逆行动永远需要人闸」应该标〔争议〕，现在被写成不可协商

**文件与小节**：`10-方法论总结/04-模块四.md` 4.2、4.3 硬规则 1；`15-DIA/02-A-行动层.md` 第 3 节；`15-DIA/07-三条横切约束.md` 约束三；`40-参考/02-术语表.md`。

**具体问题**：这条在模块四被标为〔判断〕，但在 DIA 详解的三个文件里被陈述为「**不可协商**」「无论评测指标多好、运行多久无事故，都不能开放为全自动」，没有任何标注，也没有列出反方立场。

而产业现实是：**大量不可逆行动今天就在全自动执行**——程序化广告投放（预算一旦花出去不可撤回）、算法交易、自动放款与自动扣款、自动发送的营销短信与推送、自动化的物流下单与承运商调度、SaaS 的自动扣费与续订。这些系统的通行做法不是「人闸」，而是**限额 + 速率限制 + 异常熔断 + 事后补偿 + 保险**。作者自己在 `01-电商.md` 里也写了「是否退款：小额自动，大额人闸」——这已经是对「R3 永远需要人」的一个例外，但正文没有承认它是例外。

**为什么是问题**：这是全库最强硬的规范性主张之一，而它作为对现实的描述是错的，作为规范也不是领域共识。一个做过支付或广告的 CTO 会立刻举出反例，而当一条「不可协商」被举出反例，读者会怀疑其他几条「不可协商」。更实际的问题是：这条规则会让方法论在最有价值的高频不可逆场景（支付、发货、触达）上无话可说。

**建议怎么改**：
1. 在 DIA 三处补上〔争议〕标注，并列出反方立场：「产业界普遍用限额 + 速率上限 + 熔断 + 事后补偿替代人闸，代表场景是程序化广告、自动放款、自动触达。」
2. 把规则改写成**有条件**的形式，这样反而更有力：「R3 行动开放自动执行需要同时满足：单次影响有硬上限、单位时间总量有硬上限、有可执行的事后补偿路径、有实时异常熔断、有一个具名担责人。**四者缺一即保留人闸。**」这既承认了现实，又保住了作者真正想守的东西（不是「必须有人点确认」，而是「必须有可承担的损失上界」）。
3. 相应修改「R3 最高只能到 L2」这条硬规则和术语表。

### 3.12 【应修】六层划分存在三处交叉重叠，「一个中心两个方向」这个记忆锚点覆盖不了它自己的框架

**文件与小节**：`15-DIA框架详解/00-架构总览.md` 分层图；`10-方法论总结/05-模块五.md` 5.1。

**具体问题**：
1. **权限出现在三个地方**：本体层（`04-O-本体层.md` 第 6 节定义四维权限模型）、运行层（`06-R-运行层.md` 第 2 节「权限落到运行时」）、以及横切约束一。三处内容高度重复。这说明权限不是「本体层的一个功能」，而应该只是横切约束——但 O 层和 R 层都各写了一遍，读者不知道该在哪一层做设计。
2. **R 运行层本质是第四条横切约束，被误画成了最底层**。它的内容（环境隔离、成本熔断、发布回滚、可观测性）作用于所有六层，与「事实层之下」这个位置没有任何关系。而它包含的「权限落到运行时」又与横切约束一重复。把 R 画在 F 之下，只是因为分层图需要一个底。
3. **A 层画在 I 层之上，但被 I 层调用**。图里自上而下是 D / A / I / O / F / R，而正文说「智能层调用行动」「Agent 的能力边界 = 本体暴露的工具集（查询工具 + 行动工具）」。在分层架构的惯例里调用方在上、被调用方在下，此处正好相反。读者按图理解会以为 A 是 I 的上游。
4. **「一个中心，两个方向，三条约束」这个记忆锚点覆盖不全**。向上是 A 和 D，向下是 F——那 I 和 R 在哪个方向？I 夹在 A 与 O 之间，R 在 F 之下但与「事实」无关。这个锚点很好记，但它描述的是一个四层框架，不是六层。

**为什么是问题**：这是全站唯一的架构图，出现在 README、首页、模块五、DIA 总览四处。图与文不一致、层与约束混淆，会让懂架构的读者认为这个六层是为了凑一个好记的形状而不是从职责推导出来的——这恰恰是作者批评别人「概念包装」的那类问题。

**建议怎么改**（三选一，我倾向第二个）：
- **保守改法**：保留六层，但在总览里明说「A 与 I 之间不是调用层级关系，图上的上下表示的是『离决策的远近』而非调用方向」，并把 O 层第 6 节的权限内容全部并入横切约束，O 层只保留「权限的四个维度定义在本体上」一句加链接。
- **诚实改法**：改成 **五层 + 四约束**——D / A / I / O / F 五层，权限、证据、可逆、**运行（隔离·成本·发布）**四条横切。记忆锚点相应改成「一个中心，两个方向，四条约束」。这比现在自洽，代价是要改一句已经用了很多遍的口号。
- **激进改法**：承认这是三层（决策 / 语义 / 事实）加若干横切，六层是展开视角。

### 3.13 【应修】M0–M4 与 L0–L4 大部分是同一把尺子换了个皮

**文件与小节**：`20-实践/01-成熟度模型.md`；`10-方法论总结/04-模块四.md` 4.3 与 4.7。

**具体问题**：把两套分级并排：

| 成熟度 | 定义 | 对应的自治级别 |
|---|---|---|
| M3 可行动 | 「系统草拟，人一键确认」 | **就是 L2 的定义** |
| M4 可自治 | 「系统在限额内自动执行」 | **就是 L3 的定义** |

M0/M1/M2 描述的是组织与语义的状态（这部分有独立价值，尤其 M2 作为分水岭的论证是全库最好的段落之一），但 M3/M4 只是把 L2/L3 换了个名字重说一遍。全库同时还有 R1–R3、四象限、五条准入判据、九要素、十条症状、12 问——编号框架密度过高，且顶层的两套互相包含。

**为什么是问题**：CIO 读到第三套五级量表时会开始怀疑这是包装。而且它制造了实际的表述困难：一个域「M3 但只有一个场景在 L2」该怎么报告？文中规则二说「级别按域算」，但没说域内多场景不同自治级别时如何汇总。

**建议怎么改**：把成熟度模型收敛为 **M0–M2 三级（描述组织与语义状态）+ 一个覆盖率指标**。M3/M4 用「该域内有 N 个决策达到 L2 以上 / L3 以上」表达，而不是新造一级。这与作者自己的规则三完全一致——他已经写了「有价值的是『有多少决策进入了闭环』，不是『最高做到第几级』」，那就应该让模型本身长成这个样子，而不是先给五级再叮嘱别追求级别。

**总判决：单条判断的准确率不低（有一条是全库最扎实的判断），但整体框架是 2024 年的。夸大之处集中在 Debate 与 Text-to-SQL 两条。**

| # | 文中主张 | 核实结果 | 依据 |

### 4.3d 「瓶颈不在模型」（命题一、`01-模块一.md` 1.1）

⚠️ **对典型企业流程自动化基本成立，但表述过于绝对，且存在作者应当正面回应的反证。**

**支持面**：Anthropic/Material 2026（集成 46% / 数据 42% / 变更管理 39%，模型能力不在首位）；Forrester "Context, Not Models, Is The Real AI Bottleneck"；Gartner 给出的取消原因是成本、价值不明、风控不足而非准确率；甚至 MIT NANDA 自己的原文也说 "Tools fail not because of poor models…"。

**反证（这是文中完全缺失、也是最有分量的一块）**：
- **METR（2026-01）**：视觉/计算机操作类任务的 50% 可靠度时程比软件任务**低 40–100 倍**；**许多可靠性关键任务需要 98%+ 的成功率才值得自动化**，因此 50% 时程并不等于「可委托」；且任务时程六年来每约 7 个月翻一番、2024–25 期间每约 4 个月翻一番——**说明能力仍是在变动的那个变量**。
- **run-to-run 方差是模型属性，治理层消除不掉**：pass^4 常比 pass^1 低 15–25 个百分点；90% 的基准分可能对应约 70% 的生产可靠性。这一点直接冲击文中「稳定性：同一输入多次结果一致」这条评测维度——它把一个模型层的固有性质当成了可以通过工程达标的指标。
- **时间上的自我反驳**：2025–26 年 agent 得以部署的公认前提条件恰恰是**模型侧**的——推理模型、更长上下文、MCP/A2A 工具协议、成本坍塌。如果是能力升级解锁了部署，那么直到不久前能力都还是约束。文中的说法因此是**对此刻的描述，不是一条规律**。

**建议改法（可直接采用）**：
> 「对于结构化、可验证、短时程的企业流程，边际瓶颈已从模型转移到集成、数据与组织（Anthropic 2026：46%/42%/39%；Gartner 2025：AI-ready 数据）；但对于长时程、跨系统、要求 98%+ 可靠性的自主决策，模型可靠性仍是硬约束（METR 2026：computer-use 时程低 40–100 倍）。」

同时应披露一个利益结构：「问题不在模型」这个结论的问卷证据，很大比例来自模型厂商自己的调研。
