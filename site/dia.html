一、为什么大多数项目停在 PoC

十条症状。每一条决策者都亲身经历过。

#症状根因
1口径不唯一：三个部门三个答案，会议在争论定义中结束没有机制裁决谁是权威
2只读陷阱：做成会说话的看板，三个月后日活个位数没有写回，价值链多了一环
3数据湖谬误：数据都进来了，业务侧感受不到变化把物理集中当成语义统一
4PoC 与生产的断崖：两周做完，十个月上不了线PoC 证明模型能做对，生产要求做错时的行为
5没有评测：「感觉还不错」缺金标准集，生成式系统尤其容易「看起来对」
6把 Agent 当员工：期望自主，不给输入输出合同拟人化期待代替工程化定义
7组织没有承接：流程照旧，只是多了一个要看的东西只做系统交付，没做运营模式变更
8从数据出发：做出一堆没人要的能力正向推导产生可能性，不产生需求
9静默错误：上游改字段，下游错了三周无数据合同、无断言、无时点正确性
10范围与成本膨胀：本体越建越大，一年没有结果缺少「复杂度必须付租金」的纪律
共同点

十条里只有一条半是模型问题。其余全是语义、闭环、边界与治理问题——这正是本架构要解决的四件事。

二、架构总览

决策智能架构，是把企业的事实与企业的行动，通过一层业务承认的本体缝合起来，并在权限、证据、可逆四条约束下，交给分级授权的智能体去驱动的架构。

D决策界面谁在决策 · 依据什么 · 谁担责
▲ 决策需求向下驱动
A行动可写回 · 可逆分级 · 审批链 · 幂等 · 频次上限
I智能规则 / 模型 / Agent · 工具即本体行动 · 分级自治
O本体★ 中心　对象 · 属性 · 关系 · 事件 · 指标 · 行动绑定
F事实口径权威唯一 · 血缘可追 · 时点正确
▲ 事实向上支撑
横切四约束 · 贯穿全部五层

权限　定义在本体上；Agent 继承调用者权限，无人值守时以担责岗位的委托身份运行。
证据　任何结论可追溯到输入与版本；坏消息不可隐藏；证据链自身也需被治理。
可逆　默认可撤销；R3 自动化需满足四条件，缺一即保留人闸。
运行　环境隔离 · 配额熔断 · 发布回滚 · 可观测。

一个中心

本体是整个架构唯一的语义权威。对上定义智能层能看到什么、能做什么；对下定义事实层必须以什么口径供给；对内承载权限模型。

架构判据

除本体外，不存在第二条通往业务语义的路径。

因为一旦本体只是「一个可选的语义层」，就会立刻出现绕过它的捷径：报表直连数据库、Agent 写自由 SQL、前端硬编码业务公式。三个月后企业就有了第二套、第三套口径，本体退化成文档。

两个方向

向下连接事实——本体的每个对象与指标必须追溯到权威源，满足口径唯一、血缘可追、时点正确。这是可信度的来源。

向上驱动行动——本体的对象上绑定行动，智能层调用行动，人在决策界面审批。这是价值的来源。

缺前者，本体是漂亮的空壳；缺后者，本体是更贵的数据仓库。

三、O · 本体层（中心）

一句话：让机器认识这家企业。

本体不是什么

它不是区别
数据模型数据模型服务于存储与事务效率；本体服务于业务语义与决策
知识图谱图谱通常只读、面向检索；本体必须绑定行动，是可执行的
元数据目录目录服务于「找数据」；本体服务于「做决定」

数据模型回答「怎么存」，知识图谱回答「知道什么」，本体回答「这家企业是什么，以及能对它做什么」。

六个构成要素

要素说明
对象业务名词：客户、订单、SKU、工单、合同
属性分三类：源属性 / 派生属性（只允许一个权威实现）/ 状态属性（必须有状态机）
关系本体相对数据表最大的价值：把跨系统的语义缝合成可遍历的路径
事件发生了什么，带时间戳且不可变。重放与审计的基础
指标只允许一个权威实现，有唯一 Owner。查询层只做只读投影
行动绑定在对象上、可改变企业状态的操作

对象准入五判据

不是所有业务名词都该进本体。必须同时满足五条：

#判据不满足的后果
1有唯一真身（权威源 + 主键）出现多个版本的「客户」，口径战争
2有稳定标识（跨系统映射规则明确）关系连不起来，数据看着有其实用不了
3有明确生命周期（状态机已定义）行动的前置条件无法表达
4有绑定行动或明确决策用途本体膨胀——最常见的失败模式
5有业务 Owner（具体的人，不是部门）变更无人裁决，本体腐化
最常被跳过的一条

判据 4 是防止本体膨胀的唯一闸门。「有 300 张表就建 300 个对象」的项目，都是从跳过它开始的。

从决策倒推，不做全企业本体

最常见的失败路径是「先把全公司本体建完，再谈应用」——这条路会消耗 12–18 个月，几乎必然在业务侧失去耐心之前无法产生结果。

选定一个决策
   ↓
做这个决策需要知道哪些东西？   → 对象（3–7 个）
它们之间是什么关系？           → 关系
决策依据哪几个数？             → 指标
决策的结果是对什么做什么？      → 行动
   ↓
只建这些。其余一概不建。

一个健康的第一版本体规模：5 个以内对象，3 个以内关系，1 个行动。

本体是产品，不是项目产物

一旦本体成为语义权威，它必须具备产品的全部特征：版本、合同、变更流程、废弃策略、Owner、业务语言的文档。

经验规则

没有变更流程的本体，会在六个月内退化成一份没人看的文档。

权限沿本体传播

四个维度：对象级行级属性级行动级

销售 A 通过 Agent 查询时，Agent 看到的必须恰好是销售 A 能看到的那个世界。不存在「AI 账号」这种拥有超级权限的身份。这一条如果破了，整个系统在合规上不可用。

四、F · 事实层

这一层不产生价值，但它决定上面所有价值是否可信。

三个必须

  1. 口径权威唯一同一度量全企业只有一个权威计算实现，查询层只做只读投影。发现第二处实现按缺陷处理，不按「灵活性」处理。
  2. 血缘可追任何数字能在 5 分钟内回答：来自哪个源、经过什么加工、什么口径版本、数据时点、上次更新时间。血缘是可查询的运行时元数据，不是一张架构图。
  3. 时点正确（PIT）用「当时可知」的数据解释当时的事实。靠双时间轴与有效期区间实现。
最贵的静默错误

用今天的主数据解释昨天的业务：用今天的客户分级分析上季度转化、用今天的类目回溯半年前的品类表现、用今天的组织架构归因去年业绩。

时点错误不报错。它会给你一个看起来完全正常、并且偏乐观的数字，直到上线后效果对不上。

把静默错误变成显式失败

数据进入本体前跑一组自动断言，设计原则是不抽样看趋势，而是对账：

类型例子
完整性对账应有记录数 − 实际记录数 = 已归因缺失数（差额必须为 0）
量纲断言金额/数量比值落在合理区间——防止差 100 倍的静默错误
双算校验关键派生量用两条独立实现各算一遍并比对
参照完整性订单引用的客户 ID 必须存在
时序逻辑发货时间 ≥ 下单时间；状态转移合法
跨源交叉与独立数据源比对，偏差超阈值报警

量纲断言与双算校验是投入产出比最高的两条——它们抓的是「看起来完全正常」的那一类错误，恰恰是最贵的那一类。

不可变 + 可重放

原始数据只增不改，修正通过新增记录表达；给定代码版本 + 数据版本能重算出完全相同的结果。

没有这两点，永远无法回答「三周前它为什么给出那个建议」。

接多少数据

判据

每接入一个数据源，能否说出它支撑哪个对象的哪个属性、服务哪个决策？说不出来的不接。

五、A · 行动层

这是分隔「会说话的看板」与「决策智能平台」的那条线。

行动契约：十一个必备要素

缺任何一项都不允许上线。

#要素说明
1前置条件用状态机表达，如「订单状态 ∈ {待发货}」
2参数模式取值范围就是安全边界，如调价幅度 ∈ [−15%, +15%]
3权限人工触发时继承调用者身份；自动执行时以担责岗位的委托身份运行，禁止权限大于担责人
4副作用改变哪些对象状态，触发哪些下游
5幂等键重复执行不产生重复效果。必填项，不是优化项
6可逆性R1 / R2 / R3（见下）
7审批链什么条件下免批，什么条件下强制人工
8审计记录触发者、参数、依据、口径与模型版本、结果
9失败语义失败后状态、是否重试、何时需人工
10频次上限 / 速率限制按对象、按执行者、按全局分别设限。参数范围管单次幅度，管不了「一天五千次，每次都在范围内」
11数据依赖与新鲜度依赖哪些对象/指标、要求多新的数据。没有它，「数据缺失则失败关闭」无从判定

可逆性分级

级别定义例子授权取向
R1 可撤销一键回到原状态，无外部影响改标签、调优先级可较早开放自动
R2 可补偿有明确反向操作调价、创建工单、库存调拨限额内自动
R3 不可逆外部世界已改变已发货、已付款、已触达客户永远需要人
最实用的一个落地模式

把 R3 拆成 R2 + R3：

「自动发货」        = R3，不能自动
拆解后：
「自动创建发货单」   = R2（可作废）  → 可以自动
「确认发货」        = R3（不可逆）  → 保留人闸，一键确认

AI 承担 95% 工作量，人只保留最后那个不可逆的确认动作。

不要制造第二套真相

判据

关掉这个 AI 平台，企业的业务数据是否完全不受影响？
是 → 写回设计正确（平台是决策者与执行者，不是记录者）
否 → 制造了第二套真相，必须重构

例外：平台可以保留决策记录与证据链——这是平台独有的、有价值的资产，不与业务系统冲突。

审批链的关键一行

在历史正常区间内 + 影响面小 + R1/R2   →  自动执行，事后可查
超出正常区间 或 影响面中等            →  单人审批
超出硬阈值 / 影响面大 / R3           →  多级审批 / 强制人工
数据缺失、口径不明、置信度低          →  失败关闭：不执行，明确报告

最后一行是关键：系统在不确定时的默认行为必须是不动作 + 明确报告，而不是「按最佳猜测执行」。

六、I · 智能层

三种智能各归其位

企业里最常见的浪费，是用大模型解决一个 if 语句能解决的问题。选型按顺序问：

  1. 能写成规则吗？能就写规则。企业更看重「每次都一样」，而不是「大多数时候更聪明」。
  2. 规则写不下，有标签数据吗？有就用预测模型。
  3. 输入非结构化、或需要多步综合判断？才用 Agent。

Agent 的能力边界 = 本体暴露的工具集

❌  Agent + 数据库连接 + 「你可以写 SQL 查任何东西」
✅  Agent + 本体工具集 + 「你可以调用这 12 个工具」
不给自由 SQL 的原因后果
口径失控Agent 自拼的公式与财务不一致，结论不可采信
权限失控行级/属性级权限无法在自由 SQL 上强制
不可审计无法回答「这个数怎么算出来的」
不可回归同一问题两次给出不同答案
工具设计要点

工具的失败必须是显式的（NOT_READY: 缺少 8-20 的库存快照），而不是返回空结果——空结果会被 Agent 当成「没有异常」。

分级自治 L0–L4

级别系统做什么人做什么准入条件
L0 观察只输出分析与解释全部决策与执行上线即可
L1 建议推荐动作与理由决策 + 执行离线评测达标
L2 草拟生成参数已填好的动作草稿审批 + 一键执行影子运行期通过
L3 限额自动阈值内自动执行，超限升级例外处理 + 抽检连续 N 期在线指标达标
L4 全自动全量自动执行监控 + 定期审计长期稳定，且仅限 R1/R2
硬规则

R3 不可逆行动最高只能到 L2。
晋级条件必须事前冻结，不能看到结果后临时议定。
降级条件自动生效，不需要审批。
晋级靠证据，不靠信心。

没有评测集就不上线

  1. 离线金标准集（上线前）必须覆盖失败模式：缺数据、口径歧义、极端值、恶意输入。冻结后不得因结果不好而修改——改了就失去了裁决能力。
  2. 影子运行（上线中）在真实数据流上产出建议但不执行，与人的实际决策比对。分歧比一致更有价值：每一个分歧都要归因（系统错 / 人错 / 口径不清）。
  3. 在线抽检（上线后）持续按比例人工复核。L3/L4 不能取消抽检。

指标不只是准确率

维度为什么
弃权率主动说「不确定」的比例。一个从不弃权的系统是危险的
错误分布90% 准确率但错的都是大单，等于不可用
稳定性同一输入多次结果一致——企业要可预测
单次决策成本每次 3 元 × 每天 500 次，只省 2 分钟人工 = 经济上不成立

让系统学会说「这个我不确定，请人来看」，比让它多对几个百分点更有价值。

提示词也是代码

提示词、模型版本、温度参数会改变系统行为，因此必须版本化、绑定证据、变更即回归、可回滚。

典型事故

有人「优化」了提示词，指标悄悄降了 8%，两周后才发现，且无法定位是哪次改动。根因是提示词不在版本控制里。

七、D · 决策界面层

这一层决定项目的方向。方向错了，下面五层做得再好也是白做。

四象限：选谁先做

错误可逆错误不可逆
高频次★ 第一批
自动化价值最高，可快速积累证据		谨慎：需强审批链
适合 L1–L2
低频次价值有限
除非单次价值极高		✗ 不要碰
战略决策，人的领域
最常见的选型错误

选了公司最重要、最有战略价值的决策。那通常是低频、不可逆、多方博弈的——是最不该做第一个的。重要 ≠ 适合先做。

人机权责矩阵

角色定义可以是 AI 吗
建议者提出方案✅ 通常从这里开始
决定者拍板取决于自治级别
执行者实际操作系统✅ 通过行动层
担责者出问题时负责❌ 永远是人
交付时必须回答

哪一个旧动作因此被取消了？
如果答案是「没有，只是多了一个参考」，这个场景在组织意义上没有落地，它会在三个月内消亡。
落地的标志是减法。

界面形态的优先级

  1. 嵌入现有工作流（最优）：ERP 待办、飞书/企微卡片、工单系统推荐
  2. 推送到人所在的地方：告警、日报、审批流
  3. 独立控制台（次选）：仅当需要复杂上下文探索
  4. 对话式界面（谨慎）：适合探索性分析，不适合日常高频决策

对话是探索的界面，不是执行的界面。一个每天要做 200 次的决策，界面应该是一个按钮和一行理由，不是一个输入框。

八、约束四 · 运行 Runtime

2026-08-23 升格

此前它是「R 运行层」，画在事实层之下。但它的内容（隔离、成本、发布回滚、可观测）作用于所有层，与那个位置没有任何关系；且它包含的「权限落到运行时」与约束一重复。现为第四条横切约束。

最不性感，但它是 PoC 与生产之间那道断崖的主体。

环境数据允许的行动
研究/沙箱脱敏或只读副本只读，零写回（凭据级隔离，不靠自觉）
预生产生产数据只读影子行动：记录不执行
生产生产数据完整行动，受权限与自治级别约束。只运行受控发布的不可变版本

成本必须能熔断

生成式系统的边际成本不可忽略，且可以在无人察觉时指数增长。四件事必须在运行约束里强制：预算、配额、熔断、成本归因。

规则

熔断必须是「停」，不是「提醒」。一个只发告警不停止的成本保护，在夜间和周末等于不存在。

发布与回滚

代码、配置、提示词、模型、本体定义、评测集全部版本化，一次发布对应一组确定的版本组合。

规则

回滚不需要审批；需要审批的是发布。

特别提醒：提示词与本体定义的变更，与代码变更享受同等待遇。它们同样改变系统行为，却经常被当成「配置微调」绕过流程——这是生成式系统最常见的事故来源。

模型供应商与版本风险

一处必须承认的边界

本方法论承诺「给定代码版本 + 数据版本可重放」。对托管大模型这个承诺不成立：模型会被下线、涨价、在同一版本号下变更行为；且 run-to-run 方差本身就是模型属性（pass^4 常比 pass^1 低 15–25 个百分点）。

行为漂移：一类不会自己暴露的失效。模型版本更新后理解口径可能发生细微偏移，表现为错误标注长期累积而无人察觉。必须与 run-to-run 方差区分：方差是同一版本内的随机性（多次采样可测），漂移是跨版本的系统性偏移（不会自己暴露）。三条监测手段：①金标准集定期重跑而不只在变更时重跑（托管模型可能在你不知情时更新）②人工推翻率与批准率的趋势 ③输出分布监控。

可行的是「可追溯」而不是「可重放」：证据链记录模型标识 + 版本 + 调用时间；关键决策的输入输出快照入证据链；模型版本变更时强制重跑评测集。

可观测性

技术指标 + 质量指标 + 业务指标，三类缺一不可。

「人工推翻率」是最诚实的指标。它直接度量业务方对系统的真实信任度，通常比技术指标更早报警。

九、四条横切约束

这三条不属于某一层，而是整套架构的设计前提。六层可以裁剪，这三条不可以。

约束一｜权限 Authority

权限定义在本体上；身份上下文必须贯穿「用户 → Agent → 工具 → 数据 → 行动」全链路，中间任何一处退化成服务账号，模型即破。越权返回明确拒绝，不是空结果。

隐蔽风险

销售 A 问「我们最大的客户是谁」，如果 Agent 用超级权限回答了，就等于绕过了原有权限体系。这类泄漏不会触发任何传统安全告警。

约束二｜证据 Evidence

决策/结论
  ├── 触发：谁、什么时候、通过什么入口
  ├── 输入：哪些对象与指标，取值与时间点
  ├── 口径：指标权威实现版本、本体版本
  ├── 推理：规则 / 模型 / 提示词版本
  ├── 输出：建议或已执行的行动、参数
  ├── 人的介入：谁审批、是否被推翻、推翻理由
  └── 结果：执行成功/失败、后续影响
坏消息不可隐藏

拒绝、弃权、失败、人工推翻——全部留痕。人推翻系统建议的理由，是最有价值的改进信号。
界面可以降噪，但不能删除或改写权威状态。做一个只展示成功案例的看板，等于主动放弃了系统改进的唯一信息来源。

约束三｜可逆 Reversibility

运行时体现为失败关闭（Fail-Closed）：

情形正确行为错误行为
数据缺失返回 NOT_READY + 缺什么用 0 或前值填充后继续
口径不明返回 NOT_EVALUATED按最可能的口径猜一个
权限不足返回 DENIED返回空结果
置信度低弃权，转人工输出最佳猜测
断言失败阻断下游告警但继续出结论

降级成「看起来成功」是最危险的失败模式。一个明确的错误会被立刻发现和修复；一个看起来正常的错误会持续污染决策数月。

三者的关系

权限  ──决定──▶  能做什么
  ↓
可逆  ──决定──▶  能自动做到什么程度
  ↓
证据  ──决定──▶  能不能被采信、能不能改进

没有权限，系统不能被授权使用；没有可逆，不能被授权自动；没有证据，不能被采信，也无法晋级。三者共同构成企业 AI 的信任基础设施。技术能力决定上限，这三条决定能不能开始。

维度传统数据中台 / BI决策智能架构
