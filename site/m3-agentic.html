3.1 三种智能形态的选型

形态适用不适用成本可解释性
确定性规则逻辑明确、合规红线、阈值判断规则数量爆炸、需要泛化极低完全
预测模型有标签、有历史、结构化、需量化缺历史、需解释推理链中中
生成/推理 Agent非结构化输入、多步任务、需综合判断高频简单判断、要求确定性输出高需专门设计

判断 按顺序问，不要跳步：①能写成规则吗 → ②规则写不下、有标签数据吗 → ③输入非结构化或需多步判断吗。

能写死的不要用模型，能用小模型的不要用大模型。
这不只是成本问题，更是可解释性与稳定性问题。企业更看重「每次都一样」，而不是「大多数时候更聪明」。

成本的量级（Anthropic 公布）：Agent 约为 chat 的 4 倍 token，多 Agent 约 15 倍。这个倍率应当直接进入选型判断，而不是等上线后才发现。

判断

让模型负责「选哪条路」，让确定性代码负责「走这条路」。模型的输出应尽可能是一个受限的选择，而不是自由文本或自由代码。

3.2 设计模式速查（术语对照，非选型指南）

本节定位已下调。它的用途是让你在别处读到这些术语时知道指的是什么，不是让你「挑一个图来用」。企业里的可靠性主要来自 3.4–3.7 讲的东西。

单 Agent

模式2026 年的状态
Tool Use所有 Agentic 能力的地基。判断 工具设计是单项投入回报最高的一件事。
⚠️ 本站此前写「企业里 80% 的价值来自这一个模式」——这个数字是我编的，没有任何研究支持，已删除。
ReAct循环存活，名字在退场。LangChain 已把 create_react_agent 更名为 create_agent；文字解析式的 Thought:/Action:/Observation: 脚手架已被原生 function calling + 供应商侧推理取代。ReAct 没有过时，它被吸收了；剩下的工作是给循环设边界（迭代上限、成本上限、trace 可观测）。
⚠️ 本站此前把〔争议〕设为「显式 thought 是否还必要」——这个争论已不活跃。真正在争的是思维链作为安全监控手段有多脆弱。
Plan-and-Execute判断 它在 2026 年首先是一个安全模式：在摄入不可信内容之前固定计划，注入就无法改变控制流（见 3.6）。
⚠️ 「计划可被人审查」这个优点会随时间衰减——批准率随时间上升而审查深度下降。这直接冲击 L2 作为长期稳定状态的假设。
Reflection / 自省判断 有客观真值时用外部验证器替代自省更便宜也更可靠。
这是本站论证最扎实的一条，现已坐实：Kamoi et al.（TACL）——「没有任何先前工作展示了仅靠 prompted LLM 反馈的成功自我纠正」，瓶颈在反馈生成；Huang et al.（ICLR 2024）仍然成立。
Router / 分类路由判断 把「无所不能的 Agent」拆成「分类器 + 窄专家」，大幅提升可评测性与可审计性。
⚠️ 它在 2026 年已部分下沉为基础设施（模型路由服务），当前形态是成本/质量级联路由，不是应用层模式。
Structured Output⚠️ 本站此前把它列为「首要设计模式」，这个归类本身就暴露了年份。2026 年它是 API 的基础能力而非模式。
仍然重要（自由文本无法被下游可靠消费，也无法被断言校验），但应作为默认设定。并有一个此前忽略的权衡：严格格式约束可能损害推理质量（EMNLP 2024）。实践取向：先自由推理、再产出结构化结果。

Pipeline「无聊但可靠」。每段可独立评测、独立回滚。

检索

模式2026 年的状态
RAG判断（原标〔共识〕称「默认方案」，已加时间限定）这个默认在 2026 年已经动摇：产业侧正从「向量库 + RAG」转向 agentic search / 检索即工具调用。
不变的判断：RAG 解决的是「知道」，不解决「能做」。
GraphRAG微软已于 2026-08-14 转入维护模式（不再接受新 PR / 新功能）；LazyGraphRAG 从未在开源版发布。决策规则：简单事实检索 文本 60.9 vs 图 60.1（打平）；复杂推理 图 +10.5；上下文摘要 图 +13.1；代价 3–5 倍索引成本。
⚠️ 此前遗漏的告诫：Text2Cypher 与 Text-to-SQL 有同样的准确率问题——换成图查询语言只是转移了语义接地问题。
Text-to-SQL⚠️ 本站此前的禁令「企业生产环境不应使用，只应存在于隔离沙箱」是错的，已改。各大平台都已 GA 且带治理地大规模提供。「隔离沙箱」不是业界控制手段，也解决不了真正的失败模式。
真实的边界是「受治理 vs 不受治理」，不是「生产 vs 沙箱」。受治理意味着：继承调用者 RBAC 的只读角色、受治理的语义层、已验证查询库、确定性 SQL 校验、回归基准。
但原有的直觉有数据支持：dbt 2026 基准 text-to-SQL 90.0% vs 语义层 98.2%；BIRD 榜首 81.95% vs 人类基线 92.96%；LinkedIn 生产实测 9%→48%；Snowflake 自承 Spider 上 90%+、真实 BI 集掉到 51%。
关键论据是失败模式不同：text-to-SQL「有时给你一个貌似合理的错答案」，语义层直接报错——这与本方法论的「失败关闭」是同一个论证。
⚠️ 不要引用任何 text-to-SQL 排行榜名次：CIDR 2026 发现主流基准标注错误率 52.8%–62.8%。
关于「模式优先级」的一处更正

本站此前给出过固定排序（Structured Output + Router + Tool Use > Plan-and-Execute > Pipeline > 其余）。这是过度声明。Anthropic、OpenAI 都主张「从最简单开始」，但没有任何一家发布过线性优先级排名，他们发布的都是决策判据。

保留下来的、站得住的原则只有一条：从最简单的方案开始，每增加一层复杂度都要说出它消除了哪个具体风险。

3.3 编排范式：工作流 vs 自主体

争议 这是当前领域最核心的分歧。

确定性工作流自主 Agent
控制流代码写死模型决定
可评测性每步可测端到端难测
成本可预算波动大
失败模式显式报错悄悄走偏

这个争论 2025 年最著名的一次交锋，以及它的收敛结论

共识 2025-06 相隔 24 小时：Cognition 发《Don't Build Multi-Agents》，Anthropic 发《multi-agent research system》，给出相反建议。收敛结论是「任务决定架构」：

并行、以读为主的工作适合多 Agent 隔离；共享状态、以写为主的工作应当保持单线程。

合并后的立场 · 判断

控制流应当是确定性的，判断应当是模型的；
并行只读可以放开，共享状态的写必须收敛到单线程。

理由是企业的三个硬约束：可评测（每步有明确输入输出）、可归因（出错能定位到步骤）、可放权（「在什么条件下自动」必须可陈述）。

实用折中：确定性骨架 + 模型节点

[确定性] 触发条件判断
      ↓
[模型]   理解与分类  ──→ 结构化输出
      ↓
[确定性] 路由到对应分支
      ↓
[模型]   在该分支内生成参数  ──→ 结构化输出
      ↓
[确定性] 参数边界校验、权限校验、不可信来源校验（见 3.6）
      ↓
[确定性] 调用行动契约
      ↓
[确定性] 审计留痕

3.4 上下文经济学

本节是重构新增。本站此前的「上下文工程与记忆」停留在「放什么、不放什么」的提示词视角，没有把上下文当作有限资源与预算来处理。2025–26 年多数 Agent 工程本质上是预算管理。

核心命题

上下文窗口是稀缺资源。即使窗口足够大，塞满它也是错的——理由与「装不下」无关：

成本（长度直接决定单次决策成本，且 Agent 每一轮都要重发历史）· 可归因（塞进去 200 页，出错时无法知道模型用了哪一段）· 权限（塞进去的每一条都要过权限校验，上下文越大越权风险越大）· 注入面（每一条不可信内容都是一个攻击入口）

上下文的四个来源与优先级

来源企业里的取向
结构化事实（来自本体）首选——只有本体化的事实才带着口径、权限和时点
指令必须版本化
非结构化检索需标注来源与时效；不能替代结构化事实；来自外部方的必须标为不可信
记忆权限与隐私的高风险区

判断 消费级 Agent 的上下文主要靠检索，企业级 Agent 的上下文应当主要来自本体。

四种上下文预算技术

技术企业里的注意点
压缩（compaction）压缩是有损的——被压掉的若是决策依据，证据链就断了。企业里应压缩对话、不压缩证据：证据写入审计记录而不是留在上下文
结构化笔记 / 外部状态与「不要制造第二套真相」有张力：笔记可以存，但不得成为业务状态的权威副本
子 Agent 上下文隔离与 3.3 的「并行只读可放开」一致。回传结论必须带证据引用，否则主 Agent 无法追溯
即时检索对应产业侧从 RAG 转向 agentic search 的转变

代码执行即工具调用（code mode）

判断 这是本站此前完全遗漏、且对成本影响最大的一项。把「逐个调用工具」改为「让模型写一段代码去调用工具」，循环、条件、错误处理随之移入代码：

  • 直接后果：Pipeline 与大半个 Plan-and-Execute 被吸收掉了——它们变成了代码里的控制流，而不是编排层的模式选择
  • 公开的量级：某些任务的 token 消耗从约 15 万降到约 2 千

企业里的约束：代码执行必须在沙箱内、无网络、权限受限，且生成的代码本身应进入审计记录——它是这次决策的推理过程。

组织记忆应当沉淀回本体

判断

记忆有三层：会话内 → 跨会话 → 组织记忆（哪类告警通常是误报、哪个供应商经常延迟）。第三层最有价值，也最被忽略，而它不应该存在向量库里，应该沉淀回本体。

「这个供应商经常延迟」应当是供应商对象上的一个派生属性，可被查询、可被审计、可被质疑，而不是散落在记忆库里的文本。这也是安全考虑：记忆库是上下文投毒的攻击目标，而本体属性有权限、有血缘、有变更记录。

上下文即配置项

提示词、模型版本、温度、检索策略、上下文模板、压缩策略——全部是会改变系统行为的配置：版本化 · 绑定证据 · 变更即回归 · 可回滚。

典型事故

有人「优化」了提示词，指标下降，很久之后才发现，且无法定位是哪次改动。根因是提示词不在版本控制里。
（此前本站在此写「指标悄悄降了 8%」——那个数字是示意不是实测，已删除。）

3.5 工具设计与互操作

❌  Agent + 数据库连接 + 「你可以写 SQL 查任何东西」
✅  Agent + 本体工具集 + 「你可以调用这些工具」

判断 Agent 的能力边界 = 本体暴露给它的工具集。这不是限制智能，是让智能可以被授权。

一处必要的软化

见 3.2 关于 Text-to-SQL 的更正。受治理的自然语言查询在 2026 年是可用的；本原则反对的是不受治理的自由数据访问，不是反对自然语言接口本身。

工具数量：用有出处的数字替换我原来编的阈值

⚠️ 本站此前写「〔共识〕工具过多会显著降低选择准确率」+「〔判断〕超过 15–20 个工具时应先用 Router 分域」。前者无出处，后者的数字是我发明的（碰巧接近一条真实建议，但那是巧合）。

工具选择准确率随暴露工具集增大而下降。
OpenAI 建议单轮可用函数「目标少于 20 个，不过这只是一个软性建议」。
Anthropic 建议超过约 10 个工具即启用工具检索，并实测到准确率恢复：Opus 4 从 49% 提升到 74%、Opus 4.5 从 79.5% 提升到 88.1%，同时 token 减少 85%。
没有任何厂商公布硬性悬崖。

工具设计的五条要点

  1. 粒度贴合业务动作，不贴合数据表✅ 查询客户近 90 天履约异常　❌ select from t_order
  2. 返回必须包含证据引用数据来源、口径版本、时间戳
  3. 失败必须显式且可被模型理解NOT_READY: 缺少 8-20 的库存快照。绝不能返回空结果——空结果会被当成「没有异常」
  4. 数量克制超过约 10 个就该考虑工具检索或 Router 分域
  5. 区分可信与不可信来源（新增）凡返回中包含外部方提供的自由文本（客户留言、供应商备注、邮件正文、网页内容），必须显式标记为不可信，且不得直接决定行动参数

MCP：工具互操作的既成标准

共识 Model Context Protocol 已于 2025-12-09 捐给 Linux Foundation 下的 Agentic AI Foundation，由 Anthropic、OpenAI、Block 共同发起，Google/微软/AWS 支持。

判断 它对本方法论是同向的，应当明确引用而不是回避：MCP 正是「工具即本体行动」这个主张的现成落地协议——把本体的查询与行动暴露为 MCP server，接入成本从 N×M 降到 N+M；企业最关心的网关级鉴权在这一层有位置。

注意点：MCP server 是一个新的攻击面与供应链依赖，应按引入外部依赖的标准审查（见 3.6）。

Agent Skills：分发与策略单元

判断 以「技能包」形式封装能力，对企业最相关的一点不是它节省 token，而是它是一个分发与策略单元——可按组织、按角色授予与回收，可版本化，可审计谁在用哪个版本。这正是本方法论关心的东西，而此前的模式谱系里没有槽位放它。

3.6 Agent 威胁模型与抗注入设计

本节是重构新增，也是本站此前最严重的缺口

全站核心主张是「不要给 Agent 自由 SQL，要给它定义良好的工具」——而工具化 Agent 恰恰是间接提示注入的主要攻击面。本站的权限模型能挡住越权，挡不住权限内的被操纵行动。

这不是假想：EchoLeak（CVE-2025-32711）

共识 2025 年 6 月披露的 EchoLeak 是首个在生产环境 LLM 系统中被武器化、并造成实际数据外泄的提示注入。

项内容
目标Microsoft 365 Copilot（覆盖 Word / Excel / PowerPoint / Outlook / Teams）
触发零点击——一封构造过的普通商务邮件，收件人不需要做任何操作
后果Copilot 处理隐藏指令，静默外泄企业内部数据
评级CVSS 9.3
攻击链绕过微软专门的跨提示注入分类器 XPIA → 用引用式 Markdown 规避链接脱敏 → 利用自动拉取的图片 → 滥用 CSP 允许的 Teams 代理
处置Aim Security 披露，微软服务端修复，确认无在野利用
两条比技术细节更重要的后果 · 判断

① 检测式防御不可依赖。EchoLeak 绕过了一个专门为提示注入设计的分类器。任何「我们加了一个注入检测模型」的方案，都必须假设它会被绕过。防线必须是结构性的——不依赖「认出攻击」，而依赖「即使没认出来，也做不成事」。

② 攻击链由若干各自合理的功能拼成。Markdown 渲染、图片自动加载、CSP 白名单——每一项单独看都是正常特性。因此逐个审查功能不足以发现问题，必须按「不可信内容能走到哪里」这条路径整体审查。

为什么权限模型不够

把 EchoLeak 换成本方法论的语境：设想一个已经完全符合本方法论的系统——Agent 继承调用者权限、只能调用本体行动、参数有范围约束、行动可逆、全程审计。

现在，一个供应商在订单备注里写一句话。Agent 读取订单对象时把这句话带进上下文，随后触发了一次完全在权限内、参数完全在范围内、审计完整的调价或补货。

没有任何一条既有约束被违反，但决策是被外部人操纵的。

判断 这意味着本方法论的四条治理约束还需要补第四类防线：输入可信度。

威胁分类

威胁在本架构中的落点
间接提示注入任何把外部方文本带进上下文的工具返回（3.5 要点 5）
记忆与上下文投毒组织记忆、共享状态、跨会话记忆（3.4）
工具滥用 / 参数操纵行动契约的参数边界与频次上限
越权升级权限约束——这是唯一一类现有约束已覆盖的
供应链（第三方工具 / MCP server / 技能包）3.5。EchoLeak 中被滥用的 Teams 代理就是一个「已被信任的通道」
成本型拒绝服务运行约束的配额与熔断

六条可落地的抗注入设计规则

判断 每一条都与本方法论已有的强项同源，是顺理成章的延伸而非外挂：

#规则与既有原则的关系
1不可信内容必须显式标记，从进入上下文那一刻起带标记延伸自「血缘可追」
2不可信内容不得决定行动参数，参数必须来自结构化事实或用户直接指令延伸自「结构化输出优先」
3高风险行动前做独立复算：校验参数能否由本体事实独立推导，不能则拒绝延伸自「双算校验」
4先定计划，再读内容（Plan-Then-Execute）延伸自「控制流确定性」
5不可信内容触发的行动降一级自治：读到外部文本的那一轮自动 L3→L2延伸自「分级自治」与「失败关闭」
6对抗性用例进评测集，通过判据是「拒绝」而非「答对」延伸自「评测集必须覆盖失败模式」

判断 注意这六条没有一条是「检测注入」。这是刻意的：EchoLeak 证明了检测会被绕过。
六条守的都是「即使注入成功进入上下文，它也无法改变行动参数、无法改变控制流、无法在无人复核的情况下执行」。

一条对 L2 的重要修正：人工确认会退化

判断

2026-06 的纵向研究显示，对 Agent 输出的批准率随时间上升，而审查深度下降。经验规则：批准率 ≥95% 时，这个检查点已经是「确认剧场」，应改为抽样复核。

这直接冲击本方法论把 L2（草拟 + 人工确认）当作长期稳定状态的假设。修正后：L2 是过渡态，不是终点；必须监控批准率，与「人工推翻率」并列；批准率过高时，正确的动作是要么晋级 L3 + 抽检，要么承认这个检查点无效并重新设计——而不是维持一个形式上的确认按钮。

供应链

第三方工具、MCP server、技能包都是新的供应链依赖，应按引入外部依赖的标准审查：来源可信度、版本锁定、变更通知、可撤销、最小权限。

一条硬规则：第三方工具不得直接绑定 R2/R3 行动。它们可以提供信息，行动必须由本企业自己定义的行动契约执行。

落地检查表见 实践 · 合规与安全前置。

3.7 harness：运行期工程

2026 年的实践共识 · 判断

团队从 harness 改造拿到的可靠性提升，大于从「ReAct 换成 Plan-and-Execute」拿到的。

harness 指的是包裹模型的那层运行框架——它决定了循环怎么开始、怎么结束、错误怎么处理、上下文什么时候重置、工具长什么样、权限在哪里检查。

件内容缺失的后果
循环边界最大迭代数、最大耗时、最大成本一次失控循环烧掉一天预算
上下文重置策略什么时候压缩、什么时候开新会话长任务后期质量断崖式下降
验证闸每一步输出在进入下一步前被确定性校验错误逐步放大，最后一步才暴露
工具人体工学工具名、参数名、错误信息是否对模型友好模型反复调错工具，token 与准确率双输
权限门权限检查发生在工具执行处，而不是入口处中途身份切换导致越权
trace 可观测每一步的输入输出、耗时、成本可回放出错无法归因

判断 这六件与本方法论的关系：它们是四条治理约束在运行期的具体实现位置。约束定义了「必须做到什么」，harness 是「在哪里做到」。

3.8 评测方法总结

层时机内容
离线金标准集上线前专家标注的历史案例，必须覆盖失败模式：缺数据、口径歧义、极端值、注入尝试（新增）
影子运行上线中真实数据流上产出建议但不执行，与人的实际决策比对
在线抽检上线后持续按比例人工复核已执行动作

判断 金标准集冻结后不得因结果不好而修改。影子运行阶段分歧比一致更有价值——每个分歧应归因为：系统错 / 人错 / 口径不清。第三类是本体建设最好的输入。

评测方法谱系

方法局限
精确匹配 / 结构校验只能测格式与取值
确定性验证器判断 企业场景应优先用这个——比 LLM 判分便宜且稳定，且验证器质量决定收益上限
人工标注对照成本高，但金标准集只需建一次
LLM-as-Judge争议 与人的一致性因任务而异；存在自我偏好偏差。只应作为补充，不应作为上线判据的唯一依据
轨迹 / trace 评测判断 2026 年企业侧评测重心已从终态正确性转向过程正确性——终态对但过程错的 Agent 在分布外会失败
A/B 分流唯一能证明业务价值的方法，但需要业务方接受实验
一处引用禁忌

OpenTelemetry 的 GenAI 语义约定仍处于 1.0 之前，2026-06 迁至独立仓库且无 tagged release——不要把它当作稳定标准引用。

指标维度

维度说明
弃权率主动说「不确定」的比例。一个从不弃权的系统是危险的
错误分布高准确率但错在高价值样本上，等于不可用
稳定性⚠️ 这不是一个可以靠工程达标的指标：run-to-run 方差是模型属性，pass^4 常比 pass^1 低 15–25 个百分点，90% 的基准分可能对应约 70% 的生产可靠性。应作为需要测量并接受的事实，而不是需要达标的目标
人工批准率新增，见 3.6。≥95% 意味着确认环节已失效
时延 / 单次成本见 投入产出测算

判断 上线后最诚实的指标是人工推翻率——它直接度量业务方的真实信任度。
